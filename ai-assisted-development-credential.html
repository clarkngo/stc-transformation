The Naming Decision: Hook vs. Credential

Keep "vibe coding" where the repo already says it belongs — marketing, not the transcript

"Vibe coding" is a great funnel hook and a poor credential name. CityU's own materials already reached this conclusion — this design just formalizes it.

Top-of-funnel · marketing
"Vibe Coding"

Accessible, low-friction pitch that gets prospective students and iKW applicants in the door. Signals "you can build real things fast."

→
Credential · transcript · employer-facing
AI-Assisted (Spec-First) Software Development

What actually gets assessed, transcripted, and shown to employers. Names the competency, not the vibe.

Why this split, per CityU's own record: the BS-AI feedback synthesis recommends using "Vibe Coding" only for marketing and replacing it with "spec-first engineering" in academic materials — otherwise the brand signals "casual, tool-driven" and breeds a cohort that resists rigor and security. At the GitHub Education Summit, Geoffrey Challen said he dislikes the term because it "implies a certain degree of not caring about the results." A credential is the wrong place to signal not caring.
⚓

Demand Anchor: iKW Cohort

Avoiding the orphaned-badge failure mode

The evidence review's sharpest warning: don't launch credentials without a real demand source. A generic "vibe coding" badge has no employer partner to validate it — exactly the orphaned badge that erodes the brand. This credential sidesteps that by anchoring to a cohort CityU already runs.

  • iKW Summer Program — AI-Enabled Web Design, Programming & Vibe Coding: Korean students travel to Seattle for an in-person cohort, coursework delivered on the same Open edX instance (learn.smartandsecurecomputing.com) used across the ecosystem.
  • MOFU + BOFU compress into one physical visit — the cohort is the demand, already funded and scheduled, with an in-person faculty touchpoint rather than a virtual funnel.
  • Stacks toward the BS in AI — issue it as a credit-bearing entry credential so completers have a real pathway, and CityU has a measurable pipeline step to track.
The iKW cohort plays the role SPD plays for the first-responder credential: a concrete population whose instructors act as the SME validators for the competencies and rubrics. Use them for the same job-analysis and calibration sessions the playbook describes.

The Crux: Assessing Judgment When AI Writes the Code

The one thing that makes this credential different from a normal coding cert

If the AI produces the code, "can they produce working code?" is the wrong question — the tool can. The assessable competence is everything the human still owns: framing the spec, steering the tool, and verifying the result.

This directly answers Challen's objection. "Not caring about the results" is precisely the failure state this credential is designed to detect and exclude. Competence is defined as the opposite of vibes: specifying, reviewing, testing, securing, and understanding AI-produced software.

✕ Vibes (fails) Accepts AI output that "runs," ships it, can't explain how it works, misses the injected security flaw.
✓ Competence (passes) Writes a testable spec, catches where the AI's output is subtly wrong, verifies with tests, fixes it when the model can't, and can defend every design decision.
Design consequence: the highest-signal tasks are the ones where the AI is wrong. A task that hands the learner plausible-but-flawed AI output and asks them to find and fix it separates the competent from the vibes far better than "build me an app."

Performance Tasks

Authentic build work, plus the "catch the AI" tasks that carry the signal

  • Capstone build (SD-1, SD-2, SD-4, SD-7). From a real iKW-relevant brief (e.g., a small web app), produce a spec, build it with AI assistance, ship tests, and document the human/AI split. Deliverable is the working app + spec + test suite + a short build log.
  • Flawed-output review (SD-3). Hand the learner AI-generated code that runs but contains a subtle correctness bug and a maintainability smell. They must find, explain, and fix both.
  • Security injection task (SD-5). Give an app with a planted vulnerability (leaked secret, injectable prompt, unsafe dependency). They must detect and remediate it — mirroring the AI-testing/security week.
  • Live debugging defense (SD-6). In a short session, introduce a failure the model struggles with; the learner debugs it live and explains their reasoning. This is also the authorship check (see Integrity).
Anchor tasks in cleared, reusable scenarios. Build a small library of planted-bug and planted-vuln artifacts so each cohort isn't sourced from scratch — same reuse discipline as the first-responder credential.

Sample Rubric — SD-3: Review & Verify AI-Generated Code

The competency that most directly rebuts "not caring about the results"

Criterion 1 · Not yet 2 · Approaching 3 · Competent 4 · Exemplary
Correctness review Accepts output because it "runs"; misses the bug. Suspects an issue but can't localize it. Finds the correctness bug and explains why it's wrong. Finds it, explains the root cause, and shows the input that triggers it.
Security review Overlooks the planted vulnerability. Notes a vague concern without identifying the flaw. Identifies the vulnerability and its class. Identifies it, remediates it, and names how the AI introduced it.
Verification No test or check applied to the AI output. Runs it manually once; no repeatable test. Writes a test that would catch the defect. Test suite covers the defect and the spec's edge cases.
Understanding Cannot explain what the code does. Explains the happy path only. Explains the code and the fix in their own words. Explains it, the fix, and the trade-offs of an alternative approach.

Passing standard (set with iKW instructors): Competent (3)+ on every criterion; Understanding may not fall below 3 — a learner who can't explain the code has not demonstrated the competency, regardless of output quality.

The "Understanding" row is the anti-vibes guardrail: it makes explanation a pass condition, not a bonus. That's the rubric-level answer to Challen's critique.

Identity & Integrity

When AI assistance is allowed and expected, authorship means understanding — not keystrokes

Low stakes
Practice builds

Unproctored, AI-assisted practice. Skill-building, not certification. AI use fully allowed.

Medium stakes
Capstone + reviews

Verified-track identity. AI use allowed and logged (build log / prompt history). Graded on judgment, tests, and security — not on whether AI helped.

High stakes
Live debugging defense

Short live session: learner extends/fixes their own submission and explains it. Verifies both authorship and understanding at once.

Don't ban the AI — that would assess the wrong thing. The whole point of the credential is competent AI-assisted development, so a lockdown "no tools" exam measures a skill you're not certifying. Instead, verify authorship through a live defense where the learner reasons about and modifies their own work in real time. Someone who "vibed" their way to a passing artifact cannot survive the defense; someone competent barely notices it.

Verifiable issuance

Issue as an Open Badge 3.0 / verifiable credential listing the demonstrated competencies (SD-1…SD-7), assessment type, credit value, and the BS-AI articulation. That metadata is what lets an employer — or the BS-AI registrar — trust and act on it.

Minimum Viable Version

For the next iKW cohort

  • 1
    6–7 competencies (SD-1…SD-7), validated in one job-analysis session with iKW instructors.
  • 2
    1 capstone build + 2 "catch the AI" tasks (flawed-output review + security injection), on cleared iKW-relevant briefs.
  • 3
    Analytic rubrics (start with SD-3 above) calibrated with instructors; capture the sign-off memo.
  • 4
    Live debugging defense as the authorship check — no lockdown proctoring, AI allowed throughout.
  • 5
    Issued as a verifiable, credit-bearing credential that stacks toward the BS in AI; "vibe coding" used only in the recruiting pitch.
This reuses everything from the first-responder build — rater training, rubric format, integrity tiers, issuance — proving the point that the assessment infrastructure is built once and amortized across the credential portfolio.
