How AI 410 Was Built: From Plan to Delivery

A lessons-learned report on building AI 410: AI Engineering, the first fully built course for the upcoming Bachelor of Science in AI. It is written for program managers and colleagues who are new to this way of planning, building, teaching and delivering a course with an AI assistant.

1. The short version

Five things to take away if you read nothing else.

  1. Building is no longer the slow part. Keeping things consistent is. With an AI assistant, a guide, a lesson or a rubric can be drafted in minutes. Most of the late effort went into making the syllabus, the student site, Brightspace and the rubrics say the same thing.
  2. Lock the non-negotiables on day one. The fixed course description, "everything runs in Codespaces", "free tiers first" and the Dean's two-week rule arrived partway through. Each one caused a round of rework. Write them down before any content is built.
  3. Decide structure before content. The course changed shape twice: from 8 weekly units to 4 merged units, then to 2 weeks per unit. Every reshape meant rewriting guides, lessons and schedules.
  4. Give every artifact exactly one source of truth. The syllabus lives in OneDrive, the student site in one GitHub repo, and instructor material in a private repo. Brightspace links to them instead of holding copies. Each time two copies drifted, old errors came back.
  5. When AI can write the code, grade the thinking. The course grades students on judging, explaining and improving AI-produced work (the CEAU cycle), not on whether the code runs.

2. What was delivered

AI 410 is a 10-week, 5-credit course. Students build one AI chat assistant across four hands-on units, then a team Term Project.

23published student pages, WCAG 2.2 AA
4 + 4HOS and Application Challenge repo templates
175Knowledge Check questions (35 per module)
12Brightspace rubrics, each matching its points
1,000point gradebook, aligned to the syllabus
ModuleWeeksWhat students build and learn
1 · Foundations & the Agentic Loop1–2A chat backend that calls tools: when the model decides and when code decides.
2 · Embeddings, Chunking & RAG3–4Grounding answers in documents with a vector database (Chroma).
3 · Guardrails & Async Processing5–6Validating model output and moving slow work to a queue.
4 · Mobile, Push & Observability7–8A mobile client, push notifications, and tracing with Langfuse.
5 · Term Project9–10Teams finish, present and demo a full-stack app combining all four units. Phases 1 and 2 run alongside Weeks 1–8.

Where it lives

  • Student site (public): the Interactive Lesson Lab at cityuseattle.github.io/ai410. It has lessons, HOS guides, simulators and reference pages. Materials are CC BY 4.0 and the starter code is MIT.
  • Instructor material (private): a private repository in the CityU GitHub organization. It holds the syllabus, teaching guide, answer keys, Knowledge Check banks and delivery walkthrough.
  • Student work: GitHub Classroom repositories, created from the 8 templates and opened in GitHub Codespaces. Students need no local installs.
  • Delivery and grades: the Brightspace development shell. It holds assignments, discussions, quizzes, rubrics and the gradebook, and links out to the student site.
  • Syllabus master: the Word file in OneDrive. The repository copy mirrors it word for word.

3. The new way of working

One faculty subject-matter expert worked with an AI coding assistant (Claude Code) as a build partner. Every change was a reviewed pull request in a git repository.

How the pieces connect

→
DeliverBrightspace links to the site and holds assignments, quizzes, rubrics and grades.

Why this matters for a program manager: the bottleneck moves from "how long does it take to write" to "how quickly can the faculty lead make and review decisions." Plan the schedule around decision points and review time, not drafting time.

4. Timeline: plan to delivery

The course went through eight phases. The two reshapes (Sep 15 and Sep 30) explain most of the rework.

  1. Jan – Apr 14, 2026Program approved

    The BSAI proposal went through drafts and was approved by the Academic Affairs Committee on April 14. AI 410's course description and outcomes were fixed from that point.

  2. Aug 25 – Sep 14Version 1: eight weekly units

    Schedule, 8 weekly hands-on guides and starter code. The stack was simplified repeatedly for beginners: Anthropic API to the Gemini free tier on day one, Codespaces support (Sep 2), Supabase to Chroma (Sep 8), and static frontends to Streamlit (Sep 14).

  3. Sep 15Redesign: "merge, don't reduce"

    Eight units became four merged units, and nothing was dropped. Added the CEAU grading cycle, Muddiest Points, Concept Debates, Application Challenges, a Concept Companion and comparable-courses research. The 8-unit version was archived.

  4. Sep 23Constraints written down

    The standing rules were made explicit in BSAI Course Design Constraints: the official description is fixed, everything runs in Codespaces, and free tiers come first.

  5. Sep 28 – Sep 30Reshape: two weeks per unit

    The second half of the course was rebuilt around the team project, then every unit was stretched across two weeks to meet the Dean's requirement. Interactive lessons and four browser simulators were built, and AI 420–440 were realigned to AI 410.

  6. Oct 6 – Oct 13Test as a student, rework assessments

    A Codespaces test run found a retired AI model and an assistant that set up the wrong workspace, and both were fixed in the guides. Application Challenges became "spec, build, defend". The syllabus moved to the Word file, and lessons got week tabs and due-date lists.

  7. Oct 21 – Oct 23Hardening and hand-off

    Student work moved to GitHub Classroom repos. The site passed a WCAG 2.2 AA accessibility audit. Recorded lectures became written notes with captioned videos. The course moved into the CityU GitHub organization (a public site and a private instructor repo), the Knowledge Check banks went live, and "Team Project" was renamed "Term Project".

  8. Oct 24 – Oct 25Brightspace build and audit

    Every rubric was matched to its assignment's points and given level descriptions. The Term Project rubrics were split one per deliverable. Syllabus versions 7–11 were reconciled, and legacy units and old template files were removed.

5. Design decisions and why

These are the choices that make AI 410 different from a traditional course. They are reusable for AI 420, 430 and 440.

DecisionWhat it meansWhy
Merge, don't reduceEight skills are taught as four paired units. An AI assistant scaffolds the boilerplate.Learning a new concept and a new tool eight times in a row overloads beginners. Pairing them cuts the load without cutting content.
CEAU cycleEach unit is graded on Create (20%) plus Evaluate, Analyze and Understand & Refine (80%).If AI can write working code, "does it run?" no longer measures understanding. Judging, explaining and hand-improving the code does.
Two weeks per unitWeek 1: lecture, Muddiest Point, debate, build, evaluate. Week 2: analyze, refine, Application Challenge, Knowledge Check.This is the Dean's requirement. It turns the time saved on plumbing into deeper analysis instead of a faster pace.
Muddiest Point (Just-in-Time Teaching)Before each build, students post the one thing that confused them.The instructor adjusts the lecture to real confusion, and students learn to ask precise questions.
Staged Concept DebatesStudents argue an assigned side, then the opposite side, then a real position that cites a classmate.The staging rewards reasoning and makes generic AI-written posts easy to spot and weak to submit.
Application Challenge: spec, build, defendA short build against provided tests, one open decision, and a one-page memo defending it.Transfer to a new scenario, plus a written defense that only the student can give.
Low-stakes Knowledge Checks10 questions drawn from 35 per module, hint-only feedback, unlimited retakes, a 15-minute limit.With retakes there's little reason to cheat, and the time limit makes pasting into AI impractical. The goal is retention, not policing.
Term Project in three phasesTeams release v0.3, then v0.7, then v1.0, each with an ISCAP-format report. It ends with a presentation and a demo video.Steady progress instead of a last-minute build, and a research-style writing artifact students can show.
Codespaces and free tiersEvery unit runs in the browser. Paid keys are optional only.Students are mostly new to software, and STC has no lab or GPU budget.

6. Lessons learned

What worked, what we would change, and a recommendation for each.

ChangeConstraints arrived after content

The fixed description, the Codespaces and free-tier rules, and the two-week rule were each applied after material existed. The two-week rule alone meant rewriting schedules, guides and lessons, and realigning three other courses.

Recommendation: start every course with a one-page constraints document, reviewed by the Dean and program lead, before any content is built.

ChangeCopies drift, and old errors come back

Fixes made only in the repository copy of the syllabus never reached the OneDrive master, so the next edit reintroduced them: Week 8 instead of Week 7, 40 points instead of 50. Brightspace rubrics also drifted from the syllabus. One rubric mentioned "Week 1" when the syllabus didn't, and point totals didn't match their assignments.

Recommendation: name one master per artifact and write it down. Fix the master first, then copy it word for word. Brightspace should link to content, not hold its own copy.

WorkedAI as a consistency checker, not just a writer

The most valuable late-stage work was cross-checking. The assistant diffed each syllabus version against the repository copy and returned a table of exact fixes. It also audited every Brightspace assignment, quiz, discussion and rubric against the syllabus.

Recommendation: schedule an audit pass after every structural change, and before term start, across syllabus, site and LMS.

WorkedSmall, reviewed changes in git

Every change went through a pull request: about 60 merged pull requests for AI 410 in this repository alone, before the hand-off to the CityU organization. Nothing was lost, every decision has a date, and the archived 8-unit version is still one click away.

Recommendation: keep course content in version control from day one, even for faculty who don't usually use git. The assistant handles the mechanics.

ChangeTest as a student, in the real environment, early

The first real Codespaces run (Oct 6) found that the AI model named in the starter prompts had been retired for new accounts, and that the built-in coding assistant set up a new workspace instead of using the starter folder. A student would have been stuck on day one.

Recommendation: do a "fresh account" dry run of every unit as soon as it exists. Pin model names in one place, and re-test before each term, because free-tier services change without notice.

WorkedAccessibility as an automated gate

Instead of a one-off review, the publishing check fails if a page is missing alt text, labels, titles or zoom support. All 23 student pages pass WCAG 2.2 AA in light and dark mode.

Recommendation: build accessibility checks into publishing for every new course, and re-run the full audit before each term.

ChangeThe LMS is the slowest, most manual mile

The Brightspace shell came late (Oct 21). Building it meant matching 1,000 points of grade items, 16 assignment folders, 10 discussions, 5 quizzes and 12 rubrics to the syllabus. Several Brightspace features have no usable API, so parts of the work had to go through the web interface.

Recommendation: request the development shell at the start of the build, not the end. Budget dedicated time for it, and treat "rubric total = assignment points" as a launch checklist item.

ChangeRenames are expensive

"Capstone" became "Team/Term Project", then "Team Project" became "Term Project". Each rename touched pages, templates, file names, Brightspace items, rubrics and three sister courses.

Recommendation: settle names for activities and deliverables in the constraints document. Keep web addresses and page IDs stable even when display names change, because Brightspace links depend on them.

WorkedA plan B for media

Narrated lecture videos stalled on logistics (no microphone or time to record). Rather than leave gaps, each lecture became written notes with a worked example, common mistakes, a quick check and a curated video. Videos with human captions are marked "watch first" and others are marked optional.

Recommendation: make text-first lectures the default. Recorded video is an upgrade, not a dependency for launch.

WorkedInstitutional ownership before launch

The course was moved from a personal account into the CityU GitHub organization. Answer keys and quiz banks were split into a private repository, and a clear license was added, so the university owns the course and can staff it if people change.

Recommendation: create the organization repositories, decide what is public and what is private, and choose a license at the start of the build.

WorkedMarketing from the course itself (added Oct 30)

After delivery, the same way of working produced a 1:45 marketing video from scripted recordings of the public student site, with an AI voiceover and no camera. The process, the problems and a playbook are in How the AI 410 Marketing Video Was Made.

Recommendation: plan a short video once a course's student site is public. Script the recording so it can be redone when the site changes, and have a person review anything the assistant can't perceive, such as how the voice sounds.

7. Playbook for the next course

The order we would follow for AI 420, 430 and 440, with AI 410 as the structural template.

  • Week 0 · PlanCopy the approved description and outcomes word for word. Write the constraints document: structure, tools, free-tier limits and names. Get sign-off.
  • Week 0 · PlanRequest the Brightspace development shell. Create the public and private organization repositories and choose a license.
  • Week 1 · StructureFix the schedule and grading weights by copying AI 410 (four units × two weeks, then the Term Project). Draft the syllabus master in OneDrive.
  • Weeks 2–4 · BuildFor each unit: starter code template, guide, interactive lesson, simulator, Application Challenge and Knowledge Check bank. Do a fresh-account Codespaces test before moving on.
  • Week 5 · DeliverBuild Brightspace from the syllabus: grade items, folders, discussions, quizzes, rubrics (totals equal to points), and link topics to the site.
  • Week 6 · AuditCross-check the syllabus, site, templates and Brightspace. Run the accessibility audit. Get a peer faculty review.
  • Before termRe-test with fresh accounts (model names, free tiers). Set up the roster, Classroom invites and organization access.

8. What a program manager should track

Drafting is fast, so track decisions, reviews and integration instead.

9. Open items and risks

  • Single-builder dependency. One faculty lead built and knows the whole course. A second instructor should shadow a delivery and get access to the instructor repository.
  • Free-tier and model churn. AI services retire models and change limits without notice. A pre-term re-test is required every term.
  • Brightspace finishing work. Readings & Resources for Modules 2–4 still need to be added, and Knowledge Check settings need a final review.
  • Launch logistics. The Classroom roster and organization invites are set up per cohort.
  • Recorded lectures. Narrated decks for Units 2–4 are on hold. The written notes cover them in the meantime.
  • Sister courses. AI 420–440 follow AI 410's structure, but still need the same Brightspace build, audit and hand-off.

10. Glossary

HOS
Hands-On Skill unit. A two-week build-and-analyze unit; AI 410 has four.
CEAU
Create, Evaluate, Analyze, Understand & Refine. The four graded stages of every HOS.
MP
Muddiest Point. A short post naming what confused you, submitted before each build.
CD
Concept Debate. A staged discussion where students argue assigned sides on a design question.
AC
Application Challenge. A short individual build-and-defend task after each HOS.
KC
Knowledge Check. A low-stakes Brightspace quiz with unlimited retakes.
TP
Term Project. A team-built full-stack app delivered in three phases.
Codespaces
GitHub's browser-based development environment, so students need no local setup.
GitHub Classroom
Gives each student their own copy of a template repository to work and submit in.
Pull request
A proposed change in git that is reviewed before it is merged into the course.
Interactive Lesson Lab
The public AI 410 student site: lessons, guides and simulators.
