1. The problem

The industry-standard physical AI tools don't fit how BSAI students work.

  • NVIDIA Isaac Sim, Isaac Lab and Omniverse need an NVIDIA RTX GPU workstation or a paid cloud GPU. Codespaces has no GPU, and most students don't own an RTX card.
  • ROS 2 with Gazebo runs in a container, but its 3D GUI is heavy and fragile over a remote desktop, and setup failures eat the two-week HOS.
  • The current AI 440 outline (MQTT/Grafana, a PyTorch PINN, MuJoCo + BlenderProc, SB3) is feasible, but the units don't share a world. Students never watch one machine and its twin over the whole term.

The risk is a course that names Physical AI and can't let students drive a physical system and its twin.

2. The design principle

Real engine, real interfaces, simulated plant.

A homemade simulator would teach a homemade tool, and that isn't marketable. So the Twin Lab simulates only what we can't provide, the physical robot. Everything students touch is an industry standard:

  • Real physics engine. DeepMind's official MuJoCo WebAssembly build (@mujoco/mujoco, Apache-2.0) runs in the browser. Contact, friction, inertia and motor saturation are computed, not scripted. The same model file runs in Python mujoco in a Codespace.
  • Real interfaces. Students write Python nodes against ROS 2's rclpy API with standard message types (geometry_msgs/Twist, sensor_msgs/LaserScan, nav_msgs/Odometry…). The code ports to a real ROS 2 install almost unchanged.
  • Real file formats. Robots and scenes are MJCF and export to OpenUSD (.usda), which Omniverse and Isaac Sim open. Logs are planned as MCAP for Foxglove, and policies as ONNX.
  • A "real robot" with secrets. The plant is a second MuJoCo world built from hidden, per-serial parameters (wheel radii, mass, motor gain, latency, sensor bias). The twin starts from the spec sheet. Closing that gap is the sim-to-real work employers describe.

3. What employers ask for

A small sample of 2026 robotics-simulation postings, not a market survey.

  • A physics simulator. Postings name Isaac Sim, and several accept MuJoCo, Gazebo, Drake or Webots as equivalents.
  • ROS 2 is usually required, often for connecting simulation to robot software.
  • OpenUSD appears for asset and scene work (authoring, composition, referencing).
  • Sim-to-real is the differentiator. Postings ask candidates to measure and reduce the gap between simulated and real behaviour, compare simulated sensor data against the real robot, and do system identification.
  • Domain randomisation, synthetic data, CI for simulation tests, and Python (C++ a plus).

5. Architecture

One static site, one shared model format, two runtimes.

Browser · GitHub Pages (no install)

  • MuJoCo WASM: plant (hidden parameters) + twin (student's parameters)
  • Topic bus with ROS 2 message types and rates
  • Python nodes via Pyodide and an rclpy-shaped API
  • Three.js view, twin modes, calibration replay, exports

Codespace · same files, heavier work

  • pip install mujoco==3.17.0: the browser's MJCF loads byte-identical (verified)
  • Offline system ID and PINN training on exported run logs (PyTorch CPU)
  • Gymnasium + SB3 policy training → ONNX
  • Optional: real ROS 2 + rosbridge, for students who want the real thing
Shared formats: MJCF (robot and world) · OpenUSD (scenes) · ROS 2 message schemas · JSON/MCAP (logs) · ONNX (policies). Students' finished twins are deployable static sites, so the O6 "deploy a functional digital twin" can mean a live URL on the student's own GitHub Pages: a portfolio piece an employer can click.

Load cost: about 9 MB for MuJoCo and about 10 MB for Python on first visit, then cached. Single-threaded MuJoCo needs no special server headers, so GitHub Pages works as is.

7. What the prototype proved

Twin Lab v0.1: one HTML file, with MuJoCo, Three.js and Pyodide pinned from jsDelivr.

Feasibility test 1 passed: real physics on GitHub Pages MuJoCo 3.17 WASM loads from a CDN without special headers and steps two worlds plus a 1-second look-ahead in real time. The exact MJCF the browser builds loads in Python mujoco 3.17.0 (SHA-256 match) and behaves the same. The .usda export opens in Pixar's usd-core with correct units, axis and geometry.

System identification on the AMR-0042 run, scored by replaying its commands through the twin (RMSE):

  • Spec-sheet twin: 1.36 m.
  • Correct wheel radii only: 0.19 m. Radii dominate.
  • Latency, or mass + motor gain, alone: barely moves the error.
  • All true parameters: 0.00 m.

Each replay takes about 0.4 s, so students can search by hand or write a fitting script.

Modelling issues found and fixed while building it

These matter because students would hit them on real tools too.

  • Caster friction. MuJoCo combines contact friction by taking the larger of the two surfaces, so "frictionless" casters dragged at the floor's friction. Fixed with contact priority.
  • Lidar seeing itself. A rangefinder only ignores its own body, so beams starting on a child body hit the robot's lidar puck. Fixed by mounting the beams on the base.
  • Turning error from wide tyres. Wide tyres scrub in turns and spinning wheels over-report rotation. Fixed with thin tyres, noslip solver iterations, and gyro-fused heading (what real AMR drivers do).

Not yet in v0.1

Camera and synthetic data, manipulator and drone packs, MCAP export, the Gymnasium wrapper, the rosbridge mode, MQTT bridge, accessibility audit (keyboard teleop and tabs work; no screen-reader pass yet), and unmodelled effects so a perfect calibration never reaches exactly zero error.

Two ways to stay compliant: (a) open it from inside the Codespace through a forwarded port, with the static files in the course repo; or (b) read the rule as "no local installs", which the lab meets better than Codespaces does. 3. Free tiers and free resources firstfits MuJoCo (Apache-2.0), Three.js (MIT), Pyodide (MPL-2.0), GitHub Pages, Codespaces free hours. No keys. NVIDIA tools appear only as optional "open your export in Isaac Sim" stretch work, never graded.

9. What it can't do, honestly

  • No RTX path-traced rendering. Synthetic images will be raster quality, not Omniverse photorealism. Teach the pipeline (randomise → render → auto-label → measure the gap), not the renderer.
  • No GPU-parallel RL. Isaac Lab trains thousands of environments at once; we train a few on CPU. Keep policies small (driving, pushing, docking).
  • No DDS networking. The bus mimics ROS 2 topics but not QoS, discovery or tf2. The optional rosbridge mode is where students meet the real middleware.
  • The "real robot" is still a simulation. It has hidden differences but the same physics engine, so effects outside MuJoCo (cable drag, sensor temperature drift) only appear if we model them. Say so plainly in the course; real hardware is already out of scope in the outline.
  • Marketing language. Students learn MuJoCo, ROS 2 interfaces and OpenUSD, not Isaac Sim. Course copy should say "skills that transfer to Isaac Sim and Omniverse", not "Isaac Sim experience".
