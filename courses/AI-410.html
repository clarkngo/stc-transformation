In plain terms: you'll build the same kind of app all term, a chat assistant that gets smarter over time. In each module you start from an AI-assisted working version and spend your time judging, explaining and improving it, not just typing it from scratch. Then you apply the same idea to a new scenario on your own. No prior backend experience assumed.

Course Description: AI Engineering applies rigorous software engineering principles to the development and deployment of autonomous, learning-based systems. This course emphasizes leveraging Large Language Models (LLMs) within purpose-built software solutions to address real-world business challenges. Students will explore system architecture for agent development and integration, context engineering through Retrieval-Augmented Generation (RAG) and vector databases, and best practices for deploying and monitoring AI models in production environments. The curriculum also covers probabilistic logic for handling nondeterministic outputs. Learners gain hands-on experience building a full-stack AI solution, focusing on asynchronous data processing, push-based AI notifications, and seamless integration of vector stores for dynamic RAG applications. Mastery of these concepts will equip students to design and implement robust AI-powered applications using full-stack AI.

Course Outcomes

As a result of this course, students will know or be able to do the following:

  1. O1 — Define and explain the essential components of full-stack AI systems, such as LLM architecture, agentic loops, and the differences between prompt engineering and context engineering.
  2. O2 — Design and implement a Retrieval-Augmented Generation (RAG) pipeline using vector databases to deliver context to autonomous agents.
  3. O3 — Analyze and break down the multi-layered architecture of agent-driven applications to identify and address potential bottlenecks in asynchronous data processing and nondeterministic reasoning.
  4. O4 — Evaluate and critique the performance and reliability of production AI models using appropriate observability tools and metrics for assessing probabilistic outputs.
  5. O5 — Develop a fully functional, agent-driven mobile application that seamlessly integrates real-time notifications and persistent vector storage into a comprehensive full-stack solution.

Course Design Philosophy: Merge, Don't Reduce

Each AI Challenge (AIC) pairs a new AI/agent concept with a new piece of backend tooling (FastAPI, Chroma, Redis/RQ, Expo, Langfuse). Asking students new to production software to absorb a new concept and a new tech component in the same sitting, eight times in a row, is cognitive overload on two axes at once, so two related skills are taught together as one AIC, without doubling the load.

The fix isn't cutting content — it's changing what AI does in the loop

Every one of the original 8 skills still gets taught, and all 5 Outcomes still get covered; nothing is dropped. What changes is that students use an AI coding assistant to scaffold the boilerplate (the FastAPI wiring, the Chroma setup, the Redis connection) instead of spending class time building it line by line. Per the Dean's requirement, each AIC runs across two full weeks, so the time that used to go into fighting plumbing goes into genuinely deep Evaluate, Analyze, and Understand & Refine work, and into applying the skill to a new scenario.

The CEAU Cycle — Replacing "Score the Code"

If an AI assistant can produce working code, grading whether the code works stops measuring whether the student understands it. Traditional Bloom's builds up to Create as the hardest, final stage. In an AI-assisted course that ordering is backwards: Create is now the fast, cheap part. The stages that actually take skill come after it:

Traditional Bloom's OrderAI-Era Reordered Stage
Stage 1: FoundationalCreate / Scaffold
Stage 2: Critical GateEvaluate
Stage 3: Deep DissectionAnalyze
Stage 4: MasteryUnderstand & Refine
1

Create / Scaffold

Student uses an AI assistant to get a working version running fast: the starting point, not the deliverable.

2

Evaluate

Is the AI-produced result actually correct? What's missing, wrong, or fragile? The critical gate: can the student judge output they didn't write by hand?

3

Analyze

Why does this work, mechanically? Dissect one specific piece (a function, a query, a request flow) and explain it in the student's own words.

4

Understand & Refine

Extend or fix something in the scaffold by hand, no AI: the mastery check. Can they change it correctly without AI doing that part too?

How Each Module Runs

Each module centres on one AIC, worth 100 points (10% of the course), in two parts:

  • Part A: Build (Week 1) — Create/Scaffold, then Evaluate.
  • Part B: Apply (Week 2) — Analyze and Understand & Refine on the build, then an individual Part B challenge: build to a short spec with provided tests in a new scenario, make one decision the spec leaves open, and defend it in DECISIONS.md (about 60–90 minutes). It ends with a short Post Mortem in NOTES.md: what's still unclear, what you'd do differently (including how you used AI), and what you'll carry into the Term Project. No AI for the Post Mortem.

Both parts live in one GitHub Classroom repo, and the last push before the end of Week 2 is the submission; there is no Brightspace upload for the AIC. It's graded once, at the end of Week 2: 60 points for the build (the CEAU stages, with the Post Mortem graded inside Understand) and 40 for the challenge (Design 20, Justify 20). The Classroom repos keep the old name: AIC 1 is AI410-HOS01, and so on.

Every week also has its own Concept Debate and Knowledge Check, graded separately from the AIC: Debate A and a theory check in Week 1, Debate B and a skill check (reading code, logs and tests) in Week 2.

Instructor setup — Concept Debate groups (one time, before CD01 opens)

Split the class into two debate groups of about the same size. You can assign the groups yourself or let students choose, as long as the two groups stay close to even. The groups switch sides with every debate (rotation below). One way to set it up in Brightspace:

  1. Go to Communication → Groups → New Category. Name it "Concept Debate Groups", with 2 groups and the group prefix "Debate Group".
  2. To let students choose: use a Self Enrollment type and set each group's maximum to half the class (rounded up), so the sides stay even. To assign them yourself: use # of Groups – Auto Enrollment with Randomize users in groups checked, or enroll students by hand.
  3. Skip the "set up discussion areas" option. Each CD stays one whole-class discussion topic, because students must read the other group's posts for Stages 2 and 3.
  4. Tell students to find their group under Communication → Groups, and point them to the rotation below. It's also shown in each module's lesson.

New words this week
Frontend & backend —
the two halves of the app: what the user sees (frontend) versus the server holding your API key (backend).
LLM —
the AI model itself (here, Google's Gemini) that generates the reply.
Agentic loop & tool calling —
the cycle where the model decides to use a real function instead of just replying with text, and the result comes back before it answers.
This week
  • Lecture & Concept Debate A (CD01).
  • Create/Scaffold — prompt an AI assistant to build a full-stack chat app that can call a real tool.
  • Evaluate — test it on purpose (does it call the tool when it should, skip it when it shouldn't, fail gracefully?) and note what you found.
  • Knowledge Check (theory), KC01 — what's the difference between the frontend and backend, and why does the API key live in the backend only? What happens, step by step, from typing a message to the agent deciding to call a tool?

New words this week
Embedding & chunking —
splitting a document into pieces (chunking), then turning each piece into a list of numbers representing its meaning (embedding).
Vector database —
a database built to store embeddings and quickly find the closest matches to a query.
RAG (Retrieval-Augmented Generation) —
having the model answer using retrieved chunks of real text instead of only its own memory.
This week

Week 5 — AIC 3 · Part A: Build — Guardrails & Async Processing

Merges legacy Weeks 6–7.

Handling nondeterministic output (validation/retry guardrails) and moving long-running work off the request path (background jobs): the two reliability concerns that show up together in any real production agent.

Outcome 3 Module 3 lesson → AIC 3 build guide →Simulator →
New words this week
Nondeterministic & guardrail —
the same input can produce a different output each time (nondeterministic); a guardrail checks that output and retries or fixes it if something's wrong.
Asynchronous (async), queue & worker —
work that runs in the background instead of making the user wait, held in a waiting line (queue) and picked up by a separate process (worker).
This week
  • Lecture & Concept Debate A (CD05).
  • Create/Scaffold — prompt an AI assistant to add a validate/retry guardrail around a tool call, plus a Redis-backed queue and worker for document ingestion.
  • Evaluate — test a malformed tool call, confirm a document upload returns a job ID instantly and reports status correctly, and confirm chat stays responsive while a job runs.
  • Knowledge Check (theory), KC05 — why can't you trust every model response without checking it first? Why move long-running work to a background job instead of making the user wait?
