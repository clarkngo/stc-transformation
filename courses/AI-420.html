AI 420: Agentic AI

5 Credits Prerequisites: CS 352, DS 479 10 Weeks 4 Merged HOS Capstone: Portfolio Project Course design v0.3 — Sep 24, 2026
This is the course design: outcomes, stack, schedule, grading, and what each unit builds. The hands-on guides, starter code, and answer keys are built (in faculty testing), following the same pattern as AI 410 (see the side-by-side comparison). Background on the stack choices: AI 420 / 430 / 440 Technology Stack Brainstorm. Every choice here follows the BSAI Course Design Constraints: the course description is fixed, everything runs in GitHub Codespaces, and free tiers come first.
In plain terms: in AI 410 you built an app with an AI model inside it. In AI 420 you build software where the AI decides what to do next. It picks a tool, looks at what came back, notices when it went wrong, and tries again, all without a person clicking "next." Every unit adds a working agent to your portfolio. By Week 10 you'll have taken one real, manual business process and handed it to a team of agents, with numbers showing how well they do it.

Course Description: Agentic AI empowers students to design intelligent systems capable of perceiving their environment, reasoning through complex, multi-step plans, utilizing external tools (such as APIs, web browsers, and databases), and self-correcting their actions to achieve specific outcomes without ongoing human intervention. This course emphasizes the core principles of agency, including individual agencies, the development of custom tools, advanced reasoning techniques, multi-agent workflows, and orchestration. By the end of the course, students will have built professional portfolios featuring a range of functional agent examples, acquired industry-ready AI engineering skills, and developed agentic mindsets to transform manual business processes into automated sequences of agent-driven tasks.

Course Outcomes

As a result of this course, students will know or be able to do the following:

  1. O1 — Explain the core components of an "AI Agent" (Reasoning, Planning, Tool Use, and Memory), distinguish them from standard LLM inference, and identify common agentic patterns.
  2. O2 — Implement custom tools and integrate them into an agentic loop via function calling.
  3. O3 — Analyze agent reasoning traces to diagnose why an agent failed at a given task, such as identifying tool-call errors or logic loops.
  4. O4 — Assess agent system performance through agent-on-agent testing and quantitative metrics, including success rate, cost per task, and latency.
  5. O5 — Produce a professional-grade portfolio project that automates a multi-step business process, such as an autonomous marketing department or a self-healing coding assistant.

Course Design: Same CEAU Cycle, Applied to Agents

AI 420 keeps AI 410's CEAU rubric. It fits agents especially well because an agent's output changes from run to run. "Did the code run" says almost nothing, and "can you explain what the agent did and why" says a lot.

1

Create / Scaffold

Use an AI coding assistant to get the unit's agent running. Not graded on its own.

2

Evaluate

Run the agent against the unit's task set. Where does it succeed, fail, or succeed for the wrong reason?

3

Analyze

Open one trace and walk it step by step: what the model saw, what it decided, which tool it called, and what came back.

4

Understand & Refine

Fix or extend one behavior by hand (a tool, a prompt, a stop condition), then show the before/after run.

The portfolio accumulates. It isn't assembled at the end.

Each HOS ends with a committed, runnable agent in the student's portfolio repo, with a short README: what it does, a trace screenshot, and one lesson learned. By Week 6 every student already has four working agent examples, which covers the "range of functional agent examples" in the course description. The capstone then adds the centerpiece.

Weekly Breakdown

Week 1 — HOS 1: Anatomy of an Agent: Inference vs. the Agentic Loop

Merges: agent components & LLM inference · agentic patterns.

Students solve the same task twice: once with a single LLM call, then with a loop they write themselves (model → tool call → observation → model again, until done). With no framework hiding the loop, the four components are easy to point at in the code. Reasoning is the model's decision at each step, planning is how it breaks the task down, tool use is the function calls, and memory is the growing message history. The unit closes with a tour of the common patterns: ReAct, plan-and-execute, reflection, and routing.

Outcome 1 Open hands-on guide →
What gets built
  1. Baseline: one Gemini call answers a multi-step research question. It often guesses or makes things up.
  2. A hand-written ReAct loop in about 60 lines of Python, with three tools (Wikipedia search, Wikipedia intro, calculator; free, no key) and a step cap. New unit.
  3. The same agent in ADK (patterned on agent-development hos01–hos02). Students match ADK's Events view to the steps of the loop they wrote.
  4. A plan-and-execute variant, written by hand in Stage 4, compared against ReAct on the same five tasks.
  5. Committed to the student's portfolio repo as hos-01-agent-anatomy/ with a README.
New words this week
Inference —
one request to the model, one response back. No actions, no second chances.
Agent —
a model placed in a loop where it can take actions (tool calls), see the results, and decide what to do next until the task is done.
ReAct —
"Reason + Act": the model alternates between thinking about the next step and taking it.
Plan-and-execute —
the model writes a full plan first, then works through it step by step.
Application Challenge

Given three short workflow descriptions from a real business (e.g. answering a customer email, reconciling an invoice, drafting a weekly report), decide which ones actually need an agent and which are better as a single LLM call or a fixed script. Justify each choice using the four components. Saying "no agent needed" with a good reason is a strong answer.

Knowledge check
  • Point to the line in your loop where "reasoning" happens, and to the line where "memory" grows.
  • What would happen to your agent if you removed the step cap?

Week 2 — HOS 2: Custom Tools, MCP & Memory

Merges: custom tool development & function calling · agent memory.

The course description names three kinds of external tools: APIs, web browsers, and databases. Students build one custom tool of each kind, write their function-calling schemas, and serve all three from a small MCP server. An ADK agent then uses them. The unit's second half adds memory. Short-term memory is session state within one run. Long-term memory lives in Chroma, running locally in the Codespace, where the agent writes what it learned so a later run can recall it.

Outcome 2 Outcome 1 Open hands-on guide →
What gets built
  1. API tool: marine weather (wind, gusts, waves) from Open-Meteo, a real public API that is free and needs no key. It's provided as the worked example the other tools follow.
  2. Browser tool: fetches a page and returns clean text, with a length limit so the page doesn't flood the context.
  3. Database tool: read-only SQL against Harbor Supply Co.'s SQLite database (a marine supply store), protected twice: a single-SELECT check, and the database opened read-only.
  4. All three served over MCP and used by an ADK operations agent. Tool errors are returned to the model as observations, not raised as crashes.
  5. Reference reading: agent-development hos05–06 (session state and persistent memory) and hos07 (real API tools).
  6. Stage 4, by hand: two narrow, typed tools (order_status, low_stock_report) that the model should prefer over free-form SQL.
  7. Long-term memory: the agent saves a customer preference in run 1 and uses it in run 2.
  8. Committed to the portfolio repo as hos-02-tools-mcp-memory/.
New words this week
Tool schema —
the name, description, and parameter types the model reads to decide whether and how to call a tool. The description matters as much as the code.
MCP (Model Context Protocol) —
a standard way to package tools so any compatible agent or harness can discover and call them.
Short-term vs. long-term memory —
what the agent holds during one task, versus what it stores so it can recall it in a future task.
Application Challenge

You're given a poorly written tool schema (vague description, loosely typed parameters, no error contract). Predict three specific ways a model would misuse it, rewrite it, and explain which change you expect to matter most.

Knowledge check
  • Why return a tool error to the model instead of letting the program crash?
  • What should go into long-term memory, and what should never go there?

Week 3 — HOS 3: Reasoning Traces, Failure Diagnosis & Self-Correction

Merges: trace analysis · self-correcting agents.

Students get Harbor Supply Co.'s customer-support agent, which looks fine and fails in five planted ways: a tool-argument error that crashes the run, a call to a tool that doesn't exist (after which the agent tells the customer the refund went through), a loop that repeats the same call, a silently truncated result that produces a confident wrong total, and a vaguely described tool that quotes the store's wholesale cost as the price. They trace it into Langfuse and find each failure from the trace alone before reading the source. Then they fix each cause and add generic self-correction: tool errors returned as something the model can read, repeated-call detection, and a step budget.

Outcome 3 Open hands-on guide →
What gets built
  1. A local trace per scenario, then Langfuse on every model call and tool call (same free account as AI 410 HOS 4). Students write this prompt themselves.
  2. Reference reading: agent-development hos09 (the callbacks the guards use) and hos12 (how a loop is supposed to end).
  3. A failure log: for each planted bug, the trace step where it shows up, the symptom, and the root cause.
  4. Stage 4, by hand: the fixes plus guards.py (an on_tool_error_callback and a repeated-call before_tool_callback), with before/after traces showing the agent recovering on its own.
  5. Committed to the portfolio repo as hos-03-traces-self-correction/.
New words this week
Reasoning trace —
the step-by-step record of a run: each model input and output, each tool call and its result, with timing and token counts.
Logic loop —
the agent keeps repeating the same action (or a short cycle of actions) without getting closer to done.
Reflection —
a step where the agent reviews its own last result and decides whether it's good enough or needs another try.
Application Challenge

Diagnose three unfamiliar exported traces from a different agent than the one you built. For each, name the failure type, the exact step where it first appears, and the smallest change that would prevent it. You get no access to the source code, which is how on-call debugging usually works.

Knowledge check
  • How can you tell a logic loop from an agent that is legitimately retrying?
  • Why is the "confident wrong answer" the hardest failure to catch, and what would catch it?

Week 4 — HOS 4: Multi-Agent Orchestration & Agent-on-Agent Evaluation

Merges: multi-agent workflows & orchestration · quantitative evaluation.

Students split last week's repaired single agent into a coordinator that delegates to specialist agents (ADK's sub_agents). Then they test both versions the way industry does: a simulated-user agent plays the customer across 12 scenarios, and a judge agent grades each outcome against a rubric. Every run logs success rate, cost per task (from token counts × price), and latency (p50/p95). The key comparison is whether the multi-agent version actually beat the single agent, or just cost more.

Outcome 4 Open hands-on guide →
What gets built
  1. A coordinator + 3 specialist agents (orders, catalog, reports), each holding only its own tools. Reference reading: agent-development hos07–hos08 (supervisor, team) and hos10–12 (sequential, parallel, loop).
  2. An eval harness: scenario file → simulated user → agent system → judge → metrics table.
  3. A one-page metrics report comparing the single-agent and multi-agent versions on all three metrics.
  4. Stage 4, by hand: agreement.py, which measures how often the judge agrees with the student's own grading, and in which direction it errs.
  5. Committed to the portfolio repo as hos-04-multi-agent-evaluation/.
New words this week
Orchestration —
the logic that decides which agent runs when: in sequence, in parallel, or in a loop until a condition is met.
Agent-on-agent testing —
using one agent to act as a user and another to grade the results, so hundreds of test conversations can run without a person.
Success rate · cost per task · latency —
how often it finished correctly · how much each finished task cost in model usage · how long it took, typically reported as median (p50) and slow-case (p95).
Application Challenge

A vendor claims their agent has "a 94% success rate." Write the five questions you'd ask before believing it: about the test set, the judge, the cost, the latency, and what counted as "success." Then say which answer would make you walk away.

Knowledge check
  • Why can't an LLM judge be trusted without a human spot-check?
  • Name a case where adding more agents makes a system worse.

Week 5 — Checkpoint: Failure Clinic

No new build. Students swap portfolio agents with a peer and try to break them with adversarial inputs, missing data, and tool outages. Each student then diagnoses the failures in their own agent from the peer's traces. This is the Forward Deployed Engineer habit from the Spencer Liu conversation: run the same plan against different agents and study where execution diverges before anything ships.

Outcome 3 Outcome 4
Review prompt — no new vocabulary this week
  • Which failure in your agent did you not see coming, and which trace step revealed it?
  • Which of your four portfolio agents would you trust to run unattended overnight, and why only that one?

Week 6 — Process-Mapping Workshop

Where the "agentic mindset" in the course description gets practiced directly. Students pick a real manual business process (from a job, an internship, a CityU office, or a partner employer), shadow or interview someone who does it, and map it step by step. For each step they decide: agent, deterministic code, or human checkpoint, and why. The map becomes the capstone's scope. Teams form (or students confirm going solo).

Outcome 1 Outcome 5
Review prompt
  • Which step in your process is the one an agent is most likely to get wrong, and what happens downstream if it does?
  • How will you know, with a number, that your automation is better than the manual version?

Weeks 7–9 — Portfolio Capstone Project

Automate the process mapped in Week 6. The course description's examples, an autonomous marketing department (research → draft → brand review → schedule) or a self-healing coding assistant (read failing test → diagnose → patch → re-run → open PR), are both acceptable starting points. The vendored ADK samples marketing-agency and software-bug-assistant in agent-development match them closely and can serve as starters. So is any real process that meets the minimum bar below.

Minimum bar for a "professional-grade" capstone
  • Runs end-to-end from a single trigger, with no human clicks between steps except justified checkpoints.
  • At least 3 custom tools (served over MCP), and at least 2 cooperating agents.
  • At least one self-correction mechanism, shown working in a real trace.
  • An eval suite of 15+ agent-on-agent scenarios, reporting success rate, cost per task, and latency.
  • A portfolio README a hiring manager could read in 3 minutes: the problem, architecture diagram, metrics, one failure and how it was fixed, and a demo video link.
Progress checks
  • Week 7 — Build: process map finalized; agents and tools working on the happy path.
  • Week 8 — Harden: self-correction in place; eval harness runs; first metrics exist, even if they're bad.
  • Week 9 — Measure & polish: final eval run, metrics report, README, and demo rehearsed. No new features.

Week 10 — Final Demo & Portfolio Review

Live run of the capstone from a single trigger, followed by a walkthrough of one real failure trace from development: what broke, how it showed up in the trace, and what fixed it. Peers review one another's portfolio repos using the minimum-bar checklist.

O1–O5
Self-check before you present
  • Can you name where reasoning, planning, tool use, and memory each live in your capstone?
  • Can you state your success rate, cost per task, and p95 latency from memory, and say what you'd change to improve the worst of the three?
