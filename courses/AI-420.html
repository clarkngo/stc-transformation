AI 420: Agentic AI

5 Credits Prerequisites: CS 352, DS 479 10 Weeks 4 Merged HOS Term Project Course design v0.7 — Nov 4, 2026
This is the course design: outcomes, stack, schedule, grading, and what each unit builds. Since Nov 3, 2026, students work in Google Antigravity first and build every agent in Google ADK, with the same four HOS titles. The earlier design (a hand-built loop before ADK, Chroma, Langfuse, all in Codespaces) is kept in the archived Nov 4 version of this page, with its hands-on guides and starter code and interactive lessons. In plain terms: in AI 410 you built an app with an AI model inside it. In AI 420 you build software where the AI decides what to do next. It picks a tool, looks at what came back, notices when it went wrong, and tries again, all without a person clicking "next." Every unit adds a working agent to your portfolio. By Week 10 you'll have taken one real, manual business process and handed it to a team of agents, with numbers showing how well they do it.

Course Description: Agentic AI empowers students to design intelligent systems capable of perceiving their environment, reasoning through complex, multi-step plans, utilizing external tools (such as APIs, web browsers, and databases), and self-correcting their actions to achieve specific outcomes without ongoing human intervention. This course emphasizes the core principles of agency, including individual agencies, the development of custom tools, advanced reasoning techniques, multi-agent workflows, and orchestration. By the end of the course, students will have built professional portfolios featuring a range of functional agent examples, acquired industry-ready AI engineering skills, and developed agentic mindsets to transform manual business processes into automated sequences of agent-driven tasks.

Course Outcomes

As a result of this course, students will know or be able to do the following:

  1. CO1 — Explain the core components of an "AI Agent" (Reasoning, Planning, Tool Use, and Memory), distinguish them from standard LLM inference, and identify common agentic patterns.
  2. CO2 — Implement custom tools and integrate them into an agentic loop via function calling.
  3. CO3 — Analyze agent reasoning traces to diagnose why an agent failed at a given task, such as identifying tool-call errors or logic loops.
  4. CO4 — Assess agent system performance through agent-on-agent testing and quantitative metrics, including success rate, cost per task, and latency.
  5. CO5 — Produce a professional-grade portfolio project that automates a multi-step business process, such as an autonomous marketing department or a self-healing coding assistant.

Course Design: Same CEAU Cycle, Applied to Agents

AI 420 keeps AI 410's CEAU rubric. It fits agents especially well because an agent's output changes from run to run. "Did the code run" says almost nothing, and "can you explain what the agent did and why" says a lot.

1

Create / Scaffold

Direct Antigravity to get the unit's agent running: ask for a plan, review it, then approve. Graded as engagement (20% of the HOS).

2

Evaluate

Run the agent against the unit's task set. Where does it succeed, fail, or succeed for the wrong reason?

3

Analyze

Open one trace and walk it step by step: what the model saw, what it decided, which tool it called, and what came back.

4

Understand & Refine

Fix or extend one behavior by hand (a tool, a prompt, a stop condition), then show the before/after run.

The portfolio accumulates. It isn't assembled at the end.

Each HOS ends with a committed, runnable ADK agent in that HOS's repo, with the student's NOTES.md (one section per CEAU stage) and screenshots, including a trace. By Week 8 every student already has four working agent examples, which covers the "range of functional agent examples" in the course description. The Term Project then adds the centerpiece.

Weekly Breakdown

Each merged HOS spans two weeks: the first builds and judges (Lecture, Muddiest Point, Concept Debate, Create/Scaffold, Evaluate), the second explains and masters (Analyze, Understand & Refine, Application Challenge, Knowledge Check, and the portfolio agent is committed).

Week 1 — HOS 1 (1 of 2): Anatomy of an Agent: Inference vs. the Agentic Loop — Build & Evaluate

Merges: agent components & LLM inference · agentic patterns.

Students meet the four agent components twice. First they watch them in a coding agent: they give Antigravity a small, safe job, review its plan, and note where it reasons, plans, uses a tool and remembers. Then they build one: the same multi-step research questions answered by a single LLM call and by an ADK agent with real tools. ADK's Events tab shows every step of the loop (model → tool call → observation → model again, until done), so each component is easy to point at. The unit closes with a tour of the common patterns: ReAct, plan-and-execute, reflection, and routing.

CO1 · CO2
What gets built (across both weeks)
  1. Baseline: one Gemini call answers a multi-step research question. It often guesses or makes things up.
  2. An Antigravity warm-up: a small README task done through /plan, with the plan reviewed before approval.
  3. An ADK research agent, written through a prompt to Antigravity, with three function tools (Wikipedia search, Wikipedia intro, calculator; free, no key). Students run it in adk web and compare it with the baseline on five questions, including a run with a tight step budget (max_llm_calls).
  4. A plan-and-execute variant, written by hand in Stage 4 (Week 2) as a SequentialAgent (planner, executor, writer), compared against the first agent on the same five tasks.
  5. Committed to the student's HOS 1 repo, with NOTES.md and screenshots.
New words this week
Inference —
one request to the model, one response back. No actions, no second chances.
Agent —
a model placed in a loop where it can take actions (tool calls), see the results, and decide what to do next until the task is done.
ReAct —
"Reason + Act": the model alternates between thinking about the next step and taking it.
Plan-and-execute —
the model writes a full plan first, then works through it step by step.
This week's stages
  • Muddiest Point & Concept Debate — submitted/staged before and during the build.
  • Create/Scaffold — the Antigravity warm-up and the ADK research agent, built through prompts to Antigravity.
  • Evaluate — run the baseline and the agent on the same research questions: where does the agent beat the single call, where does it still guess, and where did Antigravity's plan and its work differ?
Term Project — introduced this week

No deliverable due yet. The Term Project is worth 20% of your grade and asks you to combine all 4 HOS to automate one real, multi-step business process, presented in Week 10. Start thinking now about a team (or going solo) and a rough idea: notice manual processes around you, at work, in an internship, or in a CityU office. Full description under Weeks 9–10 below.

Week 3 — HOS 2 (1 of 2): Custom Tools, MCP & Memory — Build & Evaluate

Merges: custom tool development & function calling · agent memory.

The course description names three kinds of external tools: APIs, web browsers, and databases. Students build one custom tool of each kind, write their function-calling schemas, and serve all three from a small MCP server, which an ADK agent reaches through McpToolset. The unit's second half adds memory. Short-term memory is session state within one conversation. Long-term memory is state with the app: or user: prefix, saved by a SQLite session service (adk web --session_service_uri "sqlite:///./sessions.db"), where the agent writes what it learned so a later run can recall it.

CO1 · CO2
What gets built (across both weeks)
  1. API tool: marine weather (wind, gusts, waves) from Open-Meteo, a real public API that is free and needs no key. It's provided as the worked example the other tools follow.
  2. Browser tool: fetches a page and returns clean text, with a length limit so the page doesn't flood the context.
  3. Database tool: read-only SQL against Harbor Supply Co.'s SQLite database (a marine supply store), protected twice: a single-SELECT check, and the database opened read-only.
  4. All three served over MCP and used by an ADK operations agent. Tool errors are returned to the model as observations, not raised as crashes.
  5. Reference reading: the ADK documentation on sessions, state and memory, and on MCP tools.
  6. Stage 4 (Week 4), by hand: two narrow, typed tools (order_status, low_stock_report) that the model should prefer over free-form SQL.
  7. Long-term memory: the agent saves a customer preference in run 1 and uses it in run 2.
  8. Committed to the student's HOS 2 repo, with NOTES.md and screenshots.
New words this week
Tool schema —
the name, description, and parameter types the model reads to decide whether and how to call a tool. The description matters as much as the code.
MCP (Model Context Protocol) —
a standard way to package tools so any compatible agent or harness can discover and call them.
Short-term vs. long-term memory —
what the agent holds during one task, versus what it stores so it can recall it in a future task.
This week's stages
  • Muddiest Point & Concept Debate — submitted/staged before and during the build.
  • Create/Scaffold — the three tools on an MCP server, the ADK operations agent, and long-term memory in saved session state, built through Antigravity.
  • Evaluate — test questions that need each tool, a tool failure, and a question that should be answered from memory across two runs.

Application Challenge

Lakeview Property Management's tenant agent works, mostly, but its three tools were written in a hurry. Students predict how a model would misuse each one, rebuild them as narrow, typed tools on an MCP server until the provided tests pass, decide what the agent may remember about a tenant, and defend those decisions.

Knowledge check

  • What should go into long-term memory, and what should never go there?

Week 5 — HOS 3 (1 of 2): Reasoning Traces, Failure Diagnosis & Self-Correction — Build & Evaluate

Merges: trace analysis · self-correcting agents.

Students get Harbor Supply Co.'s customer-support agent, which looks fine and fails in five planted ways: a tool-argument error that crashes the run, a call to a tool that doesn't exist (after which the agent tells the customer the refund went through), a loop that repeats the same call, a silently truncated result that produces a confident wrong total, and a vaguely described tool that quotes the store's wholesale cost as the price. They build a trace recorder from ADK callbacks, compare its traces with adk web's Trace view, and find each failure from the traces alone before reading the source. Then they fix each cause and add generic self-correction: tool errors returned as something the model can read, repeated-call detection, and a step budget.

CO3
What gets built (across both weeks)
  1. A trace recorder (tracing.py) built from ADK's before/after model and tool callbacks, switched on with TRACE=1, writing one trace per scenario. Students write the Antigravity prompt from a spec themselves. Langfuse or Cloud Trace via OpenTelemetry is an optional extra.
  2. Reference reading: the ADK documentation on callbacks and on loop agents (how a loop is supposed to end).
  3. A failure log: for each planted bug, the trace step where it shows up, the symptom, and the root cause.
  4. Stage 4 (Week 6), by hand: the fixes plus guards.py (an on_tool_error_callback and a repeated-call before_tool_callback), with before/after traces showing the agent recovering on its own. Optional: a reflection LoopAgent or tool confirmation for refunds.
  5. Committed to the student's HOS 3 repo, with NOTES.md and screenshots.
New words this week
Reasoning trace —
the step-by-step record of a run: each model input and output, each tool call and its result, with timing and token counts.
Logic loop —
the agent keeps repeating the same action (or a short cycle of actions) without getting closer to done.
Reflection —
a step where the agent reviews its own last result and decides whether it's good enough or needs another try.
This week's stages
  • Muddiest Point & Concept Debate — submitted/staged before and during the build.
  • Create/Scaffold — the trace recorder on every model and tool call, built through Antigravity without opening the agent's code.
  • Evaluate — run each planted-failure scenario and start the failure log from the traces alone, before reading the source.

Finish HOS 3, then a quick, lightweight check-in on the Term Project introduced back in Week 1.

CO3

Application Challenge

Northgate Community Food Bank's scheduling agent misbehaved three times, and the coordinator exported the traces. Students diagnose each failure from the traces alone (no source access first), then write the guards as ADK callbacks to a spec checked by provided tests, including a hand-off rule, and defend which failure they'd fix first.

Knowledge check

Term Project — mid-course checkpoint

Not graded on depth — just confirms you're not starting Week 9 from zero. Submit: your team (or confirm going solo), and a one-paragraph project idea naming the manual business process you'll automate and which HOS pieces it'll combine.

Week 7 — HOS 4 (1 of 2): Multi-Agent Orchestration & Agent-on-Agent Evaluation — Build & Evaluate

Merges: multi-agent workflows & orchestration · quantitative evaluation.

Students split their repaired HOS 3 single agent into a coordinator that delegates to specialist agents (ADK's sub_agents). Then they test both versions the way industry does: adk eval runs 12 conversation scenarios, with ADK's simulated user playing the customer and an LLM judge grading each conversation against a written rubric. A student-written report turns the results into success rate, cost per task (from token counts × price), and latency (p50/p95). The key comparison is whether the multi-agent version actually beat the single agent, or just cost more.

CO4
What gets built (across both weeks)
  1. A coordinator + 3 specialist agents (orders, catalog, reports), each holding only its own tools. Reference reading: the ADK documentation on multi-agent systems and workflow agents (sequential, parallel, loop, graph).
  2. An evaluation with adk eval: an eval set of conversation scenarios, a config with a rubric-based judge and efficiency criteria, and report.py for the metrics table.
  3. A one-page metrics report comparing the single-agent and multi-agent versions on all three metrics.
  4. Stage 4 (Week 8), by hand: agreement.py, which measures how often the judge agrees with the student's own grading, and in which direction it errs.
  5. Committed to the student's HOS 4 repo, with NOTES.md and screenshots.
New words this week
Orchestration —
the logic that decides which agent runs when: in sequence, in parallel, or in a loop until a condition is met.
Agent-on-agent testing —
using one agent to act as a user and another to grade the results, so hundreds of test conversations can run without a person.
Success rate · cost per task · latency —
how often it finished correctly · how much each finished task cost in model usage · how long it took, typically reported as median (p50) and slow-case (p95).
This week's stages
  • Muddiest Point & Concept Debate — submitted/staged before and during the build.
  • Create/Scaffold — the coordinator and specialist sub-agents, the eval set and the eval config, built through Antigravity from a goal (no prompt given).
  • Evaluate — run the 12 scenarios against both versions and fill in the metrics table.

Application Challenge

A vendor claims its invoice-processing agent team has "a 94% success rate." Students build their own judge and evaluation harness, measure the team on fifteen scenarios against the claim (success rate, cost per task, p95 latency), compare the judge with their own grading, and write the five questions they'd ask the vendor and their recommendation.

Knowledge check
  • Why can't an LLM judge be trusted without a human spot-check?
  • Name a case where adding more agents makes a system worse.
Architecture & Bottleneck Review (folded in)
  • Can you draw, from memory, how a request moves through an agent system that combines all 4 HOS: the loop, the tools and memory, the self-correction guards, and the coordinator with its specialists?
  • Where in that path could it slow down, cost too much, or fail silently, and which trace would show it?
Integration Concept Debate — connecting all 4 HOS

Same staged format as every HOS's CD, but the topic spans the whole course, e.g. "which is the bigger production risk: a single agent with too many tools, or a team of agents with no evaluation?"

Week 9 — Term Project: Plan & Build Begins

Students (team or individual, their choice) apply the 4 HOS together to automate one real manual business process — the project is a synthesis of what was built in Weeks 1–8, not a new concept. The course description's examples, an autonomous marketing department (research → draft → brand review → schedule) or a self-healing coding assistant (read failing test → diagnose → patch → re-run → open PR), are both acceptable starting points. The vendored ADK samples marketing-agency and software-bug-assistant in agent-development match them closely and can serve as starters. So is any real process that meets the minimum bar below. Everything technical was already built once in HOS 1–4; the work here is synthesis.

A few days of lightweight planning (you've had the idea since Week 1 and a checkpoint in Week 6, so this isn't starting cold), using a compact version of Scrum, then straight into building:

  • Process map: map the manual process step by step (shadow or interview someone who does it). For each step, decide: agent, deterministic code, or human checkpoint, and why. This is the course description's "agentic mindset" in practice.
  • Backlog: each step of your process map becomes a user story ("As a [user], I want [capability], so that [benefit]"). Pick what you can really finish by Week 10; everything else stays backlog, not a promise.
  • Standups: short, regular check-ins while building (async in a group chat is fine): done, next, blocked. Solo students keep a daily log.
  • Review: the Week 10 demo, including what didn't make it in.

Project management tool (all free): GitHub Projects is recommended, since it turns the issues in your project repo into a Kanban board with no extra sign-up. Trello and Notion also work.

Example project — an autonomous marketing department for a small business
  • HOS 1 (agent loop and patterns): a plan-and-execute coordinator that turns "promote next month's workshop" into research, draft, review, and schedule steps.
  • HOS 2 (custom tools, MCP, memory): tools to read the business's website, look up past campaign results in a database, and save brand-voice rules to long-term memory.
  • HOS 3 (traces, self-correction): a brand-review step that rejects off-voice drafts and sends them back, and a repeat-call guard, both visible in recorded traces.
  • HOS 4 (multi-agent, evaluation): researcher, copywriter, and reviewer agents, tested on 15+ scenarios by a simulated business owner and a judge, with success rate, cost per campaign, and latency.

Litmus test for any idea: can you point to one part and say "this is HOS 3, and here's the trace showing it recover"? If every HOS has an honest answer, the scope is real.

Progress check
  • Early Week 9: process mapped and scope locked as a short backlog, with a rough architecture sketch (which agents, which tools), a first draft of your 15+ eval scenarios, roles assigned if it's a team, and a PM tool set up. Check early whether your eval run fits the Gemini free tier's rate limits.

Minimum bar for a "professional-grade" portfolio project (CO5)
  • Runs end-to-end from a single trigger, with no human clicks between steps except justified checkpoints.
  • At least 3 custom tools (served over MCP), and at least 2 cooperating agents.
  • At least one self-correction mechanism, shown working in a real trace.
  • An eval suite of 15+ agent-on-agent scenarios, reporting success rate, cost per task, and latency.
  • A portfolio README a hiring manager could read in 3 minutes: the problem, architecture diagram, metrics, one failure and how it was fixed, and a demo video link.
