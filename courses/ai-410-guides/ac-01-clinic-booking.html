Application Challenge 1 — Cascade Family Clinic Booking Agent

Est. 60–90 min Outcome 1 After HOS 1 · end of Week 2 Individual AI assistant allowed — disclose it 5% of final grade
This challenge follows the BSAI course design constraints: it adapts to AI 410's official Outcome 1, runs entirely in GitHub Codespaces, and uses only free tiers. The tests need no API key; the chat demo uses your free Gemini key from HOS 1.

Goal

Take the tool-calling skill from HOS 1 to a business you haven't seen: build the tools a clinic's booking agent needs from a written spec, make one decision the spec leaves open, and defend which capabilities the model should, and shouldn't, be able to call.

The scenario

Cascade Family Clinic (fictional) has two providers and a front desk that is overwhelmed with scheduling calls. They want a chat assistant patients can use to find a time, book it, and cancel. A teammate already wrote the chat app (the same agentic loop you built in HOS 1) and the clinic's data. The tools are missing. That's your job.

Two things about the app you should know before you start:

  • The app knows who is logged in. agent.py passes the logged-in patient's ID into every tool call itself. Your schemas must not let the model choose a patient.
  • The clinic runs on a fixed clock: Monday, November 2, 2026, 9:00 a.m. Use clinic_data.now(), never datetime.now(), so the tests always agree.

The spec

Every requirement below is checked by a provided test in tests/test_tools.py.

ToolMust doMust refuse (as an error the model can read)
find_open_slots(date, provider_id?)Return one day's open slots, sorted by time, optionally for one provider. Skip booked slots and slots that already started. No openings is an empty list, not an error.A date that isn't YYYY-MM-DD; an unknown provider.
book_appointment(slot_id)Book an open slot for the logged-in patient.Unknown slot or patient; a slot that's taken; a slot that already started.
cancel_appointment(slot_id)Cancel the patient's own appointment when it's more than 24 hours away, and reopen the slot.A slot that doesn't exist or isn't this patient's.
Schemas in TOOLSOne per tool, with a real description (the model reads it to decide when to call the tool).Any schema that exposes patient_id.

Every error returns {"error": "..."} and changes nothing. That's the HOS 1 rule: a tool that fails should tell the model, not crash the request.

The open decision: late cancellations

The front desk's only instruction was: "Patients should be able to cancel through the chat." The clinic charges a $40 fee for cancelling less than 24 hours ahead. Nobody said what the assistant should do inside that window. Should it cancel and charge? Refuse? Something else?

There's no single right answer, and no provided test for this case. You decide, implement your rule in cancel_appointment, prove it with your own tests, and defend it in DECISIONS.md.

The rest of the wish list

The clinic manager also asked for two more tools. You don't build them. In your memo, decide for each: expose it to the model, expose it with limits, or don't expose it, and write the schema for anything you'd expose. "Don't expose it" with a good reason is a strong answer.

  • view_patient_record: "so the assistant can answer questions about a patient's history."
  • send_sms: "so the assistant can text patients reminders."

Look at what's actually in a patient record in clinic_data.py before you decide.

Steps

1Open it and run the tests

Open the AC 1 starter-code folder in GitHub Codespaces. It installs everything for you. Then run:

pytest

Almost everything fails with NotImplementedError. That's your to-do list.

2Build the tools and schemas

Fill in tools.py until pytest passes. You may use an AI assistant (Copilot Chat in Agent mode, or another). If you do, tell it to work in this existing workspace, not a new one. Read what it writes: you'll defend it.

3Make the late-cancellation call

Implement your rule for appointments less than 24 hours away. Write at least two tests in tests/test_my_rules.py: one showing your rule, and one for the edge you think is most likely to go wrong. The file lists slots that are useful for this.

4Run the assistant

Put your free Gemini key in .env (copied from .env.example), then send these messages. The app prints every tool call, so the transcript shows what actually ran.

python agent.py --patient P1001
you> What does Dr. Patel have open tomorrow?
you> Book the 10 a.m. one.
you> quit

python agent.py --patient P1002
you> I need to cancel my appointment today.

Copy both sessions, tool lines included, into TRANSCRIPT.md. If the assistant does something you didn't expect, keep it in and say so in your memo.

5Write the memo

Fill in DECISIONS.md, about one page: your late-cancellation rule and why, your call on each wish-list tool, and what your AI assistant wrote, got wrong, or missed.

Submit (via Brightspace)
  • tools.py and tests/test_my_rules.py
  • The output of pytest, pasted as text (all tests passing, including yours)
  • TRANSCRIPT.md
  • DECISIONS.md

How this differs from HOS 1's Understand & Refine: there you extended code you already understood, by hand, with no AI. Here the business, the code, and the decisions are new, AI help is allowed, and half the grade (Analysis and Evaluation) is for the calls you make, not the typing.

Common snags

  • test_model_cannot_choose_the_patient fails. A schema lists patient_id as a parameter. Remove it from the schema. The function still takes it, because the app passes it in.
  • A time test fails by one slot. Somewhere you used datetime.now(). Use clinic_data.now().
  • An error test says "an error must not change any data". Check for the error before you change booked_by, not after.
  • agent.py fails with 502 or "model not found". The model is set to gemini-3.8-flash. If your assistant changed it, change it back. See the HOS 1 guide's Common snags.
Faculty notes: what strong answers look like, and grading

The late-cancellation decision

Three common rules, all defensible. Grade the reasoning, not the choice.

  • Refuse inside 24 hours and send the patient to the front desk. A person decides whether to charge or waive the fee. The cost is friction for the patient. (This is the answer key's rule.)
  • Cancel and record the fee. Convenient, and the slot reopens for someone else. The risk is that a chatbot charges a patient money, and disputes go to the front desk anyway.
  • Ask the patient to confirm the fee first. The strongest answers notice the trap: a confirm_fee: true parameter is filled in by the model, so it isn't real confirmation unless the app enforces it outside the model. Students who spot this are showing exactly the "should the model control this?" judgment HOS 1 teaches.

Typical answers pick a rule without saying who it protects, or test only the easy case. The boundary is in the data on purpose: S06 is 23.5 hours away and S05 is 25 hours away.

The wish list

  • view_patient_record: strong answers don't expose it, or expose only the logged-in patient's own non-clinical fields. They point out that the record's notes hold health information the model could repeat back, and that the assistant isn't supposed to give medical advice anyway.
  • send_sms: strong answers reject a free-form (phone, message) tool, which would let the model text anyone anything, in favor of something narrow like send_reminder(slot_id): a fixed template sent to the number on file for the patient's own appointment.
  • Typical answers say "expose both, they're useful," or "don't, privacy," without naming what the model could actually do with the tool.

Grading quickly (about 8–10 minutes per student)

Each criterion maps to one part of the submission, so read each part once, in this order, and pick a level:

  1. Design (40): the pasted pytest output (all passing?), then test_my_rules.py (does a test sit at the 24-hour edge, using S05 or S06?).
  2. Application (10): the transcript. Did each message trigger the right tool, and did the P1002 session apply the student's late-cancel rule?
  3. Evaluation (30): memo section 1.
  4. Analysis (20): memo section 2.

You don't need to run the code. Load the table above into Brightspace as a rubric with levels (Full = 100%, Partial = 50%, Missing = 0% of the criterion), so grading is one click per criterion. A reference submission is in the answer key, with steps to check it against the provided tests.

Worth checking in the first term

  • Do a faculty test run in a fresh Codespace (AC 1 is the only challenge that calls Gemini live). Does it fit in 60–90 minutes with an AI assistant?
  • Do the memos actually differ on the late-cancel rule, or does everyone copy the same AI suggestion?
  • Does grading actually take 8–10 minutes per student? Do two instructors give the same levels to the same submission?
  • Is the transcript worth its 10 points, or should it become a single screenshot?
