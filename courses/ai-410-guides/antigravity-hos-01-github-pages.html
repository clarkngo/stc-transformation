HOS 1 (Antigravity Pilot) — Antigravity, GitHub & GitHub Pages

Pilot — not graded Est. 75–90 min Includes a real bug and a real ADK wall
What this is: a single-HOS pilot, not a parallel course yet — Phase 1 (faculty pilot) of the Antigravity curriculum plan, drafted from the Sep 16 conversation with Spencer Liu. The regular AI 410 sequence (HOS 1–4) is unaffected and untouched — this lives alongside it until the pilot tells us whether it's worth building out further.

Goal

Get Antigravity, GitHub, and GitHub Pages working end to end — but the point isn't the plumbing, it's what the plumbing sets up. GitHub Pages serves a project site from a subpath (username.github.io/repo-name/), not the domain root, and Antigravity has no way to know that while it's writing code in Stage 1. That mismatch reliably produces a real, unprompted bug once the site goes live — which is exactly the "notice the agent got something wrong, then decide what to do about it" moment this whole pilot exists to test (see Spencer's framing). Stage 5 then pushes past what Antigravity can do generically at all, into the Google ADK escalation path the curriculum plan calls for.

What you'll need

  • An Antigravity account — free tier, no credit card. (Sign-up flow confirmed by Spencer Liu in the Sep 16 conversation as generous on tokens for exactly this kind of exercise.)
  • A GitHub account — if you don't already have one, see the GitHub section of the Account & Service Setup Guide. Same account as the rest of AI 410; nothing new to create there.
  • A browser. Nothing else for Stages 1–4 — no local Python, no starter-code folder. Unlike every other HOS in this course, you're starting from a truly blank repo on purpose. Stage 5 stays read/observe-only for the same reason — see that stage for why.

Graded the same way as the rest of AI 410 will eventually be, but this pilot itself isn't graded — it's a dry run. Each stage below still says what to produce, so faculty running the pilot have something concrete to compare against the Claude Code track.

1Create / Scaffold

Antigravity-driven. Start from nothing — an empty local folder, no starter code.

Open Antigravity, point it at a new empty folder, and give it a prompt like:

Scaffold a tiny static personal site in this folder — two pages,
sharing one stylesheet and one nav bar:
- index.html: my name, one sentence about what AI 410 is, and a nav
  link to about.html.
- about.html: two sentences about what I'm hoping to learn this term,
  and a nav link back to index.html.
- One shared stylesheet, linked from both pages, styling the nav bar
  and page body.
Plain HTML/CSS, no build step, no framework.

On purpose, don't tell it anything about GitHub Pages, folder layout, or how the site will be hosted — let Antigravity decide that on its own. Let it run, then look at the file paths it chose (open the generated HTML and check the <link> and <a href> tags) before moving on. Don't hand-edit anything yet.

2Ship It — GitHub & Pages

Prompt to public URL — and the step that exposes whatever Antigravity assumed in Stage 1.

  1. Create a new public repo on GitHub (Pages needs public, unless your account has a paid plan) and push what Antigravity built, unchanged.
  2. In the repo, go to Settings → Pages. Under Build and deployment, set Source to Deploy from a branch, pick main, and pick the folder your index.html actually lives in (/ (root) or /docs — has to match where Antigravity put it in Stage 1).
  3. Save, then wait — the first deploy usually takes one to two minutes. GitHub shows a green checkmark and a URL once it's live: https://<username>.github.io/<repo-name>/.
  4. Open that exact URL — not the local file, not a preview inside Antigravity. Notice the URL has your repo name in the path, after your username. That detail matters in Stage 3.
Submit (pilot log, not a grade)
  • The live GitHub Pages URL, plus how long Stages 1–2 took start to finish.

3Evaluate

The real test: does the live page actually work, not just the local one.

On the live URL — reload it fresh, don't trust a cached tab — check three things: does the page have any styling at all, or is it plain unstyled text? Does clicking the nav link to the other page actually load it? Open your browser's dev tools (F12 → Network or Console) and look for any red 404 errors.

If something's broken, don't fix it yet — first work out why. Look at the exact URL a failing request is trying to reach (dev tools will show it) and compare it to where that file actually lives in your repo. Antigravity built and tested this locally, where a path like /style.css means "the root of my hard drive's dev server." On GitHub Pages, your site doesn't live at the root — it lives at /<repo-name>/ — so that same absolute path now points somewhere that doesn't exist. Antigravity had no way to know that in Stage 1; it only shows up now, live.

Submit
  • What's broken (if anything) and the exact failing URL from dev tools, or — if nothing broke — a note on what Antigravity did differently that avoided this (e.g. it may have used relative paths like style.css on its own).

4Understand & Refine

By hand, no AI — fix the actual bug, not a cosmetic one.

No Antigravity for this stage. Open the file with the broken reference yourself.

If Stage 3 found a broken path: fix it by hand — change the absolute path (/style.css) to a relative one (style.css or ./style.css), so it resolves correctly no matter what subpath the site is served from. Commit, push, and reload the live URL to confirm it's actually fixed — not just that it looks right in a local preview.

If Stage 3 came back clean, don't skip this: deliberately introduce the bug yourself first (hand-edit one path to be absolute), confirm it breaks live, then fix it. Either way, you should end this stage having watched one specific path go from broken to working on the real deployed site.

Submit
  • The one line you changed, and a screenshot of the live (not local) page working correctly after the fix.

5Hit the Wall — Antigravity to ADK

Read/observe only. This is where "generic" stops being enough.

Back in Antigravity, ask for something it can't cleanly fulfill as a static site — for example:

Add a section to index.html that shows today's local weather,
fetched live from a weather API, every time the page loads.

Watch what it does. A static GitHub Pages site has no server of its own, so the honest options are limited: call a weather API directly from browser JavaScript (which means putting an API key in code anyone can view — a real security problem, not a hypothetical one), or leave the feature unfinished. Notice which one it picks, and whether it flags the tradeoff to you or just ships it quietly.

This is the wall the curriculum plan calls the ADK escalation path: a live API key that needs to stay server-side, and logic that needs to run somewhere other than the visitor's browser, is exactly the kind of customized workflow Antigravity hands off rather than solves generically. Solving it for real means standing up a small backend — which is what Google ADK is for. You're not building that backend in this pilot HOS; noticing *that this is the point where you'd need to* is the actual skill being tested here.

Submit
  • What Antigravity actually did with the weather prompt, and in one or two sentences: what would have to move server-side to do this properly, and why a static site can't be the place that happens.

Common snags

  • Pages says "not found" after a few minutes — almost always a Source/folder mismatch. If Antigravity put index.html in /docs but Pages is set to deploy from / (root) (or vice versa), it'll build successfully and still 404. Go back to Settings → Pages and match the folder exactly.
  • Repo is private — free GitHub accounts need the repo set to public for Pages to serve it. Check the repo's visibility before troubleshooting anything else.
  • Change pushed but the live site looks the same — Pages deploys are not instant; check the Actions tab (or the Pages settings page) for a running or just-finished deployment before assuming something's broken.
  • Stage 3 found nothing broken — that's a real, valid result, not a failed exercise. It means Antigravity happened to use relative paths on its own; say so in Stage 3's submission, then do the "introduce it yourself" fallback in Stage 4 so you still get the diagnose-and-fix rep.
  • Everything looks fine locally, only breaks live — that's the whole point, not a bug in the exercise. A local dev server and username.github.io/repo-name/ resolve absolute paths differently; always evaluate against the live URL, never the local one.

Faculty: this is Phase 1 of the pilot

Per the phased rollout, log this before treating it as done — this version is built specifically to produce a real error-recovery moment (Stages 3–4) and a real ADK-escalation moment (Stage 5), not just toolchain setup:

  • Did Antigravity actually produce the absolute-path bug on its own, or did you have to force it in Stage 4's fallback? Either outcome is useful data — it tells us how reliably this exercise teaches the intended lesson without hand-holding.
  • In Stage 5, did Antigravity flag the API-key security problem itself, or ship it silently? That's close to the exact "curiosity and awareness" signal Spencer described Google screening fresh grads for — worth noting whether Antigravity's own behavior helps or hides that.
  • Did the free-tier token allowance feel tight for a task this size, or was it a non-issue?
  • How long did all five stages actually take, end to end — this is the number that decides whether a full cohort trial (Phase 2) is realistic in one class session.
