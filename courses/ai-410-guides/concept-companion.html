Module 0 — Universal Tooling

Before HOS 1

These tools show up in every single HOS of this course, not just one. Get comfortable with them once, here, instead of relearning them under deadline pressure in HOS 1.

The setup pipeline you'll repeat, in some form, at the start of nearly every HOS.

Terminal / command line

A text-based way to run programs and commands, instead of clicking icons. This course uses it constantly — starting servers, installing packages, running scripts — because that's how real backend and AI-engineering work actually happens; almost nothing here has a GUI.

Python virtual environment (venv)

A private, self-contained copy of Python and its installed packages, scoped to one project folder. python3 -m venv venv creates it; source venv/bin/activate switches your terminal to use it.

Why it matters: different HOS units (and different projects entirely) can need different, sometimes conflicting, package versions. Without a venv, installing one project's dependencies can silently break another's.

Package managers — pip and npm

pip installs Python packages from a requirements.txt list; npm does the same job for JavaScript packages from a package.json file (you'll meet npm specifically in the mobile module). Same underlying idea in two different languages: a plain-text list of exactly what the project needs, and a tool that reads it and installs everything.

Environment variables & .env files

A .env file holds project settings and secrets (like GEMINI_API_KEY=...) as plain NAME=value lines, kept out of your actual code. A small library (python-dotenv) reads that file at startup and makes those values available to your program.

Why it matters: this keeps secrets out of source code you might share or commit, and this project's .gitignore already excludes .env from Git — so it's hard to leak a key by accident.

API keys

A long string that identifies you (or your app) to a service like Gemini, so it can apply your usage limits and know who's making a request. Treat it exactly like a password — never commit it, paste it into a chat, or put it in a screenshot.

GitHub Codespaces & devcontainers

A .devcontainer/devcontainer.json file describes a ready-made development environment — the right language versions, tools, and settings — that GitHub can spin up for you in the browser with one click (Code → Codespaces → Create codespace on main), dependencies and .env setup included.

Why it matters: the most common bug in this course is a local machine with an old package already installed globally that silently shadows the project's own version. A fresh Codespace sidesteps that entirely — every HOS's starter code is built to support it.
Changes to devcontainer.json only apply on rebuild. If a Codespace already exists and its config changes later (e.g. you carry the same Codespace forward from an earlier HOS into one that needs Node.js for the first time), it won't have the new tools — a command like npm will say "not found" even though the config says it should be there. Fix: Command Palette (Cmd/Ctrl+Shift+P) → "Codespaces: Rebuild Container." Your files are untouched; only the container's installed tools get reapplied.

A new terminal tab starts back at the repo root

Every HOS from HOS 3 onward asks you to run two or three processes at once (the API, the worker, the mobile dev server) in separate terminal tabs. In Codespaces, opening a new tab always starts you back at the repo's top-level folder — it does not remember that an earlier tab was sitting inside backend/.

Why it matters: if you copy just the run command (e.g. ./venv/bin/python worker.py) into a fresh tab without cd backend first, it fails — that script only exists inside backend/. Get in the habit of typing cd backend (or cd mobile) as the very first thing in every new terminal tab, every time, even if you already did it in a different tab a minute ago.

Working with an AI coding assistant (CEAU-based HOS only)

If your version of the course uses the merged-HOS format, the first stage of each HOS (Create/Scaffold) is deliberately AI-driven — you prompt an assistant to build the app, then spend the rest of the HOS proving, in writing and by hand, that you actually understand what it built.

Why it matters: the grading isn't on whether the AI-produced code runs — it's on whether you can evaluate it, explain one piece of it mechanistically, and extend it correctly without AI help. Treat Stage 1 as a starting point, not the deliverable.
Quick self-check before you continue
  • Could you explain to someone else why a venv exists, in one sentence?
  • Do you know where your Gemini API key is stored, and why it's not inside a .py file?
  • If your version of the course uses HOS format: do you know which CEAU stage is graded on code correctness, and which ones aren't?

Module A — Foundations & the Agentic Loop

HOS 1 Outcome 1

Why before you start: almost everything you build for the rest of the term is an extension of one request/response call and one decision loop. Get these two shapes solid now and every later HOS is "the same thing, plus one more piece."

The request/response shape underneath every HOS of this course.

Frontend vs. backend, and why the split exists

The frontend is what a user sees and clicks (a Streamlit page, later a mobile app). The backend is a server that holds your API key and does the real work — the frontend only ever talks to your own backend, never directly to Gemini.

Why it matters: if the frontend held the API key, anyone who opened the app in a browser could extract it. Keeping the key server-side is the whole reason the "full-stack" split exists.

An LLM API call

A request to a model provider (here, Gemini) containing a model name and some input text; the response is an object containing the model's answer (output_text) plus metadata like token usage. It's a normal network request under the hood — nothing magic about it.

Tokens & context window

A token is roughly a chunk of a word — models read and write text as sequences of tokens, not characters. Every request has a context window: a hard ceiling on how much text (your input + the model's reply, combined) one request can contain.

Tool calling / function calling

A tool is a piece of your own code the model can ask to run — a calculator, a lookup, anything. The model can't execute code itself: it replies with a function_call step naming which tool it wants and with what arguments; your backend actually runs it and sends the result back.

Two separate things, one shared name

A tool's schema (what the model sees — a JSON description, no real code) and its function (what your backend runs) are linked only by a shared string, like "calculate". Get the name mismatched between the two and the lookup silently fails.

The description field decides everything

The tool schema's description is the only thing the model reads to decide when to use a tool. A vague description gets called at the wrong times or ignored entirely; a specific one with an example gets used correctly.

The agentic loop: only your backend ever runs real code — the model only ever names which tool it wants.

Quick self-check before you continue
  • Can you explain why the frontend never holds the API key?
  • Do you know the difference between a tool's schema and its function — and what links them?
  • If you saw a model calling a tool when it clearly shouldn't have, what's the first thing you'd check?

Module B — Embeddings, Chunking & RAG

HOS 2 Outcomes 1–2

Why before you start: Retrieval-Augmented Generation (RAG) is the single most common pattern for making a model answer accurately about specific data instead of guessing. Every concept here builds toward that one pipeline.

Embeddings

A list of a few thousand numbers (a "vector") representing the meaning of a piece of text. Text with similar meaning gets vectors that point in similar directions; unrelated text points in very different directions — pure math, no human labeling needed.

Why not keyword search? A keyword search for "return policy" misses a document about "sending an item back within 30 days" that never uses the word "return." Embeddings capture meaning, not exact wording.

Chunking

Splitting a long document into smaller pieces before embedding them. Embedding an entire multi-page document into one vector blurs together everything it discusses; focused, single-topic chunks produce vectors that represent one clear idea.

The tradeoff: chunks too large and everything looks similarly related; too small and they lose the surrounding context needed to make sense on their own. Overlap between consecutive chunks avoids cutting a sentence in half at a boundary.

Cosine similarity

The standard way to compare two embeddings — it measures the angle between them, ignoring length, returning a number from -1 (opposite meaning) to 1 (identical meaning), with 0 meaning unrelated.

Vector database

A database built to search by "closest vector" instead of exact match. A collection is its equivalent of a table — every chunk you add needs an embedding of the same length as the first one ever added to that collection.

Document vs. query embeddings

The same embedding model is told which side of the search a piece of text is on (RETRIEVAL_DOCUMENT vs. RETRIEVAL_QUERY), which changes how it optimizes the resulting vector slightly. Embed both sides with mismatched settings and similarity scores become meaningless.

RAG — Retrieval-Augmented Generation

Retrieve the most relevant chunks for a user's question first, then hand them to the model as background context (typically via a system_instruction) before it answers — grounding the reply in your actual documents instead of the model's general knowledge alone.

Documents are embedded once, up front; the query is embedded the same way at search time, then compared to every chunk.
Vocabulary check
Grounding
an answer that's traceable to specific retrieved text, not the model's general knowledge.
Hallucination

  • Can you explain, in one sentence, why chunking happens before embedding rather than after?
  • Do you know what would go wrong if you embedded a query with RETRIEVAL_DOCUMENT instead of RETRIEVAL_QUERY?
  • What's the simplest experiment that proves retrieval is actually changing the model's answer?

Module C — Guardrails & Asynchronous Processing

HOS 3 Outcome 3

Why before you start: once your app is doing real retrieval and tool calls, two new risks show up — the model can produce malformed output, and slow work can freeze the app for everyone using it. This module is about naming those risks on purpose, then handling both.

Architecture / failure-point thinking

Before fixing anything, draw your app's actual request path — box per step, arrow per call — and ask two questions of every arrow: what happens if this step is slow? and what happens if it returns something malformed? "The API could go down" isn't specific enough; "if the embeddings API is down, retrieve() throws and the whole request fails instead of just skipping context" is.

Probabilistic vs. deterministic output

A model's output isn't guaranteed to be well-formed — the same tool call can come back with the right shape most of the time and a missing or malformed field occasionally. Treat model output the way you'd treat unreliable user input: never trust it blindly.

Guardrails: schema validation + retry + safe fallback

Define the exact shape you expect (a schema), validate the model's output against it, retry a limited number of times on failure, and return a clear, safe error if every attempt fails — never a raw crash.

Why it matters: a retry that resends the identical request rarely fixes a structural problem; a fixed retry limit prevents an unrecoverable case from looping forever.

Synchronous vs. asynchronous processing

Synchronous: the requester waits until the work finishes. Asynchronous: the work is handed off to run separately, and the requester gets an immediate acknowledgment instead of waiting.

Message queue & worker

A queue is a to-do list one process (your API) adds tasks to; a worker is a separate, independently-running program that pulls tasks off the queue and executes them, one at a time.

Why it matters: slow work (like ingesting a large document) no longer blocks fast work (like answering a chat message) — they run as genuinely separate processes, connected only through the queue.

Job status polling

Enqueuing work returns a job ID immediately; a separate status endpoint looks that job up by ID and reports where it is: queued → started → finished (or failed), plus the result once it's done.

A guardrail wraps every tool call: validate first, and only run the tool if the shape is right.
The API and the worker are two separate running programs, connected only through the queue.
Quick self-check before you continue
  • Can you name one specific failure point in your own app — not a generic "the API could fail"?
  • Do you know why a guardrail returns a safe error dict instead of raising an exception?
  • Can you explain why the worker needs its own copy of your environment variables?

Module D — Mobile, Push & Observability

HOS 4 Outcomes 4–5

Why before you start: the last stretch puts the same backend you've been building in front of a real device, and makes what's happening inside it visible instead of a black box you have to guess about.

Mobile dev-server model (Expo / React Native)

A local dev server streams your app's actual code to a real phone via a QR code, using an app like Expo Go — no app-store submission or build step needed for development. It's the same idea as a web dev server, just for a native-feeling mobile app.

Same backend, different client

The mobile app is just another caller of the exact same API you've been building since HOS 1 — it doesn't talk to Gemini directly either, and it doesn't require rebuilding anything on the backend.

Push notifications & push tokens

A push token uniquely identifies one specific phone running one specific app install. Your backend never talks to the phone directly — it hands the token and a message to a third-party push service (Expo's, here), which actually delivers the notification, even when the app is closed or backgrounded.

Device registration

Before your backend can push to a phone, that phone has to send its token to the backend once, so the backend can store it (keyed by a device ID) and look it up later when it needs to notify that device.

Observability: tracing & spans

Recording what actually happened on a real request — timing, inputs, outputs, cost — automatically, instead of guessing or scattering print() statements. A trace is the full record of one request; a span is one meaningful step nested inside it (e.g. retrieval, or one model call).

Why trace individual steps, not the whole request as one block? Nesting meaningful steps (retrieval vs. generation vs. tool calls) as separate spans is what lets you answer "which part was actually slow?" — wrapping everything as one giant span just tells you the total was slow.

Evaluation

A way to score output quality with a number instead of a vibe — even a rough heuristic (like how much of the retrieved context's words show up in the final answer) is enough to spot when a model is clearly ignoring what it was given.

Deployment

The gap between "runs on my laptop" and "a real, reachable product." Code nobody else can access isn't a product yet — this is what turns a term's worth of builds into something you can hand someone a link to.

Push flows through a third-party service — your backend never talks to the phone directly.
Nested spans are what let you answer "which specific step was slow?" instead of only "the whole thing was slow."
Quick self-check before you continue
  • Can you explain why push notifications go through a third-party service instead of your backend calling the phone directly?
  • Do you know the difference between a trace and a span?
  • Can you name one thing your app does that would be worth measuring with a number, not just "it feels fine"?
