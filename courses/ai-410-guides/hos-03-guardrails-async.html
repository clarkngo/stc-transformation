HOS 3 — Guardrails & Asynchronous Processing

Est. 2.5–3 hrs Outcome 3 Merges old Weeks 6–7 20% of final grade

Goal

Make HOS 2's app reliable under two different kinds of unpredictability: a model that sometimes calls a tool with bad arguments, and document ingestion that's slow enough to block the whole app if it runs inline.

What you'll need

  • Starter code: this HOS's starter-code folder — your HOS 2 app, already working.
  • A free Upstash Redis instance (no credit card) — get the connection URL from its dashboard before you start.
  • An AI coding assistant available in your environment

This HOS is graded across four stages instead of on code correctness alone. Each stage below says exactly what to submit.

1Create / Scaffold

Not graded on its own — this is the starting point, not the deliverable.

Prompt your AI assistant to add both pieces:

Add reliability to this app:
- backend/guardrails.py: a call_with_guardrail(fn, schema, ...)
  helper that calls fn(), validates the result against a Pydantic
  schema, and retries (up to 2 times) if validation fails — returning
  an {"error": ...} dict instead of raising if all retries fail.
  Define a schema for the "calculate" tool's arguments and wrap that
  tool's call in agent.py with the guardrail.
- backend/queue_setup.py + worker.py: a Redis-backed queue (using rq
  and REDIS_URL from .env) and a worker process that runs jobs from it.
- backend/jobs.py: move the document-ingestion logic (chunk, embed,
  insert into Chroma) into a job function the worker can run.
- backend/main.py: change POST /documents to enqueue the job and
  return a job_id immediately, and add GET /jobs/{id} to report status.

Remember: the worker (python worker.py) runs in its own terminal, separate from uvicorn.

2Evaluate

The critical gate — is the AI-produced result actually correct?

Test it on purpose. At minimum, try:

  • A message likely to produce a malformed tool call (e.g. "calculate the square root of a banana") — does the guardrail catch it and retry, or does the request crash?
  • Upload a document via POST /documents, confirm you get a job_id back instantly, then poll GET /jobs/{id} until it's "finished" — while sending normal chat messages the whole time to prove the app stayed responsive: 
    curl -X POST http://127.0.0.1:8000/documents \
  -H "Content-Type: application/json" \
  -d '{"doc_path": "sample_docs/return-policy.md"}'
# → should return {"job_id": "..."} immediately, not after ingestion finishes

curl http://127.0.0.1:8000/jobs/YOUR-JOB-ID-HERE
# → run this a few times; you should see "queued", then "started", then "finished"
    While that job is still processing, send a message through the chat UI at the same time — if it replies normally instead of hanging, that's your proof the two are running independently, not that ingestion is just fast.
  • Stop the worker process and upload a document — does /jobs/{id} correctly report "queued" forever, rather than erroring or hanging?
Submit
  • A short written note: what you tested, what you found, and anything the AI got wrong, missed, or handled surprisingly well.

3Analyze

Why does this work, mechanically?

Pick one specific piece — either why call_with_guardrail feeds the validation error back into the retry instead of just trying again blindly, or why the worker has to run as a separate OS process rather than a function the API calls directly. Explain the specific failure each design choice prevents.

Submit
  • A short written walkthrough of the one piece you chose, in your own words.

4Understand & Refine

The mastery check — can you extend it correctly, without AI doing this part too?

By hand this time — no AI assistance for this stage.

Extend the guardrail pattern to your second tool (from HOS 1's Understand & Refine) — write a Pydantic schema for its arguments, including at least one validation rule beyond "the field exists" (e.g. rejecting an empty string), and wire it into the tool dispatch in agent.py the same way the first tool is guarded.

Submit
  • A screenshot showing the new guardrail catching a bad call to your second tool.
  • The schema and dispatch code you wrote by hand.

Common snags

  • Jobs stuck on "queued" forever — the single most common issue. It means the worker process isn't running. Start it in its own terminal: python worker.py.
  • Testing locally on macOS, a job goes straight to "failed" — if the worker log mentions NSMutableString or fork(), that's a known macOS + RQ interaction, not a bug. Run the worker with OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES python worker.py, or just use Codespaces, where this doesn't happen.
  • The guardrail "retries" but gets the same wrong answer every time — check that correction_hint (if you're using one) actually feeds the validation error back into the next attempt. A retry with no new information has no better chance of succeeding than the first try.
