Week 1 — Foundations of Full-Stack AI Systems

Est. 3–4 hrs Outcome 1 Starts the app you'll build all term

Goal

Get the starter chat app running end to end, then replace its hardcoded reply with a real call to Gemini. By the end you'll have one working request/response loop — the base every later week extends.

What you'll need

  • Starter code: this week's starter-code folder — copy it into your own project and follow its README
  • Python 3.11+ and a terminal
  • It already contains a /backend FastAPI app with a stubbed /chat endpoint, and a /frontend folder with a single working chat page wired to call it
  • A free Gemini API key (no credit card required) from aistudio.google.com/apikey
💡 Recommended: GitHub Codespaces. This week's starter code includes a .devcontainer/devcontainer.json — push the folder to a repo, then Code → Codespaces → Create codespace on main, and dependencies + your .env file are set up automatically. It sidesteps the most common bug in this course: a local machine with an old package already installed globally that silently shadows this project's own version. See this week's starter-code README for exact commands either way.
The request/response path you're building this week.

Steps

  1. Get your bearings

    Open the starter-code folder in your code editor (VS Code, or whatever you're using) and open a terminal in that same folder. You should see two subfolders:
    1. backend/ — a small Python web server (using a framework called FastAPI) that will do the actual talking to Gemini.
    2. frontend/ — a plain HTML page with some JavaScript that gives you a chat box in the browser, and sends whatever you type to the backend.
    Why two folders? This is the "full-stack" in "full-stack AI systems" — a frontend (what the user sees and clicks) talking over the network to a backend (the server that holds your API key and does the real work). The frontend never talks to Gemini directly; it only ever talks to your own backend. You'll keep this same two-part shape for the rest of the course.

  2. Create a Python virtual environment

    In your terminal, move into the backend folder and create a "venv": 
    cd backend
python3 -m venv venv
    What this does: python3 -m venv venv creates a new folder called venv containing a private, self-contained copy of Python just for this project. Any packages you install next go inside that folder, not onto your whole computer. This matters because different projects (and different weeks of this course) can need different, sometimes conflicting, package versions — a venv keeps them from stepping on each other.

  3. Activate the virtual environment

    source venv/bin/activate
    What this does: tells your current terminal window to use the Python and packages inside venv/ instead of whatever Python is installed system-wide. You'll know it worked if your terminal prompt now starts with (venv). You have to do this again every time you open a new terminal window or tab for this project — it doesn't stay on permanently.

  4. Install the project's dependencies

    pip install -r requirements.txt
    What this does: requirements.txt is a plain text list of the exact packages (and versions) this project needs — fastapi (the web framework), uvicorn (the program that actually runs a FastAPI server), and google-genai (Google's Python library for calling Gemini). pip is Python's package installer; this command reads the list and installs everything into your activated venv.

  5. Get a free Gemini API key

    An API key is like a password that identifies you (or your app) to Google's Gemini service, so it knows who's making requests and can apply your free usage limits.
    1. Go to aistudio.google.com/apikey and sign in with any Google account.
    2. Click Create API key.
    3. Copy the long string it gives you (it starts with something like AIza...). Keep this tab open — you'll paste it in the next step.
    No credit card is required for this. Treat this key like a password: anyone who has it can make Gemini requests billed to your account. Never paste it into a file you commit to Git, or share it in a chat/screenshot.

  6. Store your API key in a .env file

    The starter code includes a file called .env.example — a template showing what environment variables the project expects, with fake placeholder values. Copy it to a real .env file and fill in your real key: 
    cp .env.example .env
    Now open the new .env file in your editor and replace the placeholder so it looks like this (using your own key, not this example one): 
    GEMINI_API_KEY=AIzaSyD-your-real-key-goes-right-here
    Why a .env file instead of pasting the key into the code? Two reasons. First, it keeps secrets out of your source code, so you can safely share or commit your code without leaking the key. Second, this project already has a .gitignore rule that excludes .env from Git, so it's very hard to accidentally commit it by mistake. A small Python library called python-dotenv (already installed via requirements.txt) reads this file at startup and makes GEMINI_API_KEY available to your code as if it were a normal environment variable.

  7. Read the stub before touching it

    Open backend/main.py in your editor. Find the function that looks like this: 
    @app.post("/chat", response_model=ChatResponse)
def chat(body: ChatRequest) -> ChatResponse:
    # TODO(week1): replace this stub with a real call to Gemini.
    ...
    return ChatResponse(reply=f"(stub reply) You said: {body.message!r}")
    What this already does: @app.post("/chat", ...) tells FastAPI "when a POST request arrives at the web address /chat, run this function." body: ChatRequest means FastAPI automatically reads the incoming JSON (like {"message": "hi"}) and hands it to you as a typed Python object with a .message field — you don't have to parse JSON by hand. Whatever this function returns gets automatically converted back into JSON and sent to whoever asked (in this case, the frontend chat page). Right now it just echoes your message back with "(stub reply)" in front — that's the placeholder you're about to replace.

  8. Replace the stub with a real Gemini call

    Delete the body of the chat function (everything between the def chat(...): line and the final return) and replace it with this: 
    from google import genai

client = genai.Client()  # reads GEMINI_API_KEY from the environment automatically


@app.post("/chat", response_model=ChatResponse)
def chat(body: ChatRequest) -> ChatResponse:
    interaction = client.interactions.create(
        model="gemini-flash-latest",
        input=body.message,
    )
    return ChatResponse(reply=interaction.output_text)
    Line by line:
    • from google import genai — imports Google's Gemini library (installed in step 4).
    • client = genai.Client() — creates one reusable connection object. Calling genai.Client() with no arguments makes it look for GEMINI_API_KEY in your environment — the value you put in .env in step 6. Put this line outside the function (at the top level of the file) so it only runs once when the server starts, not on every single chat message.
    • client.interactions.create(...) — this is the actual network call to Google's servers. model="gemini-flash-latest" picks which Gemini model answers; input=body.message is the text the user typed.
    • interaction.output_text — the model's plain-text answer, pulled out of the larger response object (more on that object's shape in the last step below).

  9. Run the server

    ./venv/bin/uvicorn main:app --reload
    Why ./venv/bin/uvicorn and not just uvicorn? If your computer already has a uvicorn or google-genai installed somewhere else (a different project, a different Python version), typing the bare word uvicorn can accidentally run that one instead of the one you just installed in your venv — even if you activated it. Calling the file directly by its path (./venv/bin/uvicorn) removes all doubt about which one runs. --reload makes the server automatically restart every time you save a change to main.py, which you'll do a lot this term.
    You should see output ending in a line like Uvicorn running on http://127.0.0.1:8000. Leave this terminal window open and running — closing it stops your server.

  10. Open the frontend and test it

    In Finder/Explorer, double-click frontend/index.html (or run open frontend/index.html on macOS). It opens in your browser as a simple chat page. Type a question and hit Send.
    Behind the scenes: the page's JavaScript sends your message to http://127.0.0.1:8000/chat (your running backend), which calls Gemini and sends the reply back, which the page then displays. If nothing happens, check your terminal — errors from the backend show up there, not in the browser.

  11. Understand what just happened

    Temporarily add print(interaction) right before the return line in main.py, save, and send another message. Look at your terminal output. You'll see the full interaction object — it's built from a list called steps (right now just one text step), plus token-usage numbers. That same steps list is what you'll inspect starting next week to detect when the model wants to use a tool. The token-usage numbers matter too: every request has a limited "context window" — a ceiling on how much text (your message + the model's reply, measured in tokens) one request can contain. You can remove the print() line once you've looked at it.

You'll know it worked when…

  • You type a question in the chat UI and get a real, on-topic Gemini-generated answer back.
  • You can point to the exact line of code that makes the LLM call and explain what's in the request and what's in the response.

Common snags

  • "No API key was provided" or "invalid API key" — check that your .env file (not .env.example) contains the real key under the exact name GEMINI_API_KEY, with no quotes or extra spaces, and that you stopped and restarted uvicorn after editing .env — it's only read once, at startup.
  • CORS errors in the browser console — the starter repo's CORS middleware already handles this; don't remove or "simplify" it.
  • Reply looks empty or broken — confirm you're reading interaction.output_text and not the whole interaction object.
