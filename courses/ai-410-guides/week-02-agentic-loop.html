Week 2 — Structured Outputs & the Agentic Loop

Est. 3–4 hrs Outcome 1 Builds on Week 1

Goal

Give your Week 1 chat app a real tool it can decide to use — the core "agentic loop" pattern (model decides → tool runs → result goes back to the model) that every later week reuses.

What you'll need

  • Starter code: this week's starter-code folder — an agent-loop skeleton with one dummy tool already stubbed in and wired
  • Your working Week 1 app (or just use this week's starter code, which already includes it)
The agentic loop you're tracing and extending this week.

Steps

  1. Set up this week's project

    Copy this week's starter-code folder to a new location (it already includes a working Week 1 backend, so you don't need to redo last week's setup). In a terminal, inside the new backend/ folder: 
    python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
    Open .env and paste in the same GEMINI_API_KEY you got last week (it works across all weeks — you don't need a new one).

  2. Understand the new idea: an "agentic loop"

    So far, the model only ever produces text. A tool (also called a "function") is a piece of your own code that the model can ask to run — for example, a calculator, a database lookup, or a weather API call. The model can't run Python itself; instead, it tells your backend which tool it wants and with what arguments, your backend actually runs it, and sends the result back so the model can use it in its final answer. That back-and-forth is the "agentic loop":
    1. You send the user's message and a list of tools the model is allowed to use.
    2. The model decides: does it need a tool, or can it just answer directly?
    3. If it needs a tool, it doesn't run any code — it replies with a function_call step naming the tool and the arguments it wants to use.
    4. Your backend runs the matching Python function itself, and sends the result back to the model as a function_result.
    5. The model reads that result and produces its final, plain-text answer.

  3. Trace the dummy tool through the code that's already there

    Open backend/tools.py. You'll see a fake tool called ping already fully wired up: 
    def _ping(**kwargs):
    """Dummy tool — proves the loop works before you add a real one."""
    return "pong"


TOOLS = [
    {
        "type": "function",
        "name": "ping",
        "description": "A no-op test tool that always returns 'pong'. Useful only for verifying the tool-calling loop is wired correctly.",
        "parameters": {
            "type": "object",
            "properties": {},
        },
    },
]

TOOL_FUNCTIONS = {
    "ping": _ping,
}
    Two separate things, one name: TOOLS is what the model sees — just a description in JSON, no real code. TOOL_FUNCTIONS is what your backend uses to look up the real Python function to run once the model asks for "ping" by name. They're linked only by that shared string "ping" — get the name wrong in one place and the lookup silently fails.
    Now open backend/agent.py and find the loop itself: 
    def run_agent(user_message: str) -> str:
    interaction = client.interactions.create(
        model=MODEL,
        input=user_message,
        tools=TOOLS,
    )

    for _ in range(MAX_TURNS):
        function_calls = [step for step in interaction.steps if step.type == "function_call"]

        if not function_calls:
            # Plain text answer — the model didn't need a tool.
            return interaction.output_text

        results = []
        for call in function_calls:
            fn = TOOL_FUNCTIONS.get(call.name)
            result = fn(**call.arguments) if fn else f"Error: no tool registered named '{call.name}'"
            results.append({
                "type": "function_result",
                "name": call.name,
                "call_id": call.id,
                "result": [{"type": "text", "text": str(result)}],
            })

        interaction = client.interactions.create(
            model=MODEL,
            input=results,
            tools=TOOLS,
            previous_interaction_id=interaction.id,
        )

    return "I couldn't finish that within the allowed number of steps."
    Walking through it:
    • tools=TOOLS on the first call — this is how the model even learns these tools exist.
    • [step for step in interaction.steps if step.type == "function_call"] — after every call, we check: did the model ask for a tool? interaction.steps is a list because a reply can contain more than one thing (a thought, a tool call, text); we only care about the function_call ones here.
    • if not function_calls: return interaction.output_text — no tool requested means the model already has its final answer, so we're done.
    • fn = TOOL_FUNCTIONS.get(call.name) then fn(**call.arguments) — look up the real Python function by the name the model gave us, and call it with whatever arguments the model supplied. **call.arguments unpacks a dict like {"expression": "5+3"} into a real keyword argument, expression="5+3".
    • previous_interaction_id=interaction.id — this is what tells Gemini "continue that same conversation," so it remembers what it originally asked and can use your function_result to write a final answer.
    • for _ in range(MAX_TURNS): — a safety limit. Without it, a model that keeps calling tools forever (or your code has a bug that never satisfies it) would loop forever too.
    Run the server (./venv/bin/uvicorn main:app --reload) and open frontend/index.html. Ask something like "call your ping tool" and watch it work before you've written a single line yourself.

  4. Define your own tool's schema

    You'll add a calculate tool. In backend/tools.py, add this to the TOOLS list, right after the ping entry (don't remove ping — keep both): 
    {
    "type": "function",
    "name": "calculate",
    "description": "Evaluate a basic arithmetic expression, e.g. '342 * 87'.",
    "parameters": {
        "type": "object",
        "properties": {
            "expression": {"type": "string"},
        },
        "required": ["expression"],
    },
},
    The description field is more important than it looks — it's the only thing the model reads to decide when to use this tool. Be specific. A vague description ("does math") gets called at the wrong times or ignored; a clear one with an example gets used correctly.

  5. Write the function that actually runs

    Add this function above your TOOLS list (near the existing _ping function): 
    import ast
import operator

_OPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.USub: operator.neg,
}


def _safe_eval(node):
    if isinstance(node, ast.Constant):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _OPS:
        return _OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _OPS:
        return _OPS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("unsupported expression")


def _calculate(expression: str, **kwargs):
    try:
        tree = ast.parse(expression, mode="eval")
        return _safe_eval(tree.body)
    except Exception as e:
        return f"Could not evaluate '{expression}': {e}"
    Why not just eval(expression)? Python's built-in eval() will run any Python code inside that string — including things like deleting files — and the model is the one generating that string. Since we can't fully trust what a model produces, _safe_eval instead reads the expression as a syntax tree (ast.parse) and only ever performs the specific math operations listed in _OPS, rejecting anything else. This is the same "don't trust model output blindly" instinct you'll build on for real in Week 6 (guardrails).
    The function's argument name — expression — must exactly match the property name you wrote in the tool's parameters schema in the previous step. That's how fn(**call.arguments) in agent.py knows what to pass in.

  6. Register the function and the tool together

    Add "calculate": _calculate, to the TOOL_FUNCTIONS dict, next to "ping": _ping,. Your tools.py should now define two tools and two matching functions. Nothing in agent.py needs to change — the loop you traced in step 3 already handles any tool you add here, as long as the names match between TOOLS and TOOL_FUNCTIONS.

  7. Test the "decides" part, not just the "uses" part

    Restart the server if it isn't still running with --reload, then in the chat UI try two very different questions:
    1. "What's 342 times 87?" — this should trigger the calculate tool. Add a temporary print(function_calls) right after that line in agent.py to see the tool call Gemini generated, with its name and arguments.
    2. "What's the capital of France?" — this should not call any tool; the model already knows the answer and should skip straight to text.
    If the model calls the tool when it shouldn't, or refuses to when it should, that's almost always a wording problem in the description field — tighten it before changing any code.

You'll know it worked when…

  • The agent calls your tool for questions that need it, and skips it for questions that don't.
  • You can show the raw function_call step in the interaction as proof the model — not your code — made the decision.

Common snags

  • Mismatched call_id — the follow-up function_result must reference the exact ID from the function_call step, or Gemini will error.
  • Infinite loop — always add a max-turns guard; don't assume the model will stop calling tools on its own.
  • Vague tool description — if the model calls the tool when it shouldn't (or doesn't when it should), tighten the description first before changing anything else.
