Week 3 — Embeddings & Chunking

Est. 3–4 hrs Outcome 1 Sandbox — not wired to the live app yet

Goal

Build intuition for embeddings and chunking in isolation, in a sandbox script, before connecting anything to your live app next week. Confirm — with a real similarity score, not just a hunch — that your chunking choices actually group related content together.

What you'll need

  • Starter code: this week's starter-code folder — includes the sandbox script and 5 sample documents
  • A folder of 5–10 short sample documents (text or markdown) — already included in the starter code
  • The same free Gemini API key from Week 1 — Gemini serves embeddings from the same key as chat, via a separate model (gemini-embedding-001)
💡 Recommended: GitHub Codespaces. This week's starter code includes a .devcontainer/devcontainer.json — push the folder to a repo, then Code → Codespaces → Create codespace on main, and dependencies + your .env file are set up automatically. It sidesteps the most common bug in this course: a local machine with an old package already installed globally that silently shadows this project's own version. See this week's starter-code README for exact commands either way.
Documents get embedded once (up front); the query gets embedded the same way at search time, then compared to every chunk.

Steps

  1. Set up this week's project

    This week's starter code is a sandbox/ folder, not a backend/ — it's a standalone script, not part of the running chat app. 
    cd sandbox
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
    Paste your Gemini API key into .env (same one from Week 1). Then open ingest_sandbox.py and skim the 5 sample documents in sample_docs/ — knowing roughly what's in them will help you judge whether your results make sense later.

  2. Understand embeddings, conceptually, before writing code

    An embedding is a list of a few thousand numbers (a "vector") that represents the meaning of a piece of text. Two pieces of text with similar meaning get vectors that point in similar directions; unrelated text gets vectors pointing in very different directions. This is what lets a computer measure "how related are these two paragraphs?" without any human labeling — it's pure math on the numbers.
    Why not just search for matching words? A keyword search for "return policy" would miss a document that talks about "sending an item back within 30 days" without ever using the word "return." Embeddings capture meaning, not exact wording, which is exactly what you want for a question-answering system where users won't phrase things the way your documents do.

  3. Understand chunking, conceptually

    Chunking means splitting a long document into smaller pieces before embedding them. You do this because embedding an entire multi-page document into one vector would blur together everything it talks about — a document covering both shipping and returns would produce a single vector that's a vague mix of both topics, matching neither well. Splitting into focused, single-topic chunks (a paragraph or two each) gives you vectors that represent one clear idea, which is what makes retrieval actually work in Week 4.

  4. Read the chunking function that's already there

    Open ingest_sandbox.py and find chunk_text() — a basic version is already written for you: 
    def chunk_text(text: str, chunk_size: int = 400, overlap: int = 50) -> list[str]:
    words = text.split()
    chunks = []
    start = 0
    while start < len(words):
        end = start + chunk_size
        chunks.append(" ".join(words[start:end]))
        start = end - overlap  # step back by `overlap` words
    return chunks
    Line by line:
    • text.split() — breaks the document into a plain list of words (splitting on whitespace).
    • while start < len(words): — keep slicing out chunks until we've covered the whole document.
    • chunks.append(" ".join(words[start:end])) — take words start through end, glue them back into a string, and save that as one chunk.
    • start = end - overlap — this is the key trick. Instead of jumping straight to where the last chunk ended, we step back by overlap words (50, by default) so consecutive chunks share a little text. Without this, a sentence that happens to fall exactly on a chunk boundary would get cut in half, and neither half alone would make sense.
    This word-count approach is intentionally simple — it doesn't know or care about sentence or paragraph boundaries, so it can still occasionally cut mid-sentence. A stretch goal, if you want one: try splitting on paragraphs first (Python's text.split("\n\n")), and only fall back to this word-count approach for any single paragraph that's still too long. You don't need to do this to finish the exercise — the version above is good enough to move on.

  5. Implement embed_chunks()

    This one is left for you to write. Find the function (it currently just raises NotImplementedError) and replace its body with: 
    def embed_chunks(chunks: list[str]) -> list[list[float]]:
    result = client.models.embed_content(
        model=EMBED_MODEL,
        contents=chunks,
        config=types.EmbedContentConfig(
            task_type="RETRIEVAL_DOCUMENT",
            output_dimensionality=EMBED_DIM,
        ),
    )
    return [e.values for e in result.embeddings]
    Line by line:
    • client.models.embed_content(...) — the actual network call to Google that turns text into vectors. Note this uses client.models, not client.interactions like Weeks 1–2 — embeddings are a different kind of request than chat.
    • contents=chunks — you can pass a whole list of strings at once; you get back one vector per string, in the same order. Much faster than one request per chunk.
    • task_type="RETRIEVAL_DOCUMENT" — tells the model "these are documents that will be searched later," which makes it optimize the vectors slightly differently than it would for a search query. You'll use "RETRIEVAL_QUERY" instead when embedding the user's question, in the next step.
    • output_dimensionality=EMBED_DIM — this model can produce very long vectors (3072 numbers) by default; asking for 1024 keeps them smaller and faster to compare, which is plenty precise for this course.
    • [e.values for e in result.embeddings] — unwraps the response into a plain list of number-lists, matching the order of the chunks you passed in.

  6. Understand cosine similarity

    Look at the already-written cosine_sim() function: 
    def cosine_sim(a, b) -> float:
    a, b = np.array(a), np.array(b)
    return float(a.dot(b) / (np.linalg.norm(a) * np.linalg.norm(b)))
    This measures the angle between two vectors, ignoring their length — it returns a number from -1 (completely opposite meaning) to 1 (identical meaning), with 0 meaning unrelated. It's the standard way to compare embeddings: a.dot(b) (the "dot product") combines the two vectors into one number that's larger when they point the same direction, and dividing by both vectors' lengths (np.linalg.norm) makes the result independent of how "long" either vector happens to be — only the direction (meaning) matters.

  7. Run the whole script

    ./venv/bin/python ingest_sandbox.py
    It will load the 5 sample documents, chunk them, embed every chunk, embed one sample query ("How long do I have to return an item?"), and print the top 3 chunks ranked by similarity to that query. Read the printed chunk text — does the #1 result actually look like the best answer to that question? For the included sample documents (a fictional outfitter's policies), it should be the return-policy chunk.

  8. Record your settings

    Note your chunk size (400 words), overlap (50 words), and how many chunks you ended up with (5 documents → 5 chunks with these settings, since none of the sample docs are long enough to split further). You'll load these exact same chunks into a real database next week, so it's worth remembering what you used.

You'll know it worked when…

  • Your similarity scores clearly separate related from unrelated chunks — not a coin flip.
  • A ranked-by-similarity list for a sample query puts the genuinely relevant chunk at or near the top.

Common snags

  • Chunks too large — everything starts looking similarly related because each chunk covers too many topics at once.
  • Chunks too small — individual chunks lose the surrounding context needed to make sense on their own.
  • Hitting the embeddings API's per-request token limit — batch your chunks into smaller groups per call if you have a large sample set.
