Week 4 — Vector Databases & RAG Pipelines

Est. 3–5 hrs Outcome 2 RAG goes live

Goal

Move your Week 3 chunks into a persistent vector database, then wire retrieval into the Week 2 agent so it answers using your documents instead of general knowledge alone.

What you'll need

  • Starter code: this week's starter-code folder — includes the Week 2 agent, a working ingest.py, and a retrieve() stub to fill in
  • A free Supabase account — this is where your document chunks and their vectors will actually live
💡 Recommended: GitHub Codespaces. This week's starter code includes a .devcontainer/devcontainer.json — push the folder to a repo, then Code → Codespaces → Create codespace on main, and dependencies + your .env file are set up automatically. It sidesteps the most common bug in this course: a local machine with an old package already installed globally that silently shadows this project's own version. See this week's starter-code README for exact commands either way.
Retrieval-Augmented Generation: retrieve first, then let the model answer using what it found.

Steps

  1. Create a free Supabase project

    1. Go to supabase.com, sign up, and click New project.
    2. Give it any name, set a database password (save it somewhere — you'll need it in a moment), and pick the region closest to you.
    3. Wait a minute or two for it to finish provisioning.
    4. Once it's ready, go to Project Settings → Database and copy the Connection string (URI format). It looks like postgresql://postgres:[YOUR-PASSWORD]@db.xxxx.supabase.co:5432/postgres.
    What is Supabase, really? Underneath, it's just a regular Postgres database (the same kind of database used all over the software industry) that Supabase hosts for you for free, plus a nice web dashboard. You're going to use one special feature of it: the pgvector extension, which teaches Postgres how to store embedding vectors and search them by similarity — turning it into the "vector database" this week is named after.
    Copy your project's connection string into backend/.env as DATABASE_URL, alongside the GEMINI_API_KEY you already have from Week 1.

  2. Create the table

    In your Supabase project's dashboard, click SQL Editor in the left sidebar, paste in the contents of this week's backend/schema.sql, and click Run: 
    create extension if not exists vector;

create table if not exists documents (
    id bigserial primary key,
    content text not null,
    embedding vector(1024) not null,
    source text
);
    Line by line:
    • create extension if not exists vector; — turns on the pgvector extension for this database. Without this line, Postgres has no idea what a vector column type even is.
    • embedding vector(1024) — a column that stores exactly 1024 numbers per row. This must match the output_dimensionality you asked for from Gemini's embedding model in Week 3 — if they don't match, inserting a row will fail with an error.
    • content text — the actual chunk text, stored right alongside its vector, so a search can return the readable text, not just numbers.
    • source text — which original file this chunk came from, handy for debugging later.

  3. Load your chunks into the table

    Run the provided ingestion script, which chunks and embeds the same 5 sample documents from Week 3, then inserts every chunk into your new table: 
    ./venv/bin/python ingest.py
    It should print a line per document showing how many chunks were inserted. Open your Supabase dashboard's Table Editor, click on documents, and confirm you see rows with real text in content and a long list of numbers in embedding.

  4. Implement retrieve()

    Open backend/retrieval.py — the function currently just raises NotImplementedError. Replace its body with: 
    def retrieve(query: str, k: int = 5) -> list[str]:
    result = client.models.embed_content(
        model=EMBED_MODEL,
        contents=query,
        config=types.EmbedContentConfig(
            task_type="RETRIEVAL_QUERY",
            output_dimensionality=EMBED_DIM,
        ),
    )
    q_vec = result.embeddings[0].values

    conn = psycopg.connect(os.environ["DATABASE_URL"])
    rows = conn.execute(
        "select content from documents order by embedding <-> %s limit %s",
        (q_vec, k),
    ).fetchall()
    conn.close()
    return [row[0] for row in rows]
    Line by line:
    • task_type="RETRIEVAL_QUERY" — notice this is different from ingest.py, which uses "RETRIEVAL_DOCUMENT". Same embedding model, but told which side of the search this text is on, which changes how it optimizes the resulting vector slightly.
    • psycopg.connect(os.environ["DATABASE_URL"]) — opens a connection to your Supabase Postgres database using the connection string you saved in .env. psycopg is the Python library for talking to Postgres.
    • order by embedding <-> %s limit %s — this is pgvector's distance operator. <-> computes how "far apart" two vectors are; ordering by it ascending puts the closest (most similar) chunks first. %s are placeholders, safely filled in with q_vec and k — never build this SQL string with Python f-strings or +, which would open you up to SQL injection.
    • [row[0] for row in rows] — each row comes back as a tuple like ("some chunk text",); this pulls out just the text.

  5. Wire retrieval into the agent

    Open backend/agent.py. Find the commented-out TODO(week4) block at the top of run_agent() and uncomment/complete it so the function starts like this: 
    def run_agent(user_message: str) -> str:
    chunks = retrieve(user_message, k=5)
    context = "\n\n".join(chunks)
    system_instruction = (
        "Use the following context to answer the user's question. "
        "If the answer isn't in the context, say you don't know.\n\n"
        f"{context}"
    )

    interaction = client.interactions.create(
        model=MODEL,
        input=user_message,
        tools=TOOLS,
        system_instruction=system_instruction,
    )
    Then find the second interactions.create() call further down (inside the tool-calling loop) and add system_instruction=system_instruction there too — the model needs that context on every turn of the conversation, not just the first one.
    Why system_instruction and not just adding it to the user's message? A system instruction is treated as background guidance for the model's behavior, separate from what the user actually said — this keeps the user's question clean (useful for logging/debugging) and is the mechanism Gemini expects for "here's context, use it" instructions.

  6. Prove it's working — both ways

    Restart the server, then in the chat UI ask something that can only be answered from your sample documents (they're a fictional outdoor-gear company's policies) — for example, "How long do I have to return an item?" It should answer correctly, citing the 30-day window from the sample return-policy.md doc. Now temporarily comment out the chunks = retrieve(...) line (and just set context = "") and ask the exact same question again — the model should now guess incorrectly or say it doesn't have enough information. That contrast — right answer with retrieval, wrong or vague answer without it — is your proof that RAG is actually doing something, not just adding overhead.

You'll know it worked when…

  • A document-specific question is answered correctly with retrieval on.
  • The same question is answered visibly worse — wrong, vague, or "I don't know" — with retrieval off.

Common snags

  • Dimension mismatch — your table's vector(N) size must exactly match your embedding model's output size, or inserts will fail.
  • Embedding the query with a different model/config than your documents — similarity scores become meaningless if the two sides aren't comparable.
  • Injecting too many or too-long chunks — cap retrieval at ~3–5 chunks so you don't blow your context budget.
