Week 4 — Vector Databases & RAG Pipelines

Est. 3–5 hrs Outcome 2 RAG goes live

Goal

Move your Week 3 chunks into a persistent vector database, then wire retrieval into the Week 2 agent so it answers using your documents instead of general knowledge alone.

What you'll need

  • Your Week 2 agent + Week 3 chunking/embedding script
  • A Supabase project (instructor-provided connection string) with the pgvector extension already enabled

Steps

  1. Create the table

    In the Supabase SQL editor, run the provided schema — a documents table with a vector column sized to match your embedding model's dimensions exactly: 
    create extension if not exists vector;

create table documents (
  id bigserial primary key,
  content text,
  embedding vector(1024)  -- must match your embedding model's output size
);

  2. Load your chunks

    Re-run your Week 3 ingestion script, but this time INSERT each chunk and its vector into the table instead of holding it in a Python list.

  3. Verify the load

    Run select count(*) from documents; and spot-check one row in Supabase's table editor.

  4. Write a retrieve() function

    Embed the incoming query the same way you embedded documents, then use pgvector's distance operator to find the closest matches: 
    def retrieve(query, k=5):
    q_vec = embed(query)
    return db.execute(
        "select content from documents order by embedding <-> %s limit %s",
        (q_vec, k),
    ).fetchall()

  5. Wire it into the agent loop

    Before calling Claude, call retrieve() on the user's message and inject the top chunks as context — either in the system prompt or as a prepended message ("Use the following context to answer the question...").

  6. Prove it's working — both ways

    Ask a question that can only be answered from your sample docs, and confirm the agent gets it right. Then temporarily disable retrieval and ask the same question again — the agent should now guess wrong or admit it doesn't know. That contrast is the proof RAG is actually doing something.

You'll know it worked when…

  • A document-specific question is answered correctly with retrieval on.
  • The same question is answered visibly worse — wrong, vague, or "I don't know" — with retrieval off.

Common snags

  • Dimension mismatch — your table's vector(N) size must exactly match your embedding model's output size, or inserts will fail.
  • Embedding the query with a different model/config than your documents — similarity scores become meaningless if the two sides aren't comparable.
  • Injecting too many or too-long chunks — cap retrieval at ~3–5 chunks so you don't blow your context budget.
