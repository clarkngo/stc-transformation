Week 6 — Probabilistic Logic & Guardrails

Est. 3–4 hrs Outcome 3 Acts on your Week 5 review

Goal

Take the malformed-output failure point from your Week 5 review and actually fix it: add a validation layer that catches bad or hallucinated model output, retries with a corrective instruction, and fails safely if it still can't recover.

What you'll need

  • Starter code: this week's starter-code folder — includes a complete, reusable call_with_guardrail() template
  • Your Week 5 Architecture & Bottleneck Review

Steps

  1. Pick your target from Week 5

    Most students will have flagged something like "malformed tool-call arguments" or "the model answers even when it shouldn't have enough context." Pick one concrete spot in your code.

  2. Define an expected schema

    Even a simple one counts. Using Pydantic: 
    from pydantic import BaseModel

class ToolArgs(BaseModel):
    city: str
    units: str = "metric"

  3. Wrap the call with validate-then-retry

    def call_with_guardrail(fn, schema, *args, max_retries=2):
    for attempt in range(max_retries + 1):
        result = fn(*args)
        try:
            return schema.model_validate(result)
        except ValidationError as e:
            if attempt == max_retries:
                return {"error": "could not get a valid response"}
            args = add_correction_hint(args, str(e))  # tell the model what was wrong
    The key part beginners skip: the retry has to actually tell the model what was wrong, not just repeat the same prompt and hope.

  4. Set a hard ceiling

    Never let this loop run unbounded — cap it (2 retries is plenty) and always have a graceful fallback message ready for when it's exhausted.

  5. Break it on purpose

    Feed the model a prompt likely to produce malformed output (a trick question, an ambiguous request) and confirm your guardrail catches it — either self-correcting on retry, or failing with a clear message instead of crashing.

  6. Log every validation failure

    Even a plain print() for now — you'll want this data for Week 9's observability work.

You'll know it worked when…

  • You can point to a specific request that would have crashed or returned garbage without the guardrail.
  • With the guardrail in place, that same request now either self-corrects or fails with a clear, safe message — never a raw crash.

Common snags

  • Over-strict schemas — rejecting valid answers just because they're worded differently than expected. Validate the shape, not the exact wording.
  • Retries that don't correct anything — sending the identical prompt again rarely fixes a structural problem; the retry needs to include what specifically failed.
