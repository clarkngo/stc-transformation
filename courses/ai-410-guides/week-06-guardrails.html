Week 6 — Probabilistic Logic & Guardrails

Est. 3–4 hrs Outcome 3 Acts on your Week 5 review

Goal

Take the malformed-output failure point from your Week 5 review and actually fix it: add a validation layer that catches bad or hallucinated model output, retries with a corrective instruction, and fails safely if it still can't recover.

What you'll need

  • Starter code: this week's starter-code folder — includes a complete, reusable call_with_guardrail() template
  • Your Week 5 Architecture & Bottleneck Review
call_with_guardrail() wraps every tool call: validate, and only run the tool if the shape is right.

Steps

  1. Set up this week's project and pick your target

    Copy this week's starter code (it already has Weeks 1–4 solved for you). Reread your Week 5 review: most students flagged something like "malformed tool-call arguments" or "the model answers even without enough context." Pick one concrete spot — this guide walks through the tool-arguments case, since it's the one nearly everyone has.

  2. Read the guardrail template that's already written for you

    Open backend/guardrails.py. The hard part — retry logic — is already done: 
    def call_with_guardrail(
    fn: Callable[..., dict],
    schema: Type[T],
    *args,
    max_retries: int = 2,
    **kwargs,
) -> T | dict:
    last_error = None
    for attempt in range(max_retries + 1):
        try:
            raw = fn(*args, **kwargs)
            return schema.model_validate(raw)
        except ValidationError as e:
            last_error = e
            print(f"[guardrail] validation failed on attempt {attempt + 1}: {e}")

    return {"error": "could not get a valid response", "last_error": str(last_error)}
    Line by line:
    • fn: Callable[..., dict] — a type hint meaning "a function that returns a dict." This is generic on purpose: call_with_guardrail doesn't know or care what it's validating, only that it produces a dict-like thing to check.
    • schema.model_validate(raw) — asks Pydantic "does raw match this schema's shape?" If yes, it returns a real Python object with typed fields. If no, it raises ValidationError, caught right below.
    • for attempt in range(max_retries + 1): — tries up to max_retries + 1 times total (the +1 is the original attempt, then the retries).
    • return {"error": ..., "last_error": ...} — if every attempt fails, this returns a plain dict instead of raising an exception. That matters: whatever calls call_with_guardrail can check isinstance(result, YourSchema) and always has a safe fallback to handle, instead of needing a try/except of its own.

  3. Define a schema for your tool's arguments

    At the bottom of guardrails.py, add a Pydantic model describing exactly what valid arguments for your calculate tool look like: 
    from pydantic import BaseModel


class ToolArgs(BaseModel):
    expression: str
    This one field, expression: str, matches the single argument your calculate tool's schema declares in tools.py. If Gemini ever returns arguments missing that field, or with the wrong type, model_validate will raise ValidationError — that's the "malformed output" your guardrail exists to catch.

  4. Wrap the tool call in agent.py

    Open backend/agent.py. First, import what you just wrote: 
    from guardrails import call_with_guardrail, ToolArgs
    Then find the line inside the loop that directly calls the tool function (result = fn(**call.arguments)) and replace it with: 
    validated = call_with_guardrail(lambda: call.arguments, ToolArgs)
result = (
    fn(**validated.model_dump())
    if isinstance(validated, ToolArgs)
    else validated  # the {"error": ...} dict from the guardrail
)
    Line by line:
    • lambda: call.arguments — call_with_guardrail expects a function it can call (possibly more than once, on retries), not a value. Since call.arguments is already just a dict sitting there, wrapping it in a zero-argument lambda turns it into something callable that returns that dict each time.
    • isinstance(validated, ToolArgs) — checks which of the two possible return types you got back: a real validated ToolArgs object (success), or the plain error dict (all retries failed).
    • fn(**validated.model_dump()) — .model_dump() converts the validated Pydantic object back into a plain dict so it can be unpacked as keyword arguments into your tool function, the same way call.arguments was before.

  5. Break it on purpose

    Restart the server and ask something designed to confuse the calculator, like "calculate the color blue" or "what's the square root of a banana?" — something that might make the model send a weird or missing expression value. Watch your terminal: you should see the [guardrail] validation failed... print line if it ever produces something that doesn't validate, and the app should keep responding instead of crashing with a raw error page.

  6. Log every validation failure

    The print() already inside call_with_guardrail is your logging for now — that's intentional, not a shortcut you need to fix. You'll replace it with real observability tooling in Week 9, using exactly this same signal.

You'll know it worked when…

  • You can point to a specific request that would have crashed or returned garbage without the guardrail.
  • With the guardrail in place, that same request now either self-corrects or fails with a clear, safe message — never a raw crash.

Common snags

  • Over-strict schemas — rejecting valid answers just because they're worded differently than expected. Validate the shape, not the exact wording.
  • Retries that don't correct anything — sending the identical prompt again rarely fixes a structural problem; the retry needs to include what specifically failed.
