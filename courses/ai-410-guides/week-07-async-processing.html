Week 7 — Asynchronous Data Processing

Est. 4–5 hrs Outcome 3 New mental model: a second process

Goal

Move document ingestion off the request/response path entirely, into a background job, so uploading a new document never blocks the chat feature. This is the week most students without backend experience feel the biggest jump — take it step by step.

What you'll need

  • Starter code: this week's starter-code folder — includes working queue/worker boilerplate
  • A free Upstash account — this gives you a managed Redis database, which is what the job queue runs on
💡 Recommended: GitHub Codespaces. This week's starter code includes a .devcontainer/devcontainer.json — push the folder to a repo, then Code → Codespaces → Create codespace on main, and dependencies + your .env file are set up automatically. It sidesteps the most common bug in this course: a local machine with an old package already installed globally that silently shadows this project's own version. See this week's starter-code README for exact commands either way.
The API and the worker are two separate running programs, connected only through the Redis queue.

Steps

  1. Create a free Upstash Redis database

    1. Go to upstash.com, sign up, and click Create database.
    2. Choose the Redis type, give it any name, and pick a region close to you.
    3. On the database's page, find the Redis connection string / URL — it looks like rediss://default:xxxxx@your-instance.upstash.io:6379 — and copy it.
    Paste it into backend/.env as REDIS_URL, alongside your existing GEMINI_API_KEY and DATABASE_URL.
    What is Redis, and why do we need it here? Redis is a very fast, simple database, commonly used as a message queue — a to-do list that one program (your API) can add tasks to, and a different program (your worker) can pick tasks off of, one at a time. That's exactly the job here: hand off "please ingest this document" without making the person who asked wait for it to finish.

  2. Understand the two pieces that are already written for you

    Open backend/queue_setup.py — this is complete, you shouldn't need to change it: 
    from redis import Redis
from rq import Queue

redis_conn = Redis.from_url(os.environ["REDIS_URL"])
queue = Queue("ai410-ingestion", connection=redis_conn)
    rq ("Redis Queue") is a small Python library that turns Redis into a job queue with almost no boilerplate. redis_conn is the raw connection; queue is the actual to-do list you'll add jobs to and that your worker will pull from.
    Now open backend/worker.py: 
    from rq import Worker
from queue_setup import queue, redis_conn

if __name__ == "__main__":
    worker = Worker([queue], connection=redis_conn)
    worker.work()
    worker.work() starts an infinite loop: check the queue for a job, run it, check again, forever — until you stop the process. This file is meant to run as its own, separate program, not something your API starts automatically.

  3. Implement the job function

    Open backend/jobs.py — you'll see this raises NotImplementedError. Move your Week 4 ingestion logic in here, reading from a file path instead of the fixed sample-docs folder: 
    def ingest_document_job(doc_path: str) -> dict:
    with open(doc_path) as f:
        text = f.read()

    chunks = chunk_text(text)
    result = client.models.embed_content(
        model=EMBED_MODEL,
        contents=chunks,
        config=types.EmbedContentConfig(
            task_type="RETRIEVAL_DOCUMENT",
            output_dimensionality=EMBED_DIM,
        ),
    )
    vectors = [e.values for e in result.embeddings]

    conn = psycopg.connect(os.environ["DATABASE_URL"])
    cur = conn.cursor()
    for chunk, vector in zip(chunks, vectors):
        cur.execute(
            "insert into documents (content, embedding, source) values (%s, %s, %s)",
            (chunk, vector, os.path.basename(doc_path)),
        )
    conn.commit()
    conn.close()

    return {"chunks_inserted": len(chunks)}
    This should look familiar — it's the same chunk → embed → insert steps from Week 4's ingest.py, just packaged as one function that a worker can call on any file path, instead of a script that only knows about the fixed sample-docs folder. Always return a plain dict here (not a custom object) — rq stores whatever you return as the job's result, and the status endpoint you write next needs to read it back.

  4. Make the upload endpoint asynchronous

    In backend/main.py, find the /documents endpoint. It currently calls ingest_document_job directly, which blocks the request until ingestion finishes. Replace that with: 
    @app.post("/documents")
def upload_document(body: UploadRequest):
    job = queue.enqueue(ingest_document_job, body.doc_path)
    return {"job_id": job.id}
    queue.enqueue(...) doesn't run ingest_document_job itself — it just drops a note on the Redis queue saying "someone please run this function, with these arguments, eventually." It returns instantly with a job object containing an id, regardless of how long the actual work takes.

  5. Add the job-status endpoint

    from rq.job import Job
from queue_setup import redis_conn

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = Job.fetch(job_id, connection=redis_conn)
    return {"status": job.get_status(), "result": job.result}
    Job.fetch(job_id, ...) looks up that same job by the ID you returned in the previous step. job.get_status() returns one of "queued", "started", "finished", or "failed"; job.result is whatever dict your job function returned, once it's finished.

  6. Run both processes and prove it end to end

    You need two terminals open at once, both with the venv activated: 
    # Terminal 1 — the API
./venv/bin/uvicorn main:app --reload

# Terminal 2 — the worker
./venv/bin/python worker.py
    Then, from a third terminal (or a tool like curl), upload a document: 
    curl -X POST http://127.0.0.1:8000/documents \
  -H "Content-Type: application/json" \
  -d '{"doc_path": "sample_docs/return-policy.md"}'
    You should get a job_id back immediately. Copy it and poll the status endpoint: 
    curl http://127.0.0.1:8000/jobs/YOUR-JOB-ID-HERE
    Run that a few times — you should see "queued", then "started", then "finished". While it's still processing, send a normal chat message through the frontend at the same time and confirm it responds instantly — that's the proof the two are running independently.

You'll know it worked when…

  • Uploading a document returns a job ID instantly, not after ingestion completes.
  • The chat feature keeps working normally while a document is still being processed in the background.

Common snags

  • Jobs stuck "queued" forever — almost always means you forgot to start worker.py in its own terminal.
  • Worker crashes on missing API keys — it's a separate process with its own environment; env vars set for your API terminal don't automatically apply there.
