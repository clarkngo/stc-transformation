Week 8 — Mobile Client & Real-Time Push Notifications

Est. 3–4 hrs Outcome 5 Runs on your own phone

Goal

Get your app running on your own physical phone, and receive a real push notification the moment a Week 7 background job finishes — no Xcode, no Android Studio, no emulator.

What you'll need

  • Starter code: this week's starter-code folder — includes the Expo mobile shell and the backend's device-registration endpoint
  • The Expo Go app installed on your personal phone
  • A free Expo account, logged in on both your terminal (npx expo login) and the Expo Go app on your phone (tap the avatar icon → sign in) — on iOS, current Expo Go won't load the project at all without this. See the Account & Service Setup Guide for the exact steps.
  • Node.js — already included if you use a Codespace (see below); install it yourself if running locally
💡 Recommended: GitHub Codespaces. This week's starter code includes a .devcontainer/devcontainer.json with both Python and Node.js pre-installed — push the folder to a repo, then Code → Codespaces → Create codespace on main. Two things differ from running locally, because your phone and the codespace aren't on the same network: you'll run npx expo start --tunnel instead of the plain command, and you'll need to make the backend's port 8000 public in the Ports tab. Full steps are in this week's starter-code README.
Push notifications flow through Expo's own servers — your backend never talks to your phone directly.

Steps

  1. Start the Expo dev server

    cd mobile
npm install
npx expo start --tunnel
    A QR code appears in your terminal.
    What just happened? npm install downloads this mobile app's JavaScript dependencies (React Native, Expo, the notifications library), similar to what pip install -r requirements.txt does for Python. npx expo start runs a local development server that streams your app's code to whatever device scans the QR code — there's no app-store submission or build step involved for development like this. In Codespaces, always add --tunnel — the plain command uses LAN mode, which can't work since your phone and the Codespace aren't on the same network (it looks like it's hanging, not actually connecting). The first time you ever run --tunnel, Expo installs a small tunneling package on the spot, which takes a minute or two — after that, it starts fast. Running locally on your own laptop and your phone is on the same Wi-Fi? Plain npx expo start (no --tunnel) is faster there. (Note: --tunnel itself doesn't need any login — but current Expo Go on iOS separately requires the same Expo account logged in on both your terminal and the phone app just to load the project at all; see the Account & Service Setup Guide.)
    No phone handy yet, or want to sanity-check the chat screen fastest? Run npx expo start --web instead — opens the app in a browser tab, no Expo Go or login needed at all. Push notifications don't exist on web (the app already skips that step cleanly there), so switch to a real phone once you get to the push-notification steps.

  2. Open the app on your phone

    Install Expo Go from your phone's app store first if you haven't already. Then scan the QR code from the previous step — with your Camera app on iOS, or directly inside Expo Go on Android. The app opens live on your phone, running your actual project code, not a pre-built app.

  3. Confirm the basics work first

    mobile/src/api.js reads its backend address from an environment variable, the same pattern as backend/.env. Copy the template and set it: 
    cd mobile
cp .env.example .env
    Open the new mobile/.env and set EXPO_PUBLIC_API_BASE to wherever your backend actually is — it needs to point at an address your phone can reach, not localhost (your phone has no idea what "localhost" means on your laptop). In Codespaces: make port 8000 Public in the Ports tab and use its forwarded URL. Running locally: use your laptop's LAN IP (on macOS: System Settings → Wi-Fi → Details, or run ipconfig getifaddr en0 in a terminal): 
    EXPO_PUBLIC_API_BASE=http://192.168.1.23:8000
    Expo automatically inlines any environment variable prefixed EXPO_PUBLIC_ into the app — no extra config needed. Reload the app after editing .env (shake your phone → Reload, or press r in the terminal running expo start) to pick up the new value; just saving the file isn't enough, unlike editing code.
    With your Week 7 backend still running, send a message in the mobile chat screen and confirm you get a reply — the same backend you've been building since Week 1, just a different client talking to it.

  4. Read the permission-request code that's already written

    Open mobile/App.js and find registerForPushNotificationsAsync() — most of it is already implemented: 
    const { status: existingStatus } = await Notifications.getPermissionsAsync();
let finalStatus = existingStatus;
if (existingStatus !== "granted") {
    const { status } = await Notifications.requestPermissionsAsync();
    finalStatus = status;
}
if (finalStatus !== "granted") {
    console.warn("Notification permission not granted.");
    return;
}

const { data: pushToken } = await Notifications.getExpoPushTokenAsync();
    This checks whether you've already granted notification permission; if not, it asks (which is the system popup you'll see on your phone). Once granted, getExpoPushTokenAsync() asks Expo's servers for a unique token identifying this specific phone, running this specific app — that token is what your backend will use later to say "send a notification to that one device."
    Run the app and accept the permission prompt when it appears.

  5. Send the push token to your backend

    Right below where pushToken is logged, you'll find a commented-out TODO(week8) line. Uncomment it: 
    await registerDevice(deviceId, pushToken);
    registerDevice is already written for you in mobile/src/api.js — it just does a normal fetch() POST to your backend's /register-device endpoint, which is also already complete on the backend side. Restart the app (shake your phone or press r in the terminal running expo start) and confirm — by adding a temporary print() in the backend's register_device function, or checking the terminal running uvicorn — that a token actually arrives.

  6. Trigger a push when a job finishes

    Open backend/jobs.py. Near the bottom of ingest_document_job(), find the commented TODO(week8) block and uncomment/complete it: 
    if device_id:
    token = get_push_token(device_id)
    if token:
        send_push_notification(
            token,
            title="Document ready",
            body=f"Finished processing {os.path.basename(doc_path)}.",
        )
    get_push_token and send_push_notification are already written for you in devices.py and push.py — send_push_notification just makes an HTTP POST to https://exp.host/--/api/v2/push/send with your stored token, exactly like the Expo push API expects.
    Notice this function now accepts a device_id parameter that has to travel all the way from the mobile app's upload request, through main.py's /documents endpoint, through queue.enqueue(...), to finally reach this job function when the worker runs it. If you're missing the notification, check that device_id is actually being passed at every one of those steps — a very common bug here is silently dropping it in the middle.

  7. Test it for real

    From the mobile app, upload a document (you can point it at one of the sample docs' paths on your machine). Then lock your phone or switch to a different app entirely — this proves the notification arrives even when the app isn't open. When the Week 7 worker finishes processing, you should see a real push notification appear on your lock screen.

You'll know it worked when…

  • You get an actual push notification on your own physical phone.
  • You can trace it back to the exact backend event (a finished job) that triggered it.

Common snags

  • npm: command not found — this week's .devcontainer/devcontainer.json installs Node.js automatically, but only when the container is built. If this Codespace was created earlier (e.g. carried over from an earlier week that never needed Node), it won't have picked up that change. Command Palette (Cmd/Ctrl+Shift+P) → "Codespaces: Rebuild Container" — your files are untouched, only the container's installed tools get reapplied from the config.
  • "Project is incompatible with this version of Expo Go" — Expo Go on your phone only ever supports the newest Expo SDK, and it updates itself, so this project's pinned version can fall behind. Fix inside mobile/: npx expo install expo@latest, then npx expo install --fix to realign every other package, then restart npx expo start --tunnel. This will happen again after any future Expo SDK release — same two commands fix it.
  • Project won't load in Expo Go at all — stuck on a loading/login screen — unlike the push-token issue below, this blocks everything, chat included. Current Expo Go on iOS requires the same Expo account logged in on both your terminal (npx expo login) and the Expo Go app on your phone (tap the avatar icon on its home screen → sign in). Logged in as different accounts, or only on one side, and the project won't open.
  • App crashes (or a red error screen) the moment it asks for a push token — getExpoPushTokenAsync() requires an EAS project ID as of SDK 49+, and a fresh project doesn't have one yet. Run npx eas init once inside mobile/ (free — sign in with the Expo account above; no credit card) and it writes the ID into app.json for you. Chat works fine without this; only push notifications need it.
  • On Android, no push notification ever arrives — not even a failed one — this isn't a bug in this course's code. Expo removed push-notification support from Expo Go on Android entirely as of SDK 53 (iOS Expo Go still supports it). Chat still works fine on Android either way; for the actual push-notification proof step, test on an iPhone if you have access to one, or build a free Expo development client via eas build --profile development instead of using Expo Go (no local Android Studio needed — EAS builds it in the cloud).
  • Push notifications don't fire in a simulator/emulator — this has to be a real physical device for the free Expo Go flow.
  • Phone can't reach your laptop's backend — make sure both are on the same Wi-Fi network, or use Expo's tunnel mode if they're not.
  • Testing with npx expo start --web: "Failed to fetch" / server log shows OPTIONS /chat ... 405 Method Not Allowed — unlike Streamlit or Expo Go on a real device, Expo web runs inside an actual browser, and browsers block cross-origin requests until the server explicitly allows them (a "CORS preflight" check). This week's starter/answer backend/main.py already includes the fix (CORSMiddleware), so you shouldn't hit this — but if you've modified main.py and lost it, or you're troubleshooting your own version, that's the cause.
  • Replies feel slower on the phone than they did testing with curl — expected, not a bug. A curl test from inside the Codespace terminal is a loopback call; your phone's request travels over the real internet through GitHub's port-forwarding proxy to reach the Codespace and back, on top of whatever the agentic loop itself takes (a Gemini call, sometimes two if a tool fires, plus retrieval and guardrail validation). A couple of seconds is normal for this setup.
  • Permission denied — if you accidentally declined the notification prompt, you'll need to re-enable it in your phone's system settings for Expo Go.
