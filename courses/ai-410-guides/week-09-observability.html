Week 9 — Observability & Evaluation

Est. 3–4 hrs Outcome 4 Instrument, don't guess

Goal

Instrument the full pipeline you've built so far with tracing, then use real trace data — not guesswork — to explain exactly why one specific request was slow, expensive, or wrong.

What you'll need

  • Starter code: this week's starter-code folder
  • A free Langfuse account
  • Your working app through Week 8
What the Langfuse dashboard shows once both functions are decorated with @observe().

Steps

  1. Create a free Langfuse project

    1. Go to cloud.langfuse.com and sign up.
    2. Create a new project (any name).
    3. Go to Settings → API Keys and create a new key pair — you'll get a Public Key (starts with pk-lf-...) and a Secret Key (starts with sk-lf-...).
    Add all three to backend/.env: 
    LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_HOST=https://cloud.langfuse.com
    Why do we need this at all? Right now, if a request is slow or wrong, your only way to find out why is guessing, or scattering print() statements everywhere and rerunning. Observability tools like Langfuse record what actually happened on every real request — timing, inputs, outputs, cost — automatically, so you can look at data instead of guessing after the fact.
    Important: set these same three variables in both your API's .env and make sure your Week 7 worker process picks them up too (it reads the same .env file via load_dotenv(), but if you ever set env vars a different way for the worker, don't forget this set).

  2. Add tracing to the agent

    Open backend/agent.py. Uncomment the import at the top: 
    from langfuse.decorators import observe
    Then add @observe() directly above the run_agent function definition: 
    @observe()
def run_agent(user_message: str) -> str:
    ...
    What @observe() actually does: it's a decorator — a wrapper that Python applies around your function without you having to change the function's own code. Every time run_agent runs, Langfuse automatically records when it started, when it ended, what arguments it received, and what it returned, and packages all of that up as a "trace" it sends to your Langfuse project.

  3. Trace retrieval as its own step

    Open backend/retrieval.py, uncomment the same import, and add @observe() above the retrieve function too: 
    @observe()
def retrieve(query: str, k: int = 5) -> list[str]:
    ...
    Because retrieve() is called from inside run_agent(), Langfuse automatically nests it as a "span" inside the outer trace, rather than as a separate, disconnected trace — that's what produces the nested view in the diagram above. This distinction — one call to retrieve() vs. one call to Gemini, each timed separately — is exactly what lets you answer "which part was actually slow?" instead of only knowing the whole request took 1.8 seconds.

  4. Send some real traffic and find it in the dashboard

    Restart your server, send 4-5 different chat messages through the frontend, then go to your Langfuse project's Traces tab in the browser. Click into one. You should see the nested structure from the diagram above, with real numbers: latency for each step, the exact input and output text, and token/cost estimates for the Gemini call.

  5. Add one simple RAG evaluation

    Add this function to agent.py (a heuristic is enough — you don't need a second LLM call for this exercise, though that's a valid stretch goal): 
    def score_faithfulness(answer: str, context: str) -> float:
    """Rough heuristic: what fraction of the context's distinct words
    show up in the answer? Not rigorous, but enough to spot when the
    model is clearly ignoring the retrieved context."""
    context_words = set(context.lower().split())
    answer_words = set(answer.lower().split())
    if not context_words:
        return 0.0
    overlap = context_words & answer_words
    return len(overlap) / len(context_words)
    Call it at the end of run_agent() right before returning, and log the score (a print() is fine for this exercise): 
    score = score_faithfulness(answer, context)
print(f"[eval] faithfulness score: {score:.2f}")

  6. Deliberately break something

    Ask a question that's clearly outside your sample documents (something with no relation to a fictional outdoor-gear company's policies), or one you know trips your Week 6 guardrail. Go back to the Langfuse dashboard and find that exact trace.

  7. Write a short critique using the trace, not a guess

    A few sentences is enough: what exactly went wrong, what the trace data shows about why (which specific step was slow, what the retrieved context actually contained, whether your Week 6 guardrail fired), and one concrete change you'd make. The point of this step is that every claim in your critique should be something you can point to in the trace — not something you're inferring from memory.

You'll know it worked when…

  • You can pull up one specific real trace in the dashboard and point to the exact step that explains the outcome.
  • Your written critique cites the trace data itself, not a guess about what probably happened.

Common snags

  • Forgetting to instrument the worker — it's a separate process from your API and needs the same environment variables set independently.
  • Tracing too broadly — wrapping your entire request handler in one giant trace makes it unreadable. Trace at the level of individual meaningful steps (retrieval, generation, tool calls) instead.
