Week 9 — Observability & Evaluation

Est. 3–4 hrs Outcome 4 Instrument, don't guess

Goal

Instrument the full pipeline you've built so far with tracing, then use real trace data — not guesswork — to explain exactly why one specific request was slow, expensive, or wrong.

What you'll need

  • Starter code: this week's starter-code folder
  • A Langfuse project (public/secret key pair)
  • Your working app through Week 8

Steps

  1. Install and configure the SDK

    pip install langfuse
export LANGFUSE_PUBLIC_KEY="..."
export LANGFUSE_SECRET_KEY="..."
    Set these in both your API process and your Week 7 worker process — they're separate programs with separate environments.

  2. Trace your main Claude call

    from langfuse.decorators import observe

@observe()
def chat(message):
    context = retrieve(message)
    return client.messages.create(...)

  3. Trace retrieval separately

    Wrap your Week 4 retrieve() function the same way, so it shows up as its own linked step inside the trace — not folded into the LLM call.

  4. Run some real traffic through it

    Send a handful of chat requests, then open the Langfuse dashboard and find those traces. Look at latency per step, token counts, and estimated cost for each one.

  5. Add one RAG-specific evaluation

    Even a basic heuristic counts — for example, a simple check (or a second, cheap LLM call) that scores whether the final answer actually used the retrieved context, versus ignoring it.

  6. Deliberately break something

    Ask a question outside your document set, or one you know trips your Week 6 guardrail. Find that specific trace in the dashboard.

  7. Write the critique

    A few sentences: what exactly went wrong, what the trace data shows about why (which step was slow, what the retrieved context actually contained, whether the guardrail fired), and one concrete change you'd make.

You'll know it worked when…

  • You can pull up one specific real trace in the dashboard and point to the exact step that explains the outcome.
  • Your written critique cites the trace data itself, not a guess about what probably happened.

Common snags

  • Forgetting to instrument the worker — it's a separate process from your API and needs the same environment variables set independently.
  • Tracing too broadly — wrapping your entire request handler in one giant trace makes it unreadable. Trace at the level of individual meaningful steps (retrieval, generation, tool calls) instead.
