Week 10 — Capstone Integration, Deployment & Demo

Est. 5–6 hrs Outcome 5 Everything, together, live

Goal

Deploy the app you've built week over week — RAG, guardrails, async processing, push notifications, and observability — and demo the whole pipeline live, working, on infrastructure that isn't your own laptop.

What you'll need

  • Starter code: this week's starter-code folder — includes a Dockerfile and a Render deploy config for both the API and worker
  • Everything from Weeks 1–9 working locally
The finished, deployed shape of everything you've built since Week 1.

Steps

  1. Full local run-through first

    Before touching deployment, walk the entire pipeline end to end on your laptop: web/mobile client → chat → RAG → guardrails → async ingestion → push notification → traced in Langfuse. Fix anything that regressed since Week 9 now, while it's still easy to debug locally with full error messages in your own terminal.

  2. Push your code to GitHub

    Render deploys from a Git repository, so if your project isn't already on GitHub, create a new (private is fine) repository and push it now: 
    git init
git add .
git commit -m "AI 410 capstone"
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPO.git
git push -u origin main
    Double-check before pushing: confirm your project has a .gitignore that excludes venv/ and .env — you never want your real API keys ending up in a GitHub repo, even a private one. The starter code already includes one; if you copied files around manually, verify it's still there.

  3. Review the Dockerfile

    Open backend/Dockerfile: 
    FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
    This describes, step by step, how to build a fresh container image containing your app: start from a base image with Python 3.12 already installed, install your dependencies from requirements.txt, copy in the rest of your code, and finally define the command that starts the server. Confirm requirements.txt is current — a package you installed in Week 7 or 9 but forgot to add to that file is the single most common deploy-time surprise, since it works fine on your laptop (where it's already installed) but fails on a brand-new container that's never seen it.

  4. Create a Render account and deploy via Blueprint

    1. Go to render.com, sign up, and connect your GitHub account when prompted.
    2. Click New + → Blueprint.
    3. Select your repository, and point Render at the backend/ folder (where render.yaml lives).
    4. Render reads render.yaml and shows you it's about to create two services — ai410-api and ai410-worker — both built from the same Dockerfile, matching the diagram above.
    5. Before clicking deploy, you'll be prompted to fill in the environment variables listed in render.yaml (they're marked sync: false, which means Render doesn't auto-fill them — you provide the real values). Fill in GEMINI_API_KEY, DATABASE_URL, REDIS_URL, and the LANGFUSE_* keys for both services, using the exact same real values from your local .env.
    Why two services from one file? This is the same lesson as Week 7, just at deploy time now: your API and your worker are separate running processes with separate jobs. render.yaml defines them as two entries under services: — the worker one overrides the Dockerfile's default startup command with dockerCommand: python worker.py instead of running uvicorn.

  5. Wait for both to deploy, then verify

    Render will build and start both services — this can take a few minutes the first time. Once both show a green "Live" status, copy your API service's public URL (something like https://ai410-api.onrender.com) and test it: 
    curl https://ai410-api-YOUR-URL.onrender.com/health
    You should get back {"status": "ok"}. If it fails, check that service's Logs tab in the Render dashboard first — almost every deploy failure at this stage is a missing or mistyped environment variable, and the logs will usually name exactly which one.

  6. Point the mobile app at the deployed backend

    Open mobile/src/api.js and update API_BASE from your laptop's local IP to your new Render URL: 
    export const API_BASE = "https://ai410-api-YOUR-URL.onrender.com";
    Restart the Expo app on your phone and re-confirm chat and push notifications both still work — this time talking to your deployed server instead of your laptop.

  7. Re-run your Week 5 bottleneck list

    Pull out your Week 5 Architecture & Bottleneck Review and go through it again, this time against the deployed version. Did anything on that list only show up now that it's running somewhere other than your own machine — cold-start latency after the free tier spins down, a timeout that was generous enough locally but not over the network, a missing environment variable you never noticed because your local .env papered over it?

  8. Prepare and give a 5-minute live demo

    Upload a document from your phone and show it processing asynchronously (poll the job status endpoint), ask a question that requires the RAG pipeline, wait for the push notification to arrive, and pull up the corresponding trace in Langfuse — the entire pipeline you've built since Week 1, live, running on infrastructure you don't have to keep your laptop open for.

  9. Present for critique

    Be ready to explain any part of the architecture, not just the happy path you rehearsed — this is where your Week 5 bottleneck review and Week 9 trace-based critique get tested in front of an audience. "I'm not sure, let me check the trace" is a perfectly good answer; guessing is not.

You'll know it worked when…

  • A stranger could install Expo Go, scan your QR code (or open your deployed app), use it for real, and receive a real push notification — with zero setup on your laptop involved.
  • You can answer "why did that happen?" for any step in the live demo, backed by a trace, not a guess.

Common snags

  • Works locally, fails deployed — almost always a missing or mistyped environment variable on the host; check the host's logs first.
  • Free-tier hosts spin down when idle — the first request after idle time can be noticeably slow. Mention this honestly during your demo rather than being caught off guard by it live.
