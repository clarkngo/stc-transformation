How to use these

≈ 10 min per grader, once per HOS

Each Application Challenge asks for judgment on a new scenario, so there's no single right answer. These pairs show where full credit and partial credit usually land. Before grading a batch, read the pair for that HOS and score both yourself, then compare with the suggested score. If two graders share a section, doing this together is the fastest way to agree.

  • The strong answer makes one clear call and defends it with a concrete consequence — what breaks, for whom, if the call were wrong.
  • The typical answer is on-topic and mostly correct but restates the week's build, stays general, or misclassifies one thing. It's what most submissions will look like.
  • The most common way to lose Transfer points is reusing the lesson's warm-up scenario instead of the student's own.

HOS 1 — Tool schemas for a different business

Week 2O1

Prompt: design the tool schemas (not implementations) another business would need for its own agent, and justify each — including whether the model should be allowed to call it at all.

Rubric for every Application Challenge: Judgment & reasoning 50 · Transfer to the new scenario 35 · Clarity 15. Scores below are suggestions to calibrate against, not answer keys — a different design argued well deserves full credit.

Strong answer · Food bank volunteer desk≈ 95 / 100

Business: a regional food bank whose agent answers volunteers' questions and manages shift sign-ups.

list_open_shifts(site: "north"|"south"|"warehouse", date: YYYY-MM-DD)   → auto
sign_up_for_shift(volunteer_id: str, shift_id: str)                   → confirm first
cancel_shift(volunteer_id: str, shift_id: str)                        → confirm first
update_emergency_contact(volunteer_id: str, name: str, phone: str)    → never

list_open_shifts is read-only; a wrong call just shows the wrong day, which the volunteer can see. Sign-up and cancel commit a real person to a real warehouse, and a cancel the volunteer didn't mean leaves a site short-staffed, so the agent proposes and the volunteer taps yes. Emergency contacts are personal data about a third party; the agent links to the secure profile page instead.

Rejected: send_reminder_to_all_volunteers. One misread request ("remind everyone about Saturday") would text 800 people. That belongs to staff with a preview step, not to a chat agent.

  • Judgment: every tool gets a call and a concrete consequence; the rejected tool shows the student can say no.
  • Transfer: a new domain with its own risks (third-party data, mass messaging), not the calculator restated.
  • Clarity: schemas use constrained types (an enum for site, a date format), which shows the HOS 1 declaration ideas carried over.
Typical answer — partial credit · Pizza shop≈ 65 / 100

The pizza shop needs get_menu(), place_order(items), and calculate_total(expression). The model should be able to call all of them because that's how function calling works — the model decides which tool to use, like in our calculator app. calculate_total is important because models are bad at math.

  • Judgment (partial): no auto / confirm / never distinction. place_order spends the customer's money and gets the same treatment as reading the menu.
  • Transfer (partial): calculate_total is the HOS 1 calculator renamed; the reasoning is the lecture's, not the new business's.
  • Clarity: readable, but items has no type or shape, so the model can't know how to fill it.
  • Feedback to give: "Which of these would you let the model call without asking the customer? What happens if it's wrong?"

HOS 2 — Review someone else's RAG pipeline

Week 4O2

Prompt: given an unfamiliar RAG pipeline (the campus help-desk code in the lesson), name one thing it gets right, one thing likely to quietly underperform, and how you'd confirm that without running it.

Rubric for every Application Challenge: Judgment & reasoning 50 · Transfer to the new scenario 35 · Clarity 15. Scores below are suggestions to calibrate against, not answer keys — a different design argued well deserves full credit.

Strong answer · Help-desk pipeline≈ 95 / 100

Right: every chunk stores {"source": article_id}. When an answer is wrong, you can see which article it came from — that's the first thing I'd want when debugging, and it lets the bot cite its source to students.

Quietly underperforms: the chunks are embedded with task_type="RETRIEVAL_QUERY", the setting meant for questions. Nothing crashes, but documents embedded as queries tend to match questions less reliably, so the bot will sometimes pull a loosely related article and answer from it. It would show up most on questions phrased very differently from the articles ("my laptop won't talk to the wifi" vs. an article titled "Connecting to eduroam").

Confirming without running it: (1) Gemini's embedding docs describe the two task types and which side each is for — the code contradicts them. (2) Ask the team for five real student questions that got bad answers, and check whether the article that should have matched was the one retrieved; if the right article exists but loses, that points at retrieval rather than the model. (3) With n_results=1, a single slightly-wrong match has no backup, which makes this worse.

  • Judgment: picks the quiet failure the rubric is looking for and explains the mechanism, not just the name.
  • Transfer: uses the new pipeline's specifics (student phrasing, help-desk articles) rather than the Northwind docs.
  • Confirm-without-running is concrete: documentation, a small set of real failures, and a way to tell retrieval problems from model problems.
Typical answer — partial credit · Help-desk pipeline≈ 60 / 100

It gets right that it uses Chroma, which is a good vector database. The problem is that hits["documents"][0][0] will crash if there are no results. Also chunking every 2,000 characters might not be ideal. To confirm, I would run the code with an empty database and see if it crashes.

  • Judgment (partial): the empty-result crash is real, but the prompt asked for something that quietly underperforms — a crash is loud. The chunking point is right but unexplained.
  • Transfer (partial): "uses Chroma" is true of every pipeline in the course; it isn't something this pipeline got right.
  • Confirm-without-running: missed entirely — the plan is to run it.
  • Feedback to give: "Which of these would give students worse answers without anyone noticing? How would you prove it from outside the code?"

HOS 3 — A guardrail for a tool we haven't built

Week 6O3

Prompt: design a guardrail (schema + validation rule; working code optional) for a tool the course hasn't built. Argue for the one field you'd validate first and what goes wrong if you skip it.

Rubric for every Application Challenge: Judgment & reasoning 50 · Transfer to the new scenario 35 · Clarity 15. Scores below are suggestions to calibrate against, not answer keys — a different design argued well deserves full credit.

Strong answer · schedule_study_reminder≈ 95 / 100

Tool: schedule_study_reminder(message, send_at, channel) for a study-assistant agent.

class ReminderArgs(BaseModel):
    message: str = Field(min_length=1, max_length=200)
    send_at: datetime            # must be timezone-aware
    channel: Literal["push", "email"]

    @field_validator("send_at")
    def in_the_future_and_soon(cls, v):
        now = datetime.now(timezone.utc)
        if v.tzinfo is None: raise ValueError("send_at needs a timezone")
        if not (now < v < now + timedelta(days=90)): raise ValueError("send_at must be within the next 90 days")
        return v

Validate first: send_at. Models are unreliable with relative dates ("next Tuesday at 9") and time zones. Skip this and you get reminders scheduled in the past (they fire instantly, or never), or at 9 AM UTC — 2 AM for a student in Seattle the night before an exam. Both look like success in the logs.

What the schema can't check: whether the student actually has an exam then, or wants 40 reminders. A per-user rate limit (a lookup against existing reminders) belongs in the tool itself, not the schema.

  • Judgment: the chosen field has a specific, realistic failure, and it's silent — exactly the HOS 3 lesson.
  • Transfer: a new tool whose risks differ from calculate's (time, time zones, spam).
  • Understands the limit of schemas and names where the remaining check should live.
Typical answer — partial credit · book_room≈ 62 / 100

For a book_room(room, time) tool I would use Pydantic to make sure room and time are both present and are strings. If they're missing the guardrail retries twice and then returns an error, just like our calculate guardrail. This matters because the model is nondeterministic and might forget a field.

  • Judgment (partial): "present and a string" is the weakest possible check; time as a free string lets "tomorrowish" through.
  • Transfer (partial): the retry description is the lecture's; nothing is specific to booking rooms (double-booking, past times, rooms that don't exist).
  • Missing: the "one field first, and what goes wrong" argument.
  • Feedback to give: "Give me one value for time that passes your schema and still breaks the booking."

HOS 4 — An observability plan for a different AI feature

Week 8O4 · O5

Prompt: propose an observability plan — what to trace, what to score, what alert you'd want — for a different kind of AI feature, and argue what's worth watching versus what's noise.

Rubric for every Application Challenge: Judgment & reasoning 50 · Transfer to the new scenario 35 · Clarity 15. Scores below are suggestions to calibrate against, not answer keys — a different design argued well deserves full credit.

Strong answer · Meeting-notes summarizer≈ 95 / 100

Feature: after a recorded meeting, an agent summarizes the transcript and emails action items to attendees.

Trace: one trace per meeting with spans for transcript fetch, summarization (model call), action-item extraction (model call), recipient lookup, and email send. Splitting summarization from extraction matters: if action items are wrong, I want to know whether the summary was already wrong.

Score: action-item recall — for a weekly sample of 20 meetings, a person marks the real action items, and the score is the fraction the agent found. Word overlap would reward copying the transcript; recall measures what people actually use the email for.

Alert: any email sent to an address that wasn't a meeting attendee → page the on-call engineer immediately. It's rare, it's a privacy incident, and someone has to act now.

Not alerting on: summary length, or per-meeting latency. Long summaries and a slow day are annoying, not urgent; both go on a weekly dashboard.

  • Judgment: one alert, clearly justified as rare + urgent + actionable; explicitly declines to alert on noise.
  • Transfer: the score is designed for this feature's purpose, and the student explains why the course's word-overlap faithfulness wouldn't fit.
  • Clarity: the span split is motivated by a debugging question, not listed for completeness.
Typical answer — partial credit · Chatbot for a bank≈ 58 / 100

I would use Langfuse to trace every request and add a faithfulness score like in HOS 4. I would set alerts for latency over 3 seconds, faithfulness under 0.7, errors, token usage, and cost, so we know right away if anything goes wrong.

  • Judgment (partial): alerting on five metrics means alerting on everything; the prompt asked what is not worth watching.
  • Transfer (low): "a chatbot" with faithfulness is the course's own feature; a bank raises new risks (account data, transactions) the plan never touches.
  • Feedback to give: "If only one of these could page someone at 3 AM, which one — and why?"
