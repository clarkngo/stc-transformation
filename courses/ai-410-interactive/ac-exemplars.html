How to use these

≈ 10 min per grader, once per challenge

Each Application Challenge leaves one decision open on purpose, so there's no single right answer. These pairs show where full and partial credit usually land on the memo, which carries Analysis and Evaluation. Before grading a batch, read the pair for that challenge and score both yourself, then compare with the suggested score. If two graders share a section, doing this together is the fastest way to agree.

  • The strong answer makes one clear call and defends it with a concrete consequence — what breaks, for whom, if the call were wrong.
  • The typical answer has working code and a rule, but argues it in general terms ("seems reasonable", "more helpful") and tests only the easy case. It's what most submissions will look like.
  • Design and Application come mostly from the pasted pytest output and the report, so you rarely need to run anything. The time goes into the memo.

AC 1 — Cascade Family Clinic booking agent

Week 2O1

Challenge: build three booking tools to provided tests, decide what happens to a cancellation inside the 24-hour, $40 late-fee window, and decide whether to expose view_patient_record and send_sms. Guide

Rubric for every Application Challenge: Application 10 · Analysis 20 · Evaluation 30 · Design 40, each scored Full (100%), Partial (50%), or Missing (0%). The scores below add up those levels. A different rule argued well deserves full credit.

Strong answer100 / 100

Late cancellations: inside 24 hours the tool refuses and tells the patient to call the front desk. The fee is money, and a person should decide whether to charge or waive it (a sick child, a snowstorm). The cost is one phone call for the patient. I rejected adding a confirm_fee: true parameter: the model fills that in, so it would be the model confirming for the patient. My tests: S02 (3 hours away) is refused and stays booked; S06 (23.5 hours) is refused; S05 (25 hours) cancels.

view_patient_record: don't expose. The notes field holds diagnoses and allergies, the model could repeat them back, and the assistant isn't supposed to give medical advice. send_sms: only as send_reminder(slot_id), a fixed template to the number on file for the patient's own appointment. A free (phone, message) tool lets the model text anyone anything.

  • Application: the transcript shows the P1002 late cancel refused by the rule, in the clinic's own data.
  • Analysis: each wish-list tool is broken down into the data it exposes and the action it allows.
  • Evaluation: a clear rule, who it protects, its cost, and a rejected alternative with a specific flaw.
  • Design: all provided tests pass, and the student's tests sit on both sides of the 24-hour edge.
Typical answer, partial credit55 / 100

Late cancellations: the agent cancels and adds the $40 fee, because patients agreed to the policy when they booked. My test cancels S02 and checks the fee is recorded.

view_patient_record and send_sms: I would expose both because they make the assistant more helpful. I'd add "only use when needed" to each description.

  • Application (full): it runs in the clinic scenario and the transcript shows the rule.
  • Analysis (partial): "more helpful" never says what the tools would let the model see or do. A description isn't a permission.
  • Evaluation (partial): a rule with a reason, but no one weighed (who pays when the chatbot charges wrongly?) and no alternative.
  • Design (partial): tests pass, but the student's only test is 3 hours away; nothing tests the 24-hour edge.
  • Feedback to give: "Who should be able to waive the fee, and could the model do that with your tool?"

AC 2 — Riverbend help-desk retrieval

Week 4O2

Challenge: measure the vendor's RAG pipeline on 20 questions with known answers, beat it with your own chunking, and choose the score below which the bot says "I don't know". Guide

Rubric for every Application Challenge: Application 10 · Analysis 20 · Evaluation 30 · Design 40, each scored Full (100%), Partial (50%), or Missing (0%). The scores below add up those levels. A different rule argued well deserves full credit.

Strong answer100 / 100

Threshold: 0.25. From the sweep: 10 right, 3 wrong, 4 declined. At 0.30 I'd get only 1 wrong but decline 6 answerable questions into a two-day queue; at 0.20, 4 wrong. A wrong answer about a Canvas deadline can cost a student a grade, so I accept some declines, but not six. The closest call is x04 ("password on the Wi-Fi printer", 0.28): it still gets an answer from the passwords article. My test documents that on purpose.

Misses: the vendor's q01, q08, q14 and q15 were chunking: the answer was cut across 500-character slices. Section chunks fixed all four. My remaining q09 ("Xbox"), q05 ("didn't" vs "did not") and q16 ("largest" vs "larger") are vocabulary: no chunking fixes them. Adding titles to my chunks lowered hit@1 from 0.81 to 0.69, because extra words dilute a word-count vector.

  • Application: beats the vendor (0.81 vs 0.56) with the sweep and misses in the report.
  • Analysis: every miss is sorted by cause, with the question that shows it and what would fix it.
  • Evaluation: the threshold is argued from the sweep's numbers, against a named cost, with two rejected alternatives.
  • Design: tests pass, and the student's tests include the x04 near miss.
Typical answer, partial credit75 / 100

Threshold: 0.2. It seemed like a good balance between answering and not answering.

Misses: some misses are because of chunking and some because the words are different. Better embeddings would help.

  • Application (full): the report shows a working chunker that beats the vendor.
  • Analysis (partial): both causes are named, but no question is tied to either.
  • Evaluation (partial): "a good balance" doesn't say which mistake is worse or use the sweep (at 0.20: 4 wrong answers).
  • Design (full): tests pass, with one answerable and one out-of-scope question.
  • Feedback to give: "Read the 0.20 row of your sweep aloud. Which of those four wrong answers would you send to a student?"

AC 3 — Pacific Bean refund guardrail

Week 6O3

Challenge: build the schema, order checks, and routing for a refund tool, replay 12 recorded model calls through it, and decide what the bot may refund without a person (never over $500). Guide

Rubric for every Application Challenge: Application 10 · Analysis 20 · Evaluation 30 · Design 40, each scored Full (100%), Partial (50%), or Missing (0%). The scores below add up those levels. A different rule argued well deserves full credit.

Strong answer100 / 100

Routing: up to $75 goes straight through. That covers a damaged bag of beans; it doesn't cover a grinder. A second refund on the same order always goes to a person, because a $75 limit is easy to beat with two $70 requests. I rejected a percentage limit: 40% of the $1,240 espresso machine is $496, under the hard limit. Tests: $75.00 goes through, $75.01 is queued, a second $10 refund on PB-1001 is queued.

Layers: the schema stops "twenty dollars", 12.833, -18, "1001", "broken" and approved: true; that last one matters most, because the model was trying to authorize itself. Only a lookup knows the friend's order isn't yours, the October order is 46 days old, and only $104 of the grinder is left. A person has to judge the stale wholesale beans. Still gets through: #12, $104 because the grinder "doesn't grind fine enough for espresso". That's buyer's remorse labelled not_as_described, and my limit only stops it by accident.

  • Application: every recorded call is handled, and the report matches the rules.
  • Analysis: each bad call is assigned to the first layer that can catch it, with why, plus a call that still passes.
  • Evaluation: a dollar limit and a repeat-refund rule, each tied to a risk, with a rejected alternative shown to fail.
  • Design: tests pass, and the student's tests sit exactly on the limit.
Typical answer, partial credit50 / 100

Routing: AUTO_REFUND_LIMIT is $100, which seems reasonable for a coffee shop. My tests check that $5 is refunded and $1,000 is queued.

Layers: Pydantic catches bad inputs, and the order checks catch the rest.

  • Application (partial): it runs, but call #12 is queued only because of the limit, and the memo never says so.
  • Analysis (partial): two layers named, but no recorded call is assigned to either, and the review queue isn't mentioned.
  • Evaluation (partial): "seems reasonable" has no criteria and no alternative.
  • Design (partial): tests pass, but nothing tests near $100, and two $95 refunds on one order would both go through.
  • Feedback to give: "Give me two refunds that each pass your rules and together you'd never approve."

AC 4 — Puget Pantry substitution observability

Week 8O4 · O5

Challenge: trace and score a grocery service's AI substitution feature, run a recorded day of orders through it, and decide what pages the on-call engineer. Guide

Rubric for every Application Challenge: Application 10 · Analysis 20 · Evaluation 30 · Design 40, each scored Full (100%), Partial (50%), or Missing (0%). The scores below add up those levels. A different rule argued well deserves full credit.

Strong answer100 / 100

Paging: page only when a substitute with one of the customer's own allergens was pushed to their phone: O-502, O-505, O-506. It's rare, it can hurt someone, and a person can act now by calling the customer or stopping the van. Price jumps (five 0.5 scores) and the 3,900 ms model call go on the dashboard: annoying, not urgent. I rejected "page on any 0.0 score", because the score also gives 0.0 when no substitute exists, which is a stocking problem, not a 3 a.m. one. My hand-built test: an allergen chosen but the push failed doesn't page.

What the spans show: choose_substitute shows what was picked and how long the model took; the score shows the price jump; notify shows the message really went out. One "order processed" line would show nothing wrong on any of the ten orders. The trace reveals that the push goes out before anyone can check it, but it can't fix that, and it can't show whether a cheaper, safe option existed (the span stores the count, not the candidates).

  • Application: every order traced and scored; the three pages match the stated rule.
  • Analysis: each problem tied to the span that shows it, compared with one log line, plus two things the trace can't show.
  • Evaluation: rare, harmful, actionable, applied; a rejected rule with the specific case it gets wrong.
  • Design: tests pass, including a hand-built edge case the day doesn't contain.
Typical answer, partial credit75 / 100

Paging: page whenever any substitution scores below 1.0, so nothing bad is missed. That pages O-502, O-504, O-505, O-506, O-507, O-508 and O-510.

What the spans show: the spans show each step of the feature and how long it took, which helps with debugging.

  • Application (full): every order traced and scored; the pages match the rule.
  • Analysis (partial): spans listed, but no problem from the day is tied to one, and no single-log comparison.
  • Evaluation (partial): a rule with a reason, but it pages for seven of ten orders, which is exactly what the operations lead warned about.
  • Design (full): tests pass, with a must-page and a must-not-page order.
  • Feedback to give: "Your pager went off seven times today. Which one would you get out of bed for?"
