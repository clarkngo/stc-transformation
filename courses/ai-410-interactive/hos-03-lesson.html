Guardrails & Async Processing

Make the HOS 2 app dependable under two kinds of unpredictability: a model that sometimes hands your code bad arguments, and slow work that freezes the app if it runs inside the request. Built in Week 5; explained and extended by hand in Week 6, with a quick Team/Term Project check-in.

Lesson overview

Outcome O312.5% HOS + MP + CD + AC+ Team/Term Project checkpoint

Your HOS 2 app works — most of the time. That's the problem this HOS is about. A model that returns valid tool arguments 95% of the time will, across a few hundred requests a day, hand your code garbage several times a day. And a document upload that takes twenty seconds to chunk and embed will, if it runs inside the web request, freeze the app for everyone while it runs. Neither shows up in a quick demo. Both show up the first week real people use it.

This HOS adds the two reliability layers every production agent needs: a guardrail that checks model output before your code trusts it, and a queue with a background worker that moves slow work off the request path. Week 5 builds and tests both. Week 6 explains why they're designed the way they are, extends the guardrail by hand, and ends with a quick check-in on your Team/Term Project.

Anchoring analogy

A busy restaurant has two rules. First, the kitchen reads back every order ticket before cooking — "no onions, extra sauce?" — because a waiter who's right 95% of the time still ruins a dish every night. That's the guardrail. Second, the waiter doesn't stand at the counter while a 40-minute brisket cooks; they hand the kitchen a ticket, take a number, and go serve other tables. That's the queue: the ticket number is your job_id, and the cook working in the back is your worker process.

Learning objectives

By the end of the two weeks you will be able to:

  1. Explain why nondeterministic model output must be validated before code acts on it. O3
  2. Implement a validate-and-retry guardrail that feeds the validation error back into the retry, and fails to data instead of crashing. O3
  3. Distinguish structural validation (a schema can check it) from semantic validation (it needs a lookup or a human). O3
  4. Analyze where an agent-driven app bottlenecks, and move long-running work to a queue and worker. O3
  5. Diagnose the common failures of a queue-based design, including a worker that isn't running. O3

Lecture: making an unpredictable system dependable

≈ 70 min3 short partsO3

Three short segments. Pause after each and try the quick check. Anything that stays fuzzy goes in your Muddiest Point.

Part 1 — Nondeterminism reaches your code ≈ 20 min

In HOS 1 you saw that the same prompt can produce different outputs. Until now that mostly affected wording. But when the model produces tool arguments, its output goes straight into your code — and code is not forgiving. The model might send {"expr": "25*4"} instead of {"expression": ...}, an empty string, a number where a string belongs, or a perfectly-formed "sqrt(banana)".

The course description calls this "probabilistic logic for handling nondeterministic outputs." In practice it means one habit: treat model output like user input. You wouldn't pass a web form's text straight into a database; don't pass a model's arguments straight into a function. Check them against a schema first — in Python, a Pydantic model that says exactly what shape and values are allowed.

Worked example

A user types "calculate the square root of a banana." The HOS 2 app passes the model's arguments straight to calculate(), which raises an exception — HTTP 500, and the user sees a generic error. With a schema that allows only digits, operators, and parentheses, the bad argument is caught before the tool runs, and the app can decide what to do next instead of crashing.

def call_with_guardrail(fn, schema, max_retries=2):
    hint = None
    for attempt in range(max_retries + 1):
        raw = fn(correction_hint=hint)          # ask the model (again)
        try:
            return schema.model_validate(raw)   # valid → done
        except ValidationError as e:
            hint = str(e)                       # tell the next attempt what was wrong
    return {"error": "could not produce valid arguments"}

Three design choices are doing the work. Retrying gives a nondeterministic system another roll. Feeding the error back makes the next roll better than the first — a blind retry repeats the same mistake. And failing to data ({"error": ...}, not an exception) keeps the request alive so the model can explain the problem to the user, like HOS 1's try/except.

One limit to keep in mind: a schema checks shape, not meaning. If the user asked for 25 + 4 and the model sends "25*4", that passes every structural check. Some mistakes need a lookup or a human — you'll sort which is which in the Application Challenge.

Quick check

Each retry costs another model call. If a tool fails validation 30% of the time and you allow 2 retries, roughly how many model calls does an average request make? Is that worth it?

Part 3 — Async: moving slow work off the request path ≈ 25 min

Ingesting a document means chunking it and embedding every chunk — easily many seconds for a long file. If POST /documents does that work inside the request, the user waits the whole time, and in a simple server so does everyone else. The fix is to split "accept the work" from "do the work."

The client checks progress with GET /jobs/{id}. The worker is a separate operating-system process, started in its own terminal — which is why the most common HOS 3 bug is jobs stuck on queued forever: nobody started the worker. Nothing errors. The queue just waits.

Try it before the build

Open the Guardrails & Queue Simulator. Send 20 requests with the guardrail off, then on. Then upload a document in inline mode and send "hi" — compare the wait with queue mode. Finally, set workers to 0.

Teaching note

This is the first HOS with two long-running processes (uvicorn and the worker). Have students split their Codespaces terminal before the build starts. And tell macOS users about the known RQ fork issue up front, or suggest Codespaces, where it doesn't occur (see the hands-on guide's Common snags).

New words this week

Nondeterministic output & guardrail
Output that can differ on every run, and a check that validates it — retrying or failing safely when it's wrong.
Schema (Pydantic)
A precise definition of what data is allowed: field names, types, and rules like "not empty."
Queue, worker & job
A waiting line of work (in Redis), a separate process that takes work from it, and one unit of that work with its own ID and status.
Request path
Everything that happens between a request arriving and its response being sent. Slow work on this path makes users wait.

    Concept Debate

    Graded · part of 5% CD categoryDiscussion board · 3 stages
    This week's question

    When a model's output fails validation, should the system keep retrying for a better answer, or fail fast and tell the user?

    You'll argue the side your debate team is assigned, then argue the other one, then drop advocacy and synthesize.

    Your side this HOS

    Sides rotate each HOS. In HOS 3, Debate Team 1 argues Side A and Debate Team 2 argues Side B — the same as HOS 1. Find your team under Communication → Groups in Brightspace. Not in a team? Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A. How sides are assigned →

    Side A — Retry until it's right (within a budget)Team 1 this HOS

    Retry with the validation error fed back, up to a sensible limit, before giving up.

    • Most validation failures are one-off; a second roll with feedback usually succeeds.
    • The user asked for a result, not an error message.
    • A retry costs cents and a second or two; a failed task costs the user's trust.

    Side B — Fail fast and tell the userTeam 2 this HOS

    Validate once; on failure, return a clear error and let the user rephrase or try again.

    • Every retry adds latency and model cost, and multiplies at scale.
    • A model that produced bad output once may be confused by the input — retrying hides that signal.
    • Fast, honest failure is predictable and easy to test.
    Stage 1 · by Tue

    Initial position

    Argue your assigned side with one specific claim and one piece of evidence — a simulator run (try "Send 20" with different retry settings), a test from your build, a cost estimate.
    Stage 2 · by Thu

    Argue the opposite

    Before replying to anyone, post the strongest version of the side you didn't hold.
    Stage 3 · by Sat

    Synthesis

    Drop advocacy. State a real position, citing at least one specific point from a classmate's post.
    Weak synthesis"Retrying is good but not too much. Balance is key."
    Strong synthesis"Jordan's simulator numbers convinced me: with the error fed back, 2 retries recovered almost every failure, but a third retry recovered almost nothing extra. So: retry exactly twice with feedback for read-only tools, and fail fast on the first failure for anything that changes data — Kai's point that a confused model is a signal matters most when the tool isn't reversible."

    Grading: Participation — initial position plus response to at least one peer (50%) · Writing — quality of argument and reasoning (50%).

    Application Challenge — design a guardrail for a tool we haven't built

    5% of courseSchema + validation rule — working code optional

    Pick a tool this course hasn't built and design its guardrail: the schema, and the one field you'd validate first — with what specifically goes wrong if you skip it.

    Warm-up: what can a schema actually catch?

    A clinic's agent has a tool book_appointment(pet_id, service, start_time, notes). For each proposed check, decide: can a schema catch it, does it need a lookup (database or API), or does it need a human?
