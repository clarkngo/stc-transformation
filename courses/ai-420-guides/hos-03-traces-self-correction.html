HOS 3 — Reasoning Traces, Failure Diagnosis & Self-Correction

Est. 3–4 hrs Outcome 3 Scaffolding: spec only — you write the prompt 12.5% of final grade
Draft — in faculty testing. The code for this HOS has been checked offline (tools against the real free APIs, agent logic against a scripted stand-in model), but not yet run end to end against Gemini. Faculty running it: note anything that breaks or takes longer than the estimate.

Goal

Harbor Supply Co.'s customer-support agent looks fine and fails in several different ways. Find every failure from the traces alone, before you read its source code — the way on-call engineers debug agents they didn't write. Then make it correct itself.

What you'll need

  • Starter code: this HOS's starter-code folder. Copy it into your portfolio repo (made from the portfolio template in Week 1) as its own folder, then open the repo in GitHub Codespaces. Dependencies install automatically.
  • Your free Gemini API key (the same one from AI 410, no credit card) from aistudio.google.com/apikey. In the HOS folder: cp .env.example .env, then paste it in as GOOGLE_API_KEY.
  • An AI coding assistant in your Codespace (Antigravity, Claude Code, or equivalent)
  • A free Langfuse account (no credit card) — the same project as AI 410 HOS 4 is fine. Keys go in .env.

Reference reading (optional, before you start)

  • agent-development hos09 — callbacks: the before/after hooks you'll use in Stage 4.
  • agent-development hos12 — loop agent: how a loop is supposed to end (exit_loop, max_iterations).

This HOS is graded across four stages instead of on code correctness alone. Each stage below says exactly what to submit.

1Create / Scaffold

Not graded on its own — this is the starting point, not the deliverable.

Don't open support_agent/tools.py or agent.py yet. First run the six scenarios and read what comes out:

python run_scenarios.py

Each run prints a trace (every tool call, result, reply, and error, with timings) and saves it under traces/. That's your local trace. Now the spec for your AI assistant. This time you write the prompt yourself.

Every agent run from run_scenarios.py (and from adk web) should also appear in Langfuse as one trace, with each model call and each tool call as its own span showing inputs, outputs, and timing. It should switch on only when Langfuse keys are in .env, and do nothing otherwise. run_scenarios.py already imports a module called tracing if one exists and calls tracing.flush() at the end.

Keep your prompt; you'll submit it.

2Evaluate

The critical gate — find every failure from the traces, not the code.

For each scenario, decide from the trace alone: did it succeed? If not, fill in one row of a failure log:

ScenarioFailure typeFirst step where it showsSymptomLikely root cause
s1-…tool-call error / logic loop / invented action / wrong data / wrong tool / nonee.g. step 2, the first check_shipment resultWhat you actually seeYour best guess, before reading the code

Not every failure crashes. Watch for runs that finish politely and are still wrong. For any number the agent states, check it against what the tools actually returned.

Submit
  • Your prompt from Stage 1.
  • A screenshot of one Langfuse trace with the tool calls visible as separate spans.
  • Your failure log, one row per scenario, written before you opened the source.

3Analyze

Why does this happen, mechanically?

Now open the source. Pick the one failure you think is most dangerous in production and explain it fully:

  • Which line of code or instruction causes it, and why does the model behave the way it does given what it was told?
  • Why didn't it crash, or, if it did, why is crashing actually the less dangerous outcome here?
  • How would a real customer or manager find out, and how long might that take?
Submit
  • A short written walkthrough of the one failure you chose, in your own words.

4Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

Fix each root cause you found in tools.py and the instruction. Then add two generic guards that don't know about any specific bug, in support_agent/guards.py, attached as ADK callbacks:

  • on_tool_error_callback: when a tool raises, return an error dict the model can read instead of crashing the run.
  • before_tool_callback: count identical calls (same tool, same arguments) within one run. After two, skip the real call and tell the model the result won't change. (Hint: returning a dict skips the tool; returning None lets it run. Keys starting with temp: in tool_context.state last for one run only.)

Rerun all six scenarios. Keep the --max-calls budget in place: it's the last line of defense if a model ignores your guard.

Submit
  • Your guards.py and a short list of the fixes you made to tools.py and the instruction.
  • Before/after traces for two scenarios, showing the agent now recovering on its own.
Honor code

Tick one when you submit: ☐ "I wrote the Stage 4 code myself, without AI assistance, under the CityU academic integrity policy." or ☐ "I used AI for part of Stage 4. Here's what I used it for and why."

Disclosed AI use earns partial credit on this stage instead of zero, so saying so honestly always costs less than hiding it. The Week 5 cold build is where independent skill is checked directly.

Common snags

  • A scenario ends with LlmCallsLimitExceededError — that's the step budget from --max-calls stopping a runaway loop. It's a finding, not a problem with the script.
  • A trace looks different each run — expected; the model isn't deterministic. If a failure doesn't show up, run that scenario again with --only. Base your log on what you saw, and note when behavior varied.
  • Nothing appears in Langfuse — traces are sent in batches, so the script has to call flush() before it exits. Also check LANGFUSE_HOST matches your account's region (the EU and US clouds have different URLs).
  • Huge red tracebacks in the terminal — ADK logs every tool error. run_scenarios.py quiets that logger and records the error in the trace instead. If your AI assistant rewrote the script, check it kept that line.
  • 429 RESOURCE_EXHAUSTED — you hit the free tier's per-minute limit. Wait a minute and rerun; the scripts' --pause option adds a gap between runs.
  • Codespaces doesn't pick up the devcontainer — Codespaces only reads .devcontainer/ at the root of a repo. Use the portfolio template (its devcontainer covers all four HOS), or make this HOS folder the root of its own repo.
