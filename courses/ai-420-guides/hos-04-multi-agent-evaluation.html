HOS 4 — Multi-Agent Orchestration & Agent-on-Agent Evaluation

Est. 4–5 hrs Outcome 4 Scaffolding: goal only 12.5% of final grade
Draft — in faculty testing. The code for this HOS has been checked offline (tools against the real free APIs, agent logic against a scripted stand-in model), but not yet run end to end against Gemini. Faculty running it: note anything that breaks or takes longer than the estimate.

Goal

Turn Harbor Supply Co.'s single support agent into a team — a coordinator plus specialists — and then find out, with numbers, whether the team is actually better. Test both versions the way industry does: a simulated customer talks to each one, a judge agent grades every conversation, and you report success rate, cost per task, and latency.

What you'll need

  • Starter code: this HOS's starter-code folder. Copy it into your portfolio repo (made from the portfolio template in Week 1) as its own folder, then open the repo in GitHub Codespaces. Dependencies install automatically.
  • Your free Gemini API key (the same one from AI 410, no credit card) from aistudio.google.com/apikey. In the HOS folder: cp .env.example .env, then paste it in as GOOGLE_API_KEY.
  • An AI coding assistant in your Codespace (Antigravity, Claude Code, or equivalent)

Reference reading (optional, before you start)

  • agent-development hos07 — manager/supervisor and hos08 — customer service team: a coordinator delegating to specialists.
  • hos10 — sequential, hos11 — parallel, hos12 — loop: the other three orchestration patterns.

This HOS is graded across four stages instead of on code correctness alone. Each stage below says exactly what to submit.

1Create / Scaffold

Not graded on its own — this is the starting point, not the deliverable.

The starter gives you the repaired single agent from HOS 3 (single_agent/), twelve test scenarios (evals/scenarios.json: a persona, a goal, and a success rule each), and a price sheet (evals/pricing.json). There's no prompt this time. Here's the goal. You decide the design and direct your assistant:

  1. A team version in team_agent/: a coordinator that routes each request to specialists, each specialist holding only the tools it needs. Reuse single_agent/tools.py and guards.py; don't copy them.
  2. An evaluation harness (evals/run_eval.py) that, for each scenario, has a simulated customer (an LLM playing the persona) hold a multi-turn conversation with either system, then has a judge (an LLM with structured JSON output) grade the transcript against the success rule.
  3. Metrics for each system: success rate; cost per task (input and output tokens × the prices in pricing.json); and latency per agent reply, as p50 and p95. Count simulator and judge tokens separately; they're the cost of testing, not of the agent.
  4. A side-by-side report comparing single and team.

Free-tier budget: a full run is roughly 10–15 model calls per scenario, so all twelve scenarios on both systems is about 250–350 calls. Get it working with 2–3 scenarios first. Consider a smaller model for the simulator and judge (SIM_MODEL and JUDGE_MODEL in .env).

2Evaluate

The critical gate — is the AI-produced result actually correct?

Before you trust any number, check the harness itself:

  • Read three simulated conversations end to end. Does the simulated customer stay in character and stop when its goal is met, or wander off and pad the conversation?
  • Check the metric math by hand for one scenario: tokens × price = the cost it reported? Is p95 really the 95th percentile of the reply times, or something else?
  • Find a scenario where the judge's verdict looks wrong to you, if there is one. What in the success rule or the judge prompt let it happen?
Submit
  • Your side-by-side report (all three metrics for both systems).
  • A short note on what you checked in the harness, and anything you had to fix before trusting the numbers.

3Analyze

Why do the numbers come out the way they do?

Explain your results. Did the team beat the single agent on success rate? Whatever the answer, it probably cost more tokens and time. Using one or two specific traces, explain where the extra cost comes from (hint: count the model calls the coordinator adds on each turn), and name one kind of request where splitting into specialists helps and one where it only adds overhead.

Submit
  • A short written analysis, in your own words, citing at least one specific conversation.

4Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

An LLM judge is only worth trusting as far as it agrees with careful human grading. Measure that yourself:

  • Read at least six transcripts from one run and record your own pass/fail in evals/human_labels.json (e.g. {"vhf-price": true, "refund-cancelled": false}).
  • Write evals/agreement.py: it compares your labels with the judge's verdicts and prints the agreement rate, which scenarios the judge passed that you failed (too lenient), and which it failed that you passed (too strict), with the judge's stated reason for each.
Submit
  • Your agreement.py and human_labels.json.
  • The agreement rate, and two or three sentences: would you report this judge's success rate to a manager as-is? If not, what would you change first?
Honor code

Tick one when you submit: ☐ "I wrote the Stage 4 code myself, without AI assistance, under the CityU academic integrity policy." or ☐ "I used AI for part of Stage 4. Here's what I used it for and why."

Disclosed AI use earns partial credit on this stage instead of zero, so saying so honestly always costs less than hiding it. The Week 5 cold build is where independent skill is checked directly.

Common snags

  • The coordinator answers questions itself instead of transferring — its instruction has to say plainly that it doesn't answer, only routes, and each specialist's description has to make ownership obvious. The coordinator reads those descriptions to decide where to send a request.
  • A two-part question only gets half answered — after transferring, the specialist owns the conversation. Tell specialists to transfer back to the coordinator when the rest of the request isn't theirs.
  • The simulated customer never says it's done — give it an exact stop word and a turn cap. Without a cap, one confused conversation can use up your free-tier quota.
  • The judge's output won't parse — ask for structured output (response_mime_type="application/json" with a schema) rather than parsing free text.
  • Your costs look impossibly low — pricing.json ships with example prices. Look up your model's current list price and update it before you report cost per task.
  • 429 RESOURCE_EXHAUSTED — you hit the free tier's per-minute limit. Wait a minute and rerun; the scripts' --pause option adds a gap between runs.
  • Codespaces doesn't pick up the devcontainer — Codespaces only reads .devcontainer/ at the root of a repo. Use the portfolio template (its devcontainer covers all four HOS), or make this HOS folder the root of its own repo.
