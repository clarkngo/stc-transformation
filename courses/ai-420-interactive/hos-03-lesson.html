Lesson overview

O312.5% HOS + MP + CD + AC+ Team/Term Project checkpoint

Harbor Supply Co.'s customer-support agent passes a quick demo. Run six scenarios and it crashes on an order number with a "#", tells a customer a refund went through that never happened, loops on a shipment check, reports a confident wrong monthly total, and quotes the store's wholesale cost as the price. Three of those five never crash. They just finish politely, wrong.

Week 5 traces every run into Langfuse and builds a failure log from the traces alone — no source code. Week 6 opens the code, fixes each root cause by hand, and adds generic guards that let the agent recover from failures nobody planted. It ends with a quick Team/Term Project check-in.

Anchoring analogy

Debugging an agent from its trace is like an airline incident review from the flight recorder: you don't get to ask the pilot what they were thinking — you have the instrument readings, second by second, and you reconstruct the decision that went wrong. That's how on-call debugging of agents actually works: an exported trace, no access to the code, and a customer waiting.

Learning objectives

By the end of the two weeks you will be able to:

  1. Read a reasoning trace step by step: model input, decision, tool call, result, reply. O3
  2. Classify agent failures: tool-call errors, logic loops, invented actions, wrong data, wrong tool. O3
  3. Find the first step where a failure shows up — before reading the source. O3
  4. Fix root causes, and add generic self-correction: errors as observations, repeat-call detection, step budgets. O3
  5. Explain why a confident wrong answer is harder to catch than a crash. O3

Lecture: reading traces and making agents correct themselves

≈ 70 min3 short partsO3

Three short segments. Pause after each and try the quick check. Anything that stays fuzzy goes in your Muddiest Point.

Part 1 — What a reasoning trace shows ≈ 20 min

A reasoning trace is the step-by-step record of one run: every model input and output, every tool call with its arguments and result, and timing and tokens for each. Locally, run_scenarios.py prints one per scenario; with tracing on, each run also becomes a Langfuse trace with every model call and tool call as its own span.

[ 0.9s] CALL   list_orders({})
[ 1.0s] RESULT list_orders -> {"orders": [ ...5 orders... ]}
[ 2.3s] SAYS   "We received 5 orders in September, totaling $1,622.79."
Quick check

Nothing in that trace is an error. What would you check to know whether the answer is right?

Part 2 — Five ways agents fail ≈ 25 min

Failure typeWhat it looks like in a trace
Tool-call errorAn exception on a tool call — often bad arguments ("#1004" into an int).
Invented actionThe model calls a tool that doesn't exist, or says it did something no tool did.
Logic loopThe same call with the same arguments, again and again, getting no closer to done.
Wrong dataA tool returned incomplete or misleading data, and the model trusted it — a confident wrong answer.
Wrong toolA vaguely described tool matched the request better than the right one.

The rule for this HOS: diagnose from the trace first. Write your failure log — scenario, failure type, first step where it shows, symptom, likely root cause — before you open tools.py. Guessing from code is easy; production doesn't give you the code.

Part 3 — Self-correction: fix causes, then add guards ≈ 25 min

Fixing each planted bug makes this agent correct. Guards make the next agent resilient to bugs nobody planted. Both are ADK callbacks:

def error_as_observation(tool, args, tool_context, error):   # on_tool_error_callback
    return {"status": "error", "error": f"{tool.name} failed: {error}",
            "hint": "Check your arguments and try once more, or explain the problem."}

def repeat_call_guard(tool, args, tool_context):               # before_tool_callback
    # same tool + same args more than twice this run -> skip the call, tell the model to stop

Plus the step budget you already know from HOS 1. Reflection — the agent reviewing its own last result — is the fourth pattern; it catches some wrong-data failures, at the cost of an extra call.

Try it before the build

Open Trace Detective. Diagnose five traces without code, then switch guards on and watch which failures recover — and which don't.

Teaching note

Tell students up front that real models vary: one run might sidestep a bug (strip the "#" itself). That's a finding, not a failure of the lab — ask them to run twice and log what reproduced.

New words this week

Reasoning trace
The step-by-step record of a run: each model input and output, each tool call and result, with timing and tokens.
Logic loop
The agent repeats the same action (or a short cycle) without getting closer to done.
Confident wrong answer
A run that finishes politely and is wrong — no error anywhere.
Guard (callback)
Code that runs around every tool call to turn failures into something the model can recover from.
Reflection
A step where the agent reviews its own last result and decides whether to accept or retry.

    Concept Debate

    Graded · part of 5% CD categoryDiscussion board · 3 stages
    This week's question

    When a tool fails, is it safer for the agent to crash loudly or to recover and keep going?

    You'll argue the side your debate team is assigned, then argue the other one, then drop advocacy and synthesize.

    Your side this HOS

    Sides rotate each HOS. In HOS 3, Debate Team 1 argues Side A and Debate Team 2 argues Side B. Find your team under Communication → Groups in Brightspace. Not in a team? Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

    Side A — Recover and keep goingTeam 1 this HOS

    Turn errors into observations; let the model fix its input or explain the problem.

    • Customers get an answer instead of an error page.
    • Most tool errors are fixable input mistakes ("#1004").
    • Guards make recovery generic, not per-bug.

    Side B — Crash loudlyTeam 2 this HOS

    Stop the run and surface the error to engineers.

    • A crash is visible; a recovered-but-wrong answer isn't.
    • Recovery can hide bugs that should be fixed at the source.
    • For actions that move money, stopping is safer than improvising.
    Stage 1 · by Tue

    Initial position

    Argue your assigned side with one specific claim and one piece of evidence — a run, a trace, a simulator setting. Not a topic summary.
    Stage 2 · by Thu

    Argue the opposite

    Before replying to anyone, post the strongest version of the side you didn't hold.
    Stage 3 · by Sat

    Synthesis

    Drop advocacy. State a real position, citing at least one specific point from a classmate's post.
    Weak synthesis"Recovering is better for users but crashing is better for debugging, so both matter."
    Strong synthesis"Sam pointed out that s2 was worse because it didn't crash — the agent told Tom his refund was done. So: recover from input errors like s1, but for anything that claims an action happened, the guard should force a hand-off, not a retry. Recovery for reads, loud failure for writes."

    Grading: Participation — initial position plus response to at least one peer (50%) · Writing — quality of argument and reasoning (50%).

    Application Challenge — diagnose three traces from someone else's agent

    5% of courseDiagnose from traces — no source code

    You get three exported traces from a different agent than the one you built, and no access to its code — which is how on-call debugging usually works. For each: name the failure type, the exact step where it first appears, and the smallest change that would prevent it.

    Warm-up: name the failure

    Each line describes what a trace shows. Classify it.

    What to submit
    • For each of the three traces: failure type, the exact first step, and your evidence.
    • The smallest change that would prevent each (a tool fix, a description fix, or a guard).
    • Which of the three you'd fix first in production, and why.

    Grading: Judgment & reasoning (50%) · Transfer to the new scenario (35%) · Clarity (15%).
