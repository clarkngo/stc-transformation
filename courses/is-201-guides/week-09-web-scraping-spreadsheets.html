Week 9 — Web Scraping & Spreadsheets

Est. 2–3 hrs CO5 Pilot domains: Maritime & Marketing/E-commerce ⚖️ Evaluate before you scrape

Goal

Learn what requests, BeautifulSoup, and selenium each actually do, evaluate the ethical and legal constraints on scraping before writing anything that touches a real site, and practice the core skill — parsing structured markup to pull out specific data — on a bug that fails the way real scraping code actually fails: silently, by finding nothing.

⚠ A note on what this page can and can't do

The in-page Python sandbox in previous weeks runs entirely inside your browser tab — it has no real network access, and it categorically cannot drive a browser the way selenium does. So this week's runner doesn't pretend to run real requests/BeautifulSoup/selenium code — it runs the same parsing skill on a small HTML string that's already embedded in the page. That's an honest substitute for the parsing step, not for the network or browser-automation steps, which you'll do for real in your Codespace.

Steps

  1. What the three tools actually do

    • requests fetches a page's raw HTML over the network, given a URL. It doesn't understand the HTML at all — it just downloads text.
    • BeautifulSoup takes that raw HTML text and turns it into a structure you can search — "give me every element with this class name."
    • selenium drives an actual browser (clicking, scrolling, waiting) — needed only when a page's real content doesn't exist until JavaScript runs, which requests alone can't trigger.
    Ask your AI assistant, in your Codespace, for a small requests + BeautifulSoup example against a page you're allowed to scrape (see the ethics check below first). This page's sandbox can't run that safely, so this is a "do it in your Codespace" step, not an in-page one.

  2. Evaluate the ethical and legal constraints — before any code runs

    Before scraping anything real, check:

    What to check before you scrape a real site

    • robots.txt — most sites publish one at /robots.txt stating which paths automated tools are and aren't allowed to access. Respect it even though nothing technically stops you from ignoring it.
    • Terms of service — many sites explicitly prohibit automated scraping in their ToS, independent of what robots.txt says.
    • Rate limiting — sending requests as fast as code can loop can look identical to a denial-of-service attack from the target site's perspective, and can genuinely degrade the service for real users.
    • Personal data — scraping and storing personal information (names, emails, especially anything domain-sensitive like patient or financial data) raises privacy obligations well beyond "is this technically accessible."
    Write one or two sentences: for your domain's typical scraping target (a maritime traffic/berth schedule site, or a competitor's product listing page), which of these four constraints is the one most likely to actually stop the project — not the one that's easiest to check.

Common snags

  • Trying to run requests.get(...) in this page's runner — it won't work here by design; do the real network call in your Codespace terminal instead.
  • Confusing "no error" with "it worked" — an empty result list from a scraper is exactly as easy to miss as the swallowed exception from Week 6. Always check that you got the data you expected, not just that nothing crashed.
  • Runner says "Loading Python…" for a while — same as previous weeks, first load downloads a real Python runtime.
