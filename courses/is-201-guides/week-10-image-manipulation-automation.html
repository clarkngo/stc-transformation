Week 10 — Image Manipulation, Automation & Capstone

Est. 3–4 hrs CO6 Pilot domains: Maritime & Marketing/E-commerce 🎓 Domain Capstone

Goal

Meet Pillow and PyAutoGUI — image manipulation and desktop automation — then close the arc this whole course has been building toward: the requirements you surfaced in Week 5's Roleplay Feedback Loop become the working, demoable project you present this week.

⚠ Why this week has no in-page runner

Pillow needs a real image file to open and a package install this guide hasn't verified reliably enough to ship. PyAutoGUI is a different kind of impossible: it controls a real mouse, keyboard, and screen — there is no version of "run this in a browser tab" for that, on this page or any other. Both tools are real and worth knowing; this page just won't pretend to run them. The code below is for reading, not clicking Run on.

What you'll need

  • Your Codespace, with all nine previous weeks' work available to pull together
  • Your Week 5 Roleplay Feedback Loop transcript
  • Your AI coding assistant, signed in and ready

Steps

  1. Pick your domain lens

    # Maritime lens — read, don't run: resizing a scanned cargo # manifest image for a mobile display. from PIL import Image img = Image.open("cargo_manifest_scan.jpg") resized = img.resize((800, 600)) resized.save("cargo_manifest_thumbnail.jpg")

  2. What Pillow actually does

    Image.open(...) loads an image file into memory as an object you can inspect and transform — .resize(), .rotate(), .crop(), applying filters — then .save(...) writes the result back out to a new file. It's the same "read, transform, write" shape as the file work from Week 6, just operating on pixels instead of text.

  3. What PyAutoGUI actually does

    placeholder
    This is a fundamentally different kind of code than anything else this term. pyautogui.click(120, 340) doesn't compute or return anything — it physically moves a real mouse cursor to a screen coordinate and clicks, exactly as if a person did it. It's used to automate repetitive tasks in applications that don't offer any other way to control them programmatically.

  4. Assemble your capstone

    Pull together what you've built across the term into one working program that answers the vague request from Week 5's Roleplay Feedback Loop.

    What "assembled" means here

    1. Start from the Week 5 signature. Your function signature and docstring, refined by the stakeholder roleplay, is the spec you're building to.
    2. Reuse, don't rewrite, modules 2-8. The variable/loop logic (Week 2), the data structures (Weeks 3-4), the exception handling (Week 6), the class design (Weeks 7-8) — this is where they combine into one program instead of ten separate exercises.
    3. Add one Week 9 or Week 10 piece. Either a small data-extraction step (reusing the html.parser pattern from Week 9 against a fixed local snippet — not a live site) or an image-handling step using Pillow in your Codespace.
    4. It has to actually run. Not "the logic makes sense" — run it in your Codespace and watch it produce real output against realistic input.

  5. Prepare your presentation

    Structure your presentation around four things:
    • The problem — the original vague ask from Week 5, in one sentence.
    • What the roleplay changed — quote the specific clarifying question that reshaped your function signature.
    • A live demo — run it, don't describe it. Show the output, including what happens on realistic bad input.
    • What you'd catch next — one thing you'd add a Diff/Debug Sprint-style check for if you kept building this.

Common snags

  • Not sure what counts as "enough" for the capstone — it doesn't need to be large. A working function that correctly handles the Week 5 requirement, with one piece of real error handling and one domain-flavored data structure, is a complete capstone.
  • Presentation turning into a code walkthrough instead of a demo — run it first, then explain what you're looking at. Reading code line-by-line is not the same as showing it work.
